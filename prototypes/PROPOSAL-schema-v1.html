主流对照：Immich asset 表的 12 条模式

以下全部来自真实源码（server/src/schema/tables/asset.table.ts），不是文档或教程。

#模式 证据（真实字段）对我们的意义
1软删除是一等公民 @DeleteDateColumn()
deletedAt: Timestamp | null		 验证了我 v1 的 deleted_at_ms。回收站必须靠"标记"而不是"删行"。
2哈希必须带算法 checksum: Buffer
checksumAlgorithm: enum		 我之前只写了一个 content_sha1 —— 不够。 一个裸哈希在换算法后无法解释。必须成对：kind + value。
3路径与文件名分列 originalPath
originalFileName（各自建索引）		 我 v1 已有 rel_dir + stem/name，方向对。 但 文件名要能模糊搜（见第 8 条）。
4id 是生成的，与路径无关 @PrimaryGeneratedColumn() id 这条验证了我上一轮发现的致命缺口。 Immich 的 id 不随文件改名变化 ⇒ 它天然没有"改名丢标注"这个问题。 我们必须照做。
5三个时间语义分开 fileCreatedAt（内容时间）
fileModifiedAt（mtime）
localDateTime（展示时区）		 我只有 mtime 一个时间。 "这张图是什么时候拍的/做的"与"文件什么时候被改过"是两件事—— 前者用于浏览排序，后者用于判过期。混成一个就会错。
6收藏是一列布尔 isFavorite: boolean default false 不是关联表。比特级的用户意图直接落列，因为"筛收藏"是高频查询。 我们归到意图层（见下）。
7可空 scope 的唯一约束 → 两条偏唯一索引 (ownerId, checksum)
  WHERE libraryId IS NULL
(ownerId, libraryId, checksum)
  WHERE libraryId IS NOT NULL		 SQL 里 UNIQUE 对 NULL 的处理是坑（多个 NULL 不冲突）。 Immich 用两条偏索引绕开它。我们要防"同一文件被重复登记"，正好用得上。
8文件名模糊搜索 using:'gin'
expression: f_unaccent(
  "originalFileName")
  gin_trgm_ops		 我之前说"本应用是语义搜索不需要关键词"——那是错的。 "按文件名找"是管理场景的基本需求，且语义搜索答不了（你说不出那段描述）。 SQLite 对应物：FTS5 trigram 分词器。
9存缩略图占位哈希 thumbhash: Buffer | null ~25 字节就能让整个网格秒出模糊占位，不必等缩略图加载。 对我们的瀑布流是直接收益——先画出色块，再渐进换真图。
10分辨率是两个整数列 width: integer | null
height: integer | null		 我 v1 把分辨率留成了展示字符串 1920 × 1440。 字符串不能排序、不能筛"≥4K"。必须拆成两个整数。
11可见性是枚举，不是一个布尔 visibility: enum
default Timeline		 "隐藏/归档/锁定"是多态维度。用多个布尔会产出 2ⁿ 个非法组合。 我们暂不需要，但要知道这条纪律。
12重复项分组靠一个 id duplicateId: uuid | null
（indexed）		 同一 duplicateId 的行互为重复。 我们 F5 的"重复 / 疑似重复"需要这个——否则每次体检都要重算全库两两比较。
第 4 条把上一轮的致命缺口钉实了。我们的 uid = sha1(lib_id | rel_dir | stem).slice(0,12) 是路径的纯函数 ⇒ 改名即丢全部标注。 Immich 的做法是 @PrimaryGeneratedColumn() id——生成一次，永不变，路径只是属性。 必须照抄这条，否则这套 schema 撑不起"管理系统"这个定位。

这个前提解锁了什么

旧的妥协绿地下的解法
items 是 18 列宽表，缺包时压缩包的 6 个字段全是 NULL 拆出 asset_file，一行一个文件角色。 缺包 = 少一行，而不是一个 NULL 块。将来加"缩略图/预览视频"也只是多一种 role。
mtime 有三种舍入口径并存 （Math.floor / Math.round / BigInt 截断） 定义唯一口径并写进字段名：mtime_ms。 单位出现在名字里 ⇒ "秒 vs 毫秒"在类型层面不可能搞混。全部数值字段同此约定。
删除靠 ON DELETE CASCADE， 与"移入回收站、可恢复"直接矛盾 第一天就 soft delete：asset.deleted_at_ms。 行不删，元数据永不跟着消失；恢复出来的条目标签评分完好。
状态派生 ⇒ 无法索引，我硬扛着 6 个筛选芯片 只对真正跨表比较的那一档做最小物化：一个由扫描器顺手维护的布尔列 + 偏索引。其余档位仍然纯派生且天然可索引。

分层原则：按「谁拥有它」和「能不能算回来」分

这张表是整份设计的地基。每一张表先回答两个问题： 谁写它？ 删掉能不能算回来？

层谁写 可算回来吗含义与后果
事实 扫描器（stat 文件系统） 可以 素材的文件事实。删掉重建即可，零风险。重建时整层丢弃。
处理 索引任务 / 体检 昂贵 重跑一遍能得到，但 3594 条要 ~11 分钟、几万条要几小时。 尽量保留——重建它的代价是时间和电。
意图 用户（你） 不能 标签 / 评分 / 备注 / 排除 / 交付历史。 丢了就是真丢了。重建流程必须原样保留，且要能导出备份。
"能不能算回来"决定重建行为，而不是"哪张表"。 所以重建的规则一句话：丢事实层、留处理层与意图层。 这条规则写进代码一处，再由单测钉住（新表忘了分类 ⇒ 测试变红）。

命名约定：把单位写进字段名

时间
  • *_at_ms — Unix 毫秒整数
  • *_ms — 时长/时刻，毫秒
  • 规范来源：BigInt mtimeNs / 1_000_000n（截断）
  • 不用浮点、不用秒
体积
  • *_bytes — 字节整数
  • 不存 "2.4 MB" 这种字符串
  • 格式化是界面的事
布尔
  • INTEGER + CHECK (x IN (0,1))
  • SQLite 没有真布尔；用 CHECK 约束把坏值挡在门外
标识
  • uid — 12 位小写 hex，全局唯一
  • *_id — nanoid，不用自增整数
  • 自增 id 在跨库合表时会撞

两个数据库，不是一个

绿地前提下可以把这个划清楚。现状是"库注册表放 userData JSON、其余放库根 SQL"—— 那是对的，但没被明确成原则。

userData/app.db 应用级 · 4 张表
  • app_meta — 版本与迁移
  • library_registry — 库注册表（含 sort_order）
  • app_setting — 设置（外观/模型目录/快捷键）
  • collect_dir — 取件白名单（安全边界）
  • activity — 操作记录
  • recent_query — 搜索历史
  • 为什么必须独立：一个库里的数据库存不了"有哪些库"—— 鸡生蛋问题。这条在现有代码里已经存在（library-registry.json），只是没用 SQL。
<库根>/.gs.db 库级 · 12 张表
  • 事实层 — asset · asset_file · asset_name_fts
  • 过程层 — asset_index_state · job · health_run · health_finding · recent_view
  • 意图层 — asset_user_meta · tag · asset_tag · collection · collection_item · asset_export
  • 跟着库走：拷库即带走全部标注。模型不在库内，换机器仍需自备模型。

应用级表（userData/app.db）

app_meta

本轮 单行表，和现有 schema_version 一样的手法： CHECK (id = 1) 让"只能有一行"变成数据库层面的约束，而不是靠约定。
字段类型约束说明
idINTEGER PKCHECK id=1 单行守卫。
schema_versionINTEGER NOT NULL 迁移版本。版本不符 ⇒ 重建（绿地模型明确接受这件事）。
created_at_ms / updated_at_msINTEGER NOT NULL建立 / 最后迁移时刻。

library_registry

本轮 哪些文件夹被登记为素材库。不可再生——扫文件系统扫不出"你把哪个目录当库"。
字段类型约束说明
lib_idTEXT PK格式 1–32 字符 库标识，写进 uid 的派生公式 ⇒ 一旦分配不可改。
rootTEXT NOT NULLUNIQUE 库根绝对路径。UNIQUE 防止同一个目录被登记两次。
display_nameTEXT NOT NULL 界面显示名。与 root 分开——名字是你的，路径是事实。
enabledINTEGER NOT NULLCHECK 0/1DEFAULT 1 是否参与检索与入库。停用不动任何文件。
compat_keyTEXT NULL 这个库的索引是用哪套 8 段兼容键建的。不兼容的库不能合并检索。
sort_orderINTEGER NOT NULLDEFAULT 0INDEX v1.2 新增。侧栏库列表的顺序。 顺序是你的，不该由路径字母序或登记时间决定—— 你有 4 个库时，"常用的排前面"是真实需求。同值时按 lib_id 兜底保证稳定。
registered_at_ms / updated_at_msINTEGER NOT NULL登记 / 修改时刻。
移除库的三种语义行为（这是产品决定，不是实现细节）
① 仅取消登记
（默认）		 删注册表行。库根下所有 .gs-* 文件原样保留—— 下次登记回来立刻能用，标注全在。这是默认，因为它完全可逆。
② 取消登记并删除本库数据库 删 .gs-index.bin + .gs.db。 必须两段式确认，且明确写出会丢什么（标注条目数 / 集合数 / 排除数）。 确认框里给"先导出一份"的入口（见下方导出节）。
③ 删除素材文件本身 不提供。与写入不变式冲突——软件永不删素材。 要删素材请到文件管理器里删，软件只负责发现它不见了。
为什么"移除库"必须写清是三种里的哪一种。 界面上一个"移除"按钮，用户理解成①（取消登记）还是②（连数据一起删）， 差别是几百条标注。这种歧义不能靠用户猜——只能把三种都摆出来，默认选可逆的那个。

collect_dir

本轮 取件白名单目录。不可再生——这是安全边界，不能猜。
字段类型约束说明
dir_idTEXTPKnanoid。
labelTEXT NOT NULLUNIQUE 目录名（"素材待用" / "移出素材"）。
abs_pathTEXTNOT NULL 绝对路径。取件只允许写进这些目录，其余一律拒绝。
is_defaultINTEGER NOT NULLCHECK 0/1DEFAULT 0 默认取件目标。界面只应允许一个为 1。

app_setting

v1.2 新增 设置页要存的东西（外观 / 模型目录 / 取件目标 / 快捷键 / 诊断开关）。 我之前描述应用级 DB 时写了"设置"，却没建这张表——说得比做得多。
字段类型约束说明
keyTEXT PK 设置键。形如 theme / model.dir / collect.default。
value_jsonTEXT NOT NULL 值，统一存 JSON（字符串也是 JSON 字符串）。 这样布尔/数组/对象不必各开一列，加设置不需要迁移。
updated_at_msINTEGER NOT NULL最后修改时刻。
纪律为什么
键与类型只有一个定义处 形状用 zod 定义在 shared/ipc.ts（契约唯一来源）， 本表只负责存。不许在界面里各写一份默认值——那就是第二份定义（P1）。
类型化取值走一个 helper 读设置时用 zod 解析。解析失败退回默认值并记一条警告，不要让整个界面崩—— 手改过 DB 或跨版本降级都会走到这条路径。
不存可从别处推导的东西 例如"当前库"是运行时状态，不该存成设置。 设置只装"用户显式表达过的偏好"。

activity

v1.2 新增 操作记录页的存储。它跟 asset_export 不是重复： 一次"批量交付 12 条" = 这里 1 行 + asset_export 12 行。 这张表答"谁在什么时候做了什么"，那张表答"哪些条目被导到哪里"。
字段类型约束说明
activity_idTEXT PK nanoid。也是批量操作的 batch_id（一族操作归一个 id）。
at_msINTEGER NOT NULLINDEX DESC 发生时刻。倒序索引 ⇒ 列表页第一屏是索引扫描。
kindTEXT NOT NULLCHECK 枚举 collect / deliver / trash / restore / purge / tag.add / tag.remove / collection.add / index.exclude / index.include / library.add / library.remove / library.toggle / index.rebuild。 用 CHECK 而不是自由文本，否则筛选与统计无从下手。
subject_kindTEXT NOT NULLCHECK 枚举 asset / library / tag / collection / app。
subject_idTEXT NULL 对象 id（uid / lib_id / tag_id …）。批量操作时为空，明细在 detail_json。
lib_idTEXT NULL 涉及哪个库。可空——因为有些操作（登记库）不属于任何库。
resultTEXT CHECK ok/skipped/failed 与 asset_export.result 同一套词。
detail_jsonTEXT NULL 结构化参数，不存渲染好的文字。 理由见下。
为什么 activity 不存"人话那一行"。 直觉做法是存一条渲染好的文案（"已把 12 条移入回收站"），省得前端再拼。 但本项目的纪律是「用户文案兜底只允许一份」—— 一旦把渲染结果写进库，同一句话就有了两个来源（历史的与现在的）， 改一次措辞就会出现新旧两种说法混在同一个列表里。 ⇒ 存 kind + detail_json， 由 Adapter 渲染（唯一文案处）。

recent_query

v1.2 新增 搜索历史。与 recent_view 分开： 前者是"我搜过什么"（跨库），后者是"我看过哪条"（属某个库的某条素材）。
字段类型约束说明
query_idTEXTPKnanoid。
kindTEXT CHECK text/image 文字搜 / 以图搜图。两者要分开记，否则重跑时不知道该拿什么当输入。
textTEXT NULL 查询文本（kind='text' 时非空）。
image_refTEXT NULL 以图搜图时的参考图 uid（kind='image' 时非空）。 存 uid 不存绝对路径——路径会变，uid 不会。
scope_lib_idTEXT NULL 当时的检索范围。NULL = 全部库。 重跑时必须还原当时的范围，否则结果对不上，用户会以为索引坏了。
result_countINTEGER NULL 当时命中数。用于显示与"结果变少了"的对照。
at_msINTEGER NOT NULLINDEX DESC 查询时刻。
纪律为什么
保留上限（如最近 200 条） 插入时修剪。历史表不设上限就会无限长，而它只服务"接着上次"这一个用途。
同一文本重复搜 → 更新时间戳
而不是新增行		 否则搜十次同样的词就占十行，把真正不同的历史挤掉。 UNIQUE (kind, text, scope_lib_id) + upsert。

库级表 · 事实层（<库根>/.gs.db）

asset

本轮 只有"条目"这个概念本身，不再带任何文件字段。 对比现状：从 18 列缩到 9 列，且缺包不再是一堆 NULL。
字段类型约束说明
uidTEXT PK12 位小写 hex v1.1 改动：生成一次，永不变（对齐 Immich 的 @PrimaryGeneratedColumn() id）。 不再是 sha1(lib_id|rel_dir|stem) —— 那个公式让改名/移动 = 丢掉全部标注。 现在的规则：扫描时先按 (lib_id, rel_path) 匹配， 匹配不上再按 content_hash 或 (size_bytes, mtime_ms) 认领，命中则保留原 uid，只更新路径。
lib_idTEXT NOT NULLINDEX 所属库。虽然每个库一个文件，仍显式带上—— 便于将来把多库的体检结果并起来看。
folderTEXT NOT NULL 一级分类目录（CR / VR / CR+VR / 其他）。
stemTEXT NOT NULL 文件名主干。参与配对（找同名压缩包）。改名时更新它，但不动 uid。
display_nameTEXT NOT NULL 界面显示名。与 stem 分开（对齐 Immich 的 originalFileName）：你可以只改显示名而不动磁盘上的文件。
rel_dirTEXT NOT NULL 相对库根的目录（不含文件名）。 索引以相对路径为准 ⇒ 库整体搬盘后索引仍可用。
content_created_at_msINTEGER NULLINDEX v1.1 新增（对齐 Immich 的 fileCreatedAt）。 "这张图是什么时候做的"——用于按内容时间浏览排序。 取不到就 NULL（很多素材没有 EXIF）。与 mtime_ms 是两件事： 前者是内容时间，后者是文件被改过的时间。
deleted_at_msINTEGER NULL偏索引 软删除（对齐 Immich 的 @DeleteDateColumn）。 NULL = 在用；非空 = 已移入回收站。 所有常规查询默认 WHERE deleted_at_ms IS NULL。
dup_group_idTEXT NULLINDEX v1.1 新增（对齐 Immich 的 duplicateId）。 同一 id 的行互为重复，由体检填写。 不存它就是每次体检都要重算全库两两比较——几千条能跑，几万条跑不动。
discovered_at_msINTEGER NOT NULL首次被发现时刻。用于"最近入库"。
updated_at_msINTEGER NOT NULL本行最后修改时刻。
索引 / 约束覆盖什么（含 v1.1 新增）
PRIMARY KEY (uid)按 uid 取单条。
UNIQUE (lib_id, rel_path) v1.1 新增：防止同一个文件被登记两次。 因为 uid 不再由路径派生，路径的唯一性必须自己声明—— 这是"id 与路径解耦"必须付的代价。
idx_asset_live (lib_id, folder) WHERE deleted_at_ms IS NULL 偏索引：库页按分类浏览（最常用）。排除回收站行 ⇒ 索引更小更快。
idx_asset_trash (deleted_at_ms) WHERE deleted_at_ms IS NOT NULL 回收站列表。只索引已删除的那几十行。
idx_asset_stem (stem)配对与按名查。
idx_asset_created (content_created_at_ms) v1.1 新增：按内容时间排序（"按拍摄/制作时间浏览"）。
idx_asset_dup (dup_group_id) WHERE dup_group_id IS NOT NULL v1.1 新增：只看有重复的那些。偏索引避免索引几万行 NULL。
为什么分辨率不在 asset 上。 Immich 把它放在 asset（因为它的 asset 就是一个主文件）。 我们一个条目有两个文件（图 + 包），宽度高度属于那个图—— 所以放 asset_file，别放在条目上。

asset_file

本轮 绿地设计里最重要的一张新表。 一行一个文件角色 —— 把现状那 11 个"图/包各一套"的列压成 6 个通用列。
字段类型约束说明
uidTEXT FK asset.uidPK(1/2)CASCADE 条目。
roleTEXT PK(2/2)CHECK image/archive 文件角色。缺包 = 没有 role='archive' 的行。 将来加"预览视频/许可证 PDF"只是扩 CHECK 列表。
rel_pathTEXT NOT NULLINDEX 相对库根路径。索引与定位都以它为准。
extTEXT NOT NULL 扩展名（小写，不含点）。
size_bytesINTEGER NOT NULL字节数。单位在名字里。
mtime_msINTEGER NOT NULL 唯一口径的修改时刻：BigInt mtimeNs / 1_000_000n（截断）。 判"文件被外部改过"就比它。 注意它与 asset.content_created_at_ms 是两件事—— 这个用于判过期，那个用于按内容时间浏览。

content_hash_kindTEXT NULLCHECK sha1/sha256 v1.1 新增，成对出现（对齐 Immich 的 checksumAlgorithm）。 一个裸哈希在换算法后无法解释——你必须知道它是怎么算出来的。
content_hash_valueTEXT NULL偏索引 内容哈希值。惰性计算——只在体检查重复时算，不扫描时算。 全库算一遍要读几十 GB，不能塞进日常路径。 与 kind 是一对，缺一不可。
索引 / 约束覆盖什么
PRIMARY KEY (uid, role) 一行一个文件角色；天然防止同一条目出现两个 role='image'。
idx_asset_file_path (rel_path) 按路径反查条目（扫描时用来匹配已有行）。
idx_asset_file_hash (content_hash_kind, content_hash_value)
WHERE content_hash_value IS NOT NULL		 v1.1 新增：体检查"完全相同"的重复项。偏索引—— 绝大多数文件还没算过哈希，不该被索引。
idx_asset_file_dims (width, height) WHERE role='image' v1.1 新增：筛"分辨率 ≥ 4K"这类条件。偏索引只覆盖图片角色。

asset_name_fts

本轮 v1.1 新增。我之前说"本应用是语义搜索，不需要关键词检索"—— 那是错的。"按文件名找"是管理场景的基本需求，而语义搜索答不了它 （你说得出"金属质感头盔"，说不出"那个叫 bracket_131 的文件"）。 对齐 Immich 的 gin_trgm_ops 文件名索引。
定义说明
FTS5 虚表
tokenize='trigram'		 SQLite 的 FTS5 自带 trigram 分词器（3.34+）， 等价于 Postgres 的 pg_trgm： 支持子串匹配（搜 bracket 能命中 bracket_131），而普通全文索引做不到子串。
external content
= asset		 用外部内容表模式，不重复存正文，只存索引。 用触发器与 asset 保持同步—— 比"每次改完记得重建索引"可靠。
索引列 display_name · stem · rel_dir（来自 asset）+ note、标签名（来自意图层）。 备注和标签也要能搜，否则"我记过一条关于它的备注"就白记了。
FTS 和语义检索是两条不同的路，不要混。 语义搜索（向量）回答"意思相近的东西"，关键词/子串搜索回答"名字里有这个词的东西"。 界面要分别给出，不能把两种分数排在一个列表里——分数不可比。 这也正是项目原有纪律里"不得跨模态比分数"的延伸。
这张表顺手修掉一个既有缺陷。现状 engine.ts 用 Number(st.mtimeNs / 1_000_000n)， 而 build_index_onnx.ts 用 Math.floor(st.mtimeMs)， 测试里又有 Math.round(st.mtimeMs) —— 同一个文件走不同路径会得到不同的 mtime，而 engine 拿它做相等比较判"改过没有"。 绿地模型下 asset_file.mtime_ms 是唯一写入口， 口径由它定义，别处只读。

库级表 · 处理层

asset_index_state

本轮 1:1 于 asset，主键即外键。抄 Immich asset_job_status 的"存时刻不存枚举"。 但比它多一个物化标志，理由见下。
字段类型约束说明
uidTEXT PKFK asset.uidCASCADE 1:1。主键即外键，不需要额外关联表。
encoded_at_msINTEGER NULL偏索引 编码成功时刻。NULL = 从未成功。 偏索引 WHERE encoded_at_ms IS NULL ⇒ "待编码/失败"筛选是索引查找而非全表扫。
encoded_mtime_msINTEGER NULL 编码那一刻该文件的 mtime 快照。 这是判"文件改过没有"的基准 —— 存快照，不存布尔，因为快照还能回答"何时改的"。
compat_keyTEXT NULL 编码时用的 8 段兼容键。与库当前 compat 不等 ⇒ 模型换了，向量不在同一语义空间。
needs_reencodeINTEGER NOT NULLCHECK 0/1DEFAULT 0偏索引 唯一一处物化。由扫描器顺手维护（它本来就要 stat 每个文件）。 偏索引 WHERE needs_reencode = 1 ⇒ 只索引异常的那几十行。
attempt_countINTEGER NOT NULLDEFAULT 0 累计尝试次数。失败 3 次后不再自动重试——避免一个坏文件每次建索引都拖慢一遍。
last_errorTEXT NULL 上次失败原因，存人话不存错误码。直接显示给用户，前端不再翻译一次。
last_error_at_msINTEGER NULL 上次失败时刻。与 encoded_at_ms 并存合法： "三天前成功过、今天重编码失败"是真实状态。
excluded_at_msINTEGER NULL偏索引 用户手动排除索引的时刻。本表唯一完全不可再生的字段。 判定优先级最高——你的选择不该被任何系统推断覆盖。
checked_at_msINTEGER NULL 上次差分扫描的时刻。界面据此显示"这个状态基于何时"， 避免"库里显示已编码、其实文件三个月前就被换过"这种静默错误。
为什么只有 needs_reencode 一个物化列，而不是整张 state 表。 状态里只有一档是跨表比较（encoded_mtime_ms ≠ 当前 mtime_ms）， 其余全是IS NULL判断——本身就可索引。 全量物化一个 state 列会引入"缓存漂移"这个新故障，而我们只需要修那一档。 ⇒ 最小物化 + 偏索引，代价与风险都最小。
needs_reencode 是缓存，不是真相。 真相是"encoded_mtime_ms 与当前 mtime_ms 相不相等"。 所以体检里要有一项：重算全库的 needs_reencode，与库里存的值比对， 不一致就报出来并修正。这是可机械断言的对账，把"缓存漂移"变成能被发现的问题。

库级表 · 任务层（v1.2 新增）

这是最要紧的一处补齐。在此之前所有任务（扫描 / 索引 / 体检 / 重建 / 入库） 的进度只活在内存里——进程一崩就什么都不知道了，而且无法断点续跑。 规格明确要求"进度必须单调且不静默"，内存里的进度两条都做不到。

job

v1.2 新增 一条任务一行。用状态枚举 + 时刻，不是纯"时刻模式"—— 因为任务有生命周期（排队→运行→结束），一条时刻列表达不了"现在正在跑"。
字段类型约束说明
job_idTEXTPKnanoid。
kindTEXT NOT NULLCHECK 枚举 scan / index / health / rebuild / ingest。
stateTEXT NOT NULLCHECK 枚举偏索引 queued / running / done / failed / cancelled。
progress_doneINTEGER NOT NULLDEFAULT 0 已完成数。只增不减——"进度单调"这条规格在字段层的落点。
progress_totalINTEGER NULL 总数。可空：扫描前还不知道有多少，不要为了显示百分比编一个。
phaseTEXT NULL 当前子阶段（"统计文件" / "编码第 3 批"）。 "不静默"的意思是这条会变，而不是只有一个转圈。
cursor_jsonTEXT NULL 断点续跑位置（如最后处理成功的 rel_path）。 崩溃后重启从这继续，而不是从头再来一遍 3594 条。
heartbeat_at_msINTEGER NULL 崩溃检测的关键。运行中定期刷新。 启动时把"running 但心跳已过期"的任务判为 failed——否则它会永远卡在"运行中"， 界面永远显示一个不存在的进度。
summary_jsonTEXT NULL 结束时的统计（新增 / 缺失 / 失败各多少）。
errorTEXT NULL 失败原因。存人话，直接可显示。
queued_at_ms / started_at_ms / finished_at_msINTEGER NULL 三个时刻。finished - started 就是实际耗时，用于"还要多久"的估算。
索引 / 约束覆盖什么
idx_job_active (state)
WHERE state IN ('queued','running')		 偏索引：启动时找活跃任务、界面轮询进度。 历史任务不进索引 ⇒ 跑过几百次后索引也不膨胀。
idx_job_recent (queued_at_ms) 任务历史列表。
至多一个活跃任务 项目已有 p-queue 与 single-flight.ts 做串行化， 但那是内存里的保证，进程重启就没了。 期望用一条偏唯一索引把它变成数据库层保证： UNIQUE ON job((1)) WHERE state IN ('queued','running')。 需在 SQLite 上实测 常量表达式偏唯一索引是否被接受——不行就退回"单测断言"。

六条设计决定

决定为什么
按 uid 对齐，不按路径 uid 稳定（v1.1 已改成生成式）⇒ 换机器、搬库、改名之后导入仍能对上。 若按路径对齐，用户整理过一次目录，整份导出就全废了。
必带 version 格式一定会变。没有版本号的文件，导入端只能猜。 识别到更高版本 ⇒ 明确拒绝并说明，不要半懂不懂地导进去。
只导意图层 事实层能扫回来，过程层能重跑。导出它们会让文件臃肿几十倍而无收益。
导入三策略，默认"合并" 合并（默认，以 uid 为键，冲突时取 updated_at_ms 较新者）/ 仅补空缺（只填当前为空的值，不覆盖任何已有标注）/ 覆盖（危险，两段式确认）。默认必须是可逆的那个。
导入前先自动备份当前状态 导入是批量写。写之前先把现状导出一份到 <库根>/.gs-backup/（保留命名空间内）。 这样"导入错了"也还有回头路。
不含素材文件 只导标注。导出/导入永远不碰素材目录——与写入不变式一致。
导出文件里出现"孤儿 uid"是正常的，不要当成错误。 导出之后你删了几条素材，再导入时那些 uid 在库里已经不存在。 正确处理是跳过并计数（"12 条标注的目标已不存在"）， 而不是整个导入失败——否则一份备份会因为一条被删的素材而永远导不回来。

随功能上线的表（本轮不建）

表跟哪个功能为什么现在不建
doc_dirF7 文档检索 门控 进入条件是"先拿 10–30 份真实文档"。现在建表就是建一个永远空着的表。 它是意图层（你加过哪些文档目录，扫不出来）—— 现状 doc_dirs 会被重建抹掉，这条才是真缺陷，随它一起修。
document / doc_chunkF7 门控 同上，属事实层。分块参数（600–900 字符 / 12% 重叠）还没实测校准过。
v1.2 把这张表里的三项挪进了"本轮"。 health_run / health_finding（体检台账，属过程层，随 F5 落地）、 asset_name_fts（关键词搜索，我上一版判断错了）、 以及元数据导出/导入（它不是表，是必须有的机制）。

这个前提也解决不了的

schema 不是唯一要改的东西。 三种 mtime 口径的分歧在 packages/indexer 与 packages/engine 的代码里， 不在表里。改 schema 定义不了"谁来写这个值"。 ⇒ 必须同时改生产者，而这按 AGENTS.md 的编码护栏 要求先有基线证据（全库 min/中位余弦 + top10 对照），改完重跑同一基线对比。
"不兼容"不等于"可以丢数据"。 现有 items.json 与 .gs-index.bin（3594×768，12.4 MB）是唯一能证明检索质量没退化的基线。 绿地重建 schema 时：索引文件格式与 items.json 都要保留可读， 否则你无法回答"重建前后检索结果是否一致"。这也正是 P-0 编码护栏存在的理由。

落地顺序（顺序本身是设计的一部分）

0 先留基线，再动任何编码/索引路径 全库 min 与中位余弦 + 若干查询的 top10 对照，归档到 reports/。没有这份基线，后面每一步都无法证明没退化。 这条是 AGENTS.md 的硬性护栏，不是我加的。
1 统一 mtime 口径（改生产者代码） 定义 mtime_ms 的唯一公式，改 indexer / engine / 主进程三处； 加一条单测断言"同一文件经三条路径得到同一个值"。先于 schema 落地—— 否则新表装进去的就是不一致的数据。
2 写绿地 migrations（应用级 4 张 + 库级 14 张） 作为 v1 一次性建立，不是增量。现有 .gs.db 与 app 侧一律丢弃重建（绿地前提明确接受）。 索引文件不动。应用级与库级是两套独立迁移—— 它们版本可以不同步（应用升级不该强制重建所有库）。
3 写"层"分类常量 + 单测 18 张表按事实 / 过程 / 意图 / 应用四组写在一处； 单测断言"迁移里建的表必须每一张都被分类"。 新增表却忘了分类 ⇒ 测试变红。这是防漂移的唯一机械手段。
4 任务表接线：心跳、断点续跑、崩溃恢复 扫描 / 索引 / 体检 / 重建 / 入库全部改成写 job 表。 启动时把"running 但心跳过期"的任务判为失败， 否则界面会永远显示一个不存在的进度。 体检改为挂在 job 上，不另写一套任务机制（P1）。
5 重建流程重写：丢事实层、留过程层与意图层 现在 removeGsDbFiles 是删整个文件， doc_dirs（意图层，扫不出来、真会丢）就这样没了； asset_index_state 里的排除名单同理。 新流程：读过程层与意图层 → 重建 → 写回。真损坏时如实告知"救不回来"。 注意 health_* 是过程层——它丢了只是要重跑，不算数据丢失。
6 元数据导出 / 导入 只导意图层，版本化 JSON，按 uid 对齐。 它必须先于重建流程改好——否则第一次重建就没有兜底。 也要接进"移除库"的确认框（"先导出一份"）。
7 清空重建：老 schema 的一次性迁移 启动时发现旧版本 .gs.db ⇒ 丢弃重建（绿地前提）。 但要做两件事：① 先把意图层能读的都读出来做一次导出 （老库里 doc_dirs 可能真有数据）； ② 明确告知用户发生了什么，不要静默重建。
