6 张表满足哪些功能

一句话：支撑的是库管理 → 扫描入库 → 浏览/详情 → 检索 → 取件 → 索引状态与维护；支撑不了的是一切「用户标注类」与「历史与任务类」。

先把最容易混的一件事分清：「表能支撑」≠「代码已通」。表已就位，但 scan / search / item / collect 还是旧实现、IPC 契约也没重列、6 个走旧 items 表的测试还是红的 —— 那些归 S2 / S3 + 契约卡。下面列的是表的支撑能力。

4 · 若要把两张提前（等你一句话才落）

下面两张按你已定的 B 口径（只建现在就要用的表）暂不建；若你要提前，字段定稿如下（仍走同一套迁移引擎与四层分类）。

job

待批准 任务。心跳管崩溃检测、游标管断点续跑 —— 没有它，进度只活在内存，崩了就没。过程层。
字段类型约束说明
job_idTEXTPKnanoid。
kindTEXTCHECK scan / index / rebuild / …任务种类。
stateTEXTCHECK queued / running / done / failed / cancelled状态机。

5 · 结论

本轮 100 条 + 索引这条链

6 张够：扫描 → 索引 → 检索 → 详情 → 取件，全部有落点。

但「管理系统」最常摸的三件事

标注（标签/评分/备注）与交付留痕缺失 —— 前者要 3 张表，后者要 1 张。

我建议第二轮先补两张

job（进度不静默 + 断点续跑）· asset_export（F6 三分类落点）—— 是功能承诺，不是锦上添花。

改动成本

绿地之下：加表 = 一条迁移 + 分类里加一行（那条「每张表必须被点名」的断言会逼着分类）。

6 · 这份对照证明不了什么

  • 「能支撑」是按字段是否存在判断的，没有跑过这些功能（S2/S3 才接线）。
  • 「部分支撑」里的性能判断（如 LIKE 能不能凑合）是按 3594 条量级估的，不是实测。
  • 第二批的优先级是我的建议，不是所有者裁定。
