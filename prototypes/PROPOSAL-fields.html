字段设计 · 索引状态与用户元数据

完整到可以照着写 migrations。来源：Immich 真实 schema（取其两条模式）， 并对齐本项目已有的 items 表与写入不变式。

三条核心决定

#决定为什么
1 状态不落库，只存"上次成功的时刻" 抄 Immich asset_job_status：整张表只有 nullable timestamp。 「待重编码」是算出来的（encoded_at < 文件 mtime），不是存出来的。 存了就要维护，维护就会漂移。
2 每个关注点一张表，不堆宽表 items 已经是 18 列的宽表，它的语义是 "扫描出来的文件事实"。用户字段塞进去会污染语义，也会让"重建时保留谁"变得无法表达。
3 所有新表都是"持久"类，重建时必须保留 这是上一轮那个真缺陷的解药：现在 libraryRebuild 删整个文件， doc_dirs、health_* 已经会被抹掉。 新表进来之前，先把"保留谁"这条规则定死。

① item_index_status —— 索引状态

item_index_status

新增 持久类 1:1 于 items，主键即外键。独立成表而不是加列到 items：它的写入者是索引任务、读取者是界面，生命周期和热表不同。
字段类型约束说明
uidTEXT PKFK items.uid 条目稳定标识。1:1 关系靠"主键即外键"表达，不需要额外的关联表。
encoded_atINTEGER NULL 编码成功时刻（Unix ms）。NULL = 从未成功编码。 这一列是整套状态的地基——「已编码 / 待编码 / 待重编码」全由它算出来。
compat_keyTEXT NULL 编码时用的 8 段兼容键。compat_key != 库当前 compat ⇒ 模型/参数换了，向量已不在同一语义空间 ⇒ 待重编码。 这是"换模型必须全量重建"这条规格在字段层的落点。
encode_errorTEXT NULL 上次失败原因，存人话不存错误码（如"文件不是可用图片"）。 NULL = 没失败过。直接显示给用户，不需要前端再翻译一次。
encode_error_atINTEGER NULL 上次失败时刻。与 encoded_at 并存是合法的： "三天前编码成功过、今天重编码失败了" 是真实存在的状态。
encode_attemptsINTEGER NOT NULLDEFAULT 0 累计尝试次数。用途：失败 3 次后不再自动重试，避免一个坏文件每次建索引都拖慢一遍。 也让你在界面上能说"已试过 3 次"。
excluded_atINTEGER NULL 用户手动排除索引的时刻。这是本表唯一"不可再生"的字段—— 其余列重跑一遍编码就能重建，这一列丢了就真没了。 它也是判定优先级最高的那一档：你的选择不该被任何系统推断覆盖。
checked_atINTEGER NULL 上次差分扫描（"检查变更"）的时刻。用途：判断界面上显示的状态 是否已经过期。超过阈值未扫描就在状态行上给一条提示—— 避免"库里显示的状态其实是三个月前的"这种静默错误。
刻意没有的东西。没有 state 枚举列，没有 vector_row 列 （items 已经有了，再来一份就是双份真相）， 没有 is_stale 布尔列（它是算出来的）。
为什么整表算"持久"（尽管大部分列可再生）。分类规则是 「一张表只要有任何一个不可再生的字段，整张表就是持久的」。 excluded_at 满足这个条件，所以整表保留。 重建时只做一件事：把文件已变过的行的 encoded_at 置空（它们确实需要重编码）。

② item_user_meta —— 评分 / 备注 / 使用状态

item_user_meta

新增 持久类 用户手写的标量字段。**刻意不加进 items**： items 的语义是"扫描出来的文件事实"，而这些是"人写的"。
字段类型约束说明
uidTEXT PKFK items.uid 1:1。没有这一行 = 这条素材还没被标注过（合法状态，不是缺失）。
ratingINTEGER NULLCHECK 1..5 评分。用 NULL 表示"未评分"，不用 0—— 0 会让你分不清"没评"和"评了零分"，而后者在语义上不存在。 范围写进 CHECK，坏数据进不了库。
noteTEXT NULL 自由备注（"客户要求再来两个变体"）。不设长度上限—— 截断是界面的事，不是存储的事。
use_stateTEXT NULLCHECK 三选一 'unused' | 'delivered' | 'archived'。 只有三个——每多一个状态就要多一套筛选与图标， 而"避免重复交付同一件"这个真实需求三个就够。用 CHECK 约束而不是无约束文本。
updated_atINTEGER NOT NULL 最后编辑时刻。用于"最近标注过"排序与冲突提示。

③ tag / item_tag —— 标签

tag

新增 持久类 抄 Immich 的 tag 表形态：标签是实体，不是逗号分隔的字符串。 去掉了它里面单用户用不到的和没 UI 的字段。
字段类型约束说明
tag_idTEXT PK nanoid。不用自增整数：将来若要跨库合并标签，自增 id 会撞。
nameTEXT NOT NULLUNIQUE 标签名。单用户 ⇒ 唯一约束只到 name，不需要 Immich 的 (userId, value) 复合唯一（那是多用户产品才需要的）。
created_atINTEGER NOT NULL 创建时刻。用于"最近用的标签"排序——那比字母序有用得多。

item_tag

新增 持久类 多对多关联表。
字段类型约束说明
uidTEXT FK items.uidPK(1/2) 条目。与 tag_id 组成复合主键， 天然防止同一标签重复贴在同一条上。
tag_idTEXT FK tag.tag_idPK(2/2) 标签。
added_atINTEGER NOT NULL 贴上时刻。
索引覆盖什么查询
PRIMARY KEY (uid, tag_id) 「这条素材有哪些标签」——列表页每行都要查，必须最快。
idx_item_tag_tag (tag_id) 反向查询需要单独建索引：「这个标签下有哪些素材」。 复合主键对反向查询**没用**——这是最常见的一个索引疏漏。

④ collection / collection_item —— 集合

collection

新增 持久类 交付与提案需要临时分组（F6 依赖它）。与"标签"的区别： 标签是多对多且扁平的描述，集合是有意的、有名字的、一次性的打包。
字段类型约束说明
collection_idTEXT PK nanoid。
nameTEXT NOT NULL 集合名（"2026-10 甲方A 提案"）。不加 UNIQUE—— 同名集合是合理的（去年的提案和今年的可以同名）。
noteTEXT NULL 集合级备注。
created_at / updated_atINTEGER NOT NULL 创建 / 最后修改时刻。

collection_item

新增 持久类 集合↔条目。刻意不做集合内排序—— 排序是"交付时按什么顺序给对方"的问题，先按 added_at 就够。
字段类型约束说明
collection_idTEXT FK collectionPK(1/2) 集合。
uidTEXT FK items.uidPK(2/2) 条目。
added_atINTEGER NOT NULL 加入时刻，也是默认排序键。
索引覆盖什么查询
PRIMARY KEY (collection_id, uid) 「这个集合里有哪些」+ 防重复加入。
idx_collection_item_uid (uid) 「这条素材被哪些集合收了」——详情页要显示它，反向索引必需。

状态派生公式（一个字都不存）

按下表顺序判定，第一条命中即为结果。顺序即优先级，不要改。

#档徽标判定条件
1图片丢失 图片丢失 items 里查不到这条 uid　或　磁盘上预览图已不存在
2已排除 已排除 excluded_at IS NOT NULL
3编码失败 编码失败 encoded_at IS NULL AND encode_error_at IS NOT NULL
4编码中 编码中 38% 索引任务的当前批次包含该 uid　（来自任务态，不读库）
5待编码 待编码 encoded_at IS NULL AND encode_error_at IS NULL
6待重编码（文件改过） 待重编码 encoded_at < items.image_mtime
7待重编码（模型换了） 待重编码 compat_key IS NOT current_compat
8已编码 已编码 其余情况
为什么"编码中"不读库。它是任务态，不是数据态—— 任务一结束这个状态就消失了。把它写进库，就会出现"库里说编码中、其实任务早挂了"的僵尸状态。 所以第 4 档由界面把「库里的数据」与「当前任务」合成得出，与现有 utils/index-state.ts 里"派生而非引擎字段"的纪律一致。
第 6、7 档需要一次差分扫描才能判准。没有扫描过时，界面显示的是 上次已知的状态。所以 checked_at 必须显示出来 （"状态基于 2026-10-15 09:12 的检查"），并提供"检查变更"这个动作。 不这样做的话，"库里显示已编码、其实文件早被换过"就是一次静默的错误答案。

持久性分类（重建元数据时保留谁）

规则一句话：一张表只要有任何一个不可再生的字段，整张表就是"持久"的。 这条规则要写进代码里**一处**，并由测试钉住，否则迟早漂移。

类别表重建时的行为
派生 items · documents · doc_chunks · library 删掉重建。全部可从扫描文件系统 / 重新抽取 / 注册表算出来。
持久 doc_dirs · health_runs · health_ledger
item_index_status · item_user_meta
tag · item_tag · collection · collection_item		 必须保留。重建流程要先读出来、重建派生表、再写回去。 doc_dirs 与 health_* 今天已经在丢—— 这次一并修掉。
已确认的现有缺陷（我查过代码，不是推测）。 library-rebuild.ts 第 ① 步是 removeGsDbFiles(dbPath) —— 删整个文件； 之后只从 items.json 导回 items 与 library。而 import.ts 里 doc_dirs / health_runs / health_ledger 一次都没出现。 ⇒ 现在点一次"重建元数据"，你注册过的文档目录和体检历史就没了。 今天没暴露，只因为文档检索是门控项、还没有任何 doc_dirs 行。

刻意不做的（对照 Immich）

Immich 有，我不抄为什么
tag_closure 闭包表
（层级标签）		 你现在 0 个标签。层级是"标签多到需要分组"才需要的功能—— 提前建闭包表意味着每次增删标签都要维护一张额外的表，而收益为零。

asset 拆成 asset-exif / asset-file / … Immich 拆是因为它有 EXIF、多文件（原图+缩略图+转码）、多模态。 我们的 items 只有图+包两种文件， 为拆而拆只会让每次查询多一次 JOIN。
smart-search 表（保存的搜索） 不在本轮范围。等"重复找同一批东西"变成真痛点再说。

迁移计划

3 新增迁移 user-metadata（现有已到 2） 创建上面 6 张新表与其索引。纯新增，不改任何现有表—— 迁移只做加法，回滚就是 DROP 这 6 张表。
4 修 libraryRebuild：从"删文件"改为"只重建派生表" ① 读出持久表 → ② 删文件重建 → ③ 从 items.json 导入派生 → ④ 写回持久表。 并在确认框里对真损坏的情况如实说明"持久数据救不回来"。 这一步必须先于新表上线，否则第一次重建就把新数据抹了。
5 把"派生 / 持久"分类写成一处常量 + 一条单测 单测断言：迁移里建的表，必须每一张都出现在"派生"或"持久"列表里。 新增表却忘了分类 ⇒ 测试变红。这是防漂移的唯一机械手段。
6 用户元数据导出 / 导入 把 6 张新表导成一份 JSON（或 CSV）。用途：重建前的兜底、 换机器、以及"我手滑删了标注"的后悔药。
