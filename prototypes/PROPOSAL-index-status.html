这是**方案**，不是已改好的界面。你看完给指令，我再动原型与代码。

① 索引状态模型：8 档

现有代码（utils/index-state.ts）已经定义了 4 档，且明确要求： 状态必须【派生】而不是引擎字段，且【不自动扫描】。我在这 4 档上扩展，不推翻： 「已编码 / 待编码 / 待重编码 / 已从索引移除」全部保留，只补 4 档。

档位徽标 什么情况下出现用户此刻最该知道的一句话 能否检索能否一键修
已编码
encoded		 已编码 向量已在索引里，且 compat 与当前模型一致 可以参与语义检索。（什么都别说，这不是要你操心的状态） 是—
待编码
pending		 待编码 已发现这条素材，但还没编码 它现在搜不到。入库任务会处理它。 否排队即可
编码中
encoding		 编码中 38% 该条目正在被索引任务处理 正在处理，等它一下。显示进度而不是转圈。 否（稍后）—
待重编码
stale		 待重编码 文件被外部改过（size/mtime 变了）
需要一次差分扫描才知道		 当前向量与文件内容已不对应，搜索结果可能指错东西。 能，但结果可能错是
编码失败
failed		 编码失败 尝试编码时报错（文件损坏 / 不是图片 / 显存不足…） 它永远搜不到，重试也不会自己好。要看失败原因。 否重试
图片丢失
imageMissing		 图片丢失 索引里有，但磁盘上的预览图不见了 取件和定位都会失败。压缩包可能还在。 否重新扫描
已从索引移除
removed		 已移除 索引里有、盘上整个条目都没了 这是一条残留记录，清掉即可。 否清理
已排除
excluded		 已排除 你手动标记"不索引这条" 是你自己的选择。体检和告警都不该再吵它。 否（你有意为之）恢复索引
为什么不直接照搬现在的 4 档？ 因为现在这 4 档里 "待编码"和"待重编码"共用同一个语气体，而它们的处置完全不同（一个排队、一个要重扫）； 更关键的是没有"编码失败"——一条永远搜不到的东西，界面若不说话，你会以为软件坏了。
尊重现有约束。 这套模型仍然【派生】：failed 与 excluded 不能凭空编，需要索引任务把"上次失败原因"与"排除名单"记进 .gs.db（可重建的派生数据）。若这两项暂时拿不到， 界面上就显示"未知"而不是猜一个——这正是现有代码注释里强调的那条纪律。

详情页的排序逻辑：能用的前提 → 我对它的加工 → 它是什么 → 危险动作。 索引状态放最上不是因为重要，而是因为它决定下面所有动作能不能成立： 一条"图片丢失"的素材，"取件"必然失败——那就不该等点下去才告诉他。 这也是现有 item-actions.ts 已经在做的事（动作分组 + 为什么点不动）， 我只是把它在视觉层级上落实。

#决策点我的建议若你不同意
1状态档数：4 → 8 保留现有 4 档、新增「编码中 / 编码失败 / 图片丢失 / 已排除」。把"图片丢失"从"已移除"里拆出来——压缩包还在和整条都没了是两件事 维持 4 档，代价是"编码失败"无法显示
2失败原因与排除名单存哪 存 .gs.db（派生数据，可重建）。拿不到就显示"未知"，不猜 不存 ⇒ 这两档只能显示"未知"，等于少两档
3列表默认列哪些 名称 / 大小 / 索引状态 / 修改时间 / 分类 / 分辨率。索引状态放在大小之后 列太多会挤；可做成"列设置"让用户自己开
4"已编码"要不要显示 要，但用弱化的绿。让"一片绿"本身成为可读信号 只显示异常档 ⇒ 你永远不知道还有没有没索引的
5详情页要不要支持编辑元数据 要。标签 / 评分 / 备注 / 集合是资产管理的核心——只读的资产管理不算管理 先只读展示，编辑放第二版
6新增字段存哪 标签/评分/备注存 .gs.db。绝不能写进素材目录（写入不变式） 无替代方案——这条是硬约束
这份提案会改到需求，不只是界面。 新增 4 个状态档、新增可编辑元数据字段， 都要写进 SPEC.md 的 §3（F1/F2）与 §5（契约）。 按项目纪律「改规格 = 改需求」，需要你明确同意。
