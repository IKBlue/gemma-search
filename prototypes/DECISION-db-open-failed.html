裁定：DB_OPEN_FAILED 收进引擎码空间（27 → 28）？

一句话：现在库坏了、检索却说「索引文件已损坏」 —— 用户按提示去重建索引，白折腾。这不是新概念，而是把已经存在的一个码升进引擎码空间。

待你裁定 2026-10-15 · 记录在 TASKS §4 · U22 · 依据 T-45 实测（reports/2026-10-15-wave3/45.txt）

1 · 现象：同一个坏库，两条路给出两个名字

路径 A · 检索 / 详情（引擎端口）

库的 .gs.db 打不开时，用户看到：
码 INDEX_CORRUPT
文案「索引文件已损坏，需要重建。」
⇒ 但索引是好的（.gs-index.bin 通过五道校验）。

路径 B · 体检

同一个坏库，用户看到：
码 DB_OPEN_FAILED
可重建 true
⇒ 名词对、处置对。

两条路对同一件事给了两个名字 —— 一个说「索引坏了」，一个说「库打不开」。用户无法判断该信谁，支持也无从下手。

2 · 为什么这算问题（三条）

问题后果
按提示操作解决不了文案让用户去「重建索引」，而坏的是库 ⇒ 重建索引后问题照旧，用户会认为「这软件修不好」。
同一件事两个名字检索说索引坏、体检说库坏 ⇒ 用户与支持无法用同一个词沟通。
这正是已经修过的那类假因果2026-10-15 T-45 刚把 IMPORT_* 一族从「被归成 INDEX_CORRUPT」里拆出来（当时也是：导入失败被说成索引损坏）。DB_OPEN_FAILED 是同一类里剩下的一例。

3 · 关键事实：这个码已经存在，只是没进引擎

事实证据（文件:行）
它已经是 main 侧的正式错误码main/db/errors.ts:18
它由打开库的适配层产出（裸 SqliteError 统一收成它）main/db/open.ts:147-149
体检路径已经在报它，且有测试断言tests/health-rebuild.test.mjs:226 / 436（H5「.gs.db 损坏 ⇒ DB_OPEN_FAILED，可重建」）
只有「经引擎端口」这条路把它改名了main/storage-ports.ts:68 case 'DB_OPEN_FAILED': → INDEX_CORRUPT（注释明写「已知边界，未擅自扩码空间」）
引擎码空间当前 27 个，SPEC 与代码一致SPEC §5「错误码（27 个：新增=兼容，改名=破坏性）」 · packages/engine/src/errors.ts

⇒ 所以这不是「发明新概念」，而是 把一个已经在用、已经在界面出现的码，升进引擎码空间 —— 属于收敛，不是扩张。

4 · 两个选项

选项改什么成本 / 风险后果
A · 加
27 → 28		 引擎 errors.ts 加 DB_OPEN_FAILED + 一句文案；删掉 storage-ports.ts:68 那条改名映射；SPEC §5 码数 27 → 28，并写「DB 类不得归成 INDEX_CORRUPT」；补一条能红断言。 小：1 个码 + 1 句文案 + 删 1 条 case + SPEC 一行。
无新表、无迁移、无契约方法变化、无格式变化。		 两条路同名同因；用户按提示走对路（重建元数据）。
B · 不加
保持 27		 什么都不改；把这条如实留成 TASKS · U22 的已知残差。 零成本，但保留一处假因果。 库坏时用户仍看到「索引文件已损坏」⇒ 按提示操作无效。

5 · 若选 A：完整改动预览（before → after）

① 引擎码空间

新增一码 与其余 27 个同形：一个常量 + 一句用户文案（文案只允许一份）。
文件改动
packages/engine/src/errors.tsERR 增 DB_OPEN_FAILED: 'DB_OPEN_FAILED'；USER_MESSAGE 增一句（候选：「这个库的元数据打不开（文件可能损坏或被占用）。索引文件没坏 —— 先试「重建元数据」，不行再看诊断。」）
SPEC.md §5.2「错误码（27 个…）」→「（28 个…）」；在 IMPORT_* 那条「不得归成 INDEX_CORRUPT」旁补一句：DB 类同理。
main/storage-ports.ts:68删掉 case 'DB_OPEN_FAILED': → INDEX_CORRUPT（引擎契约码原样透出 ⇒ 这行变多余）；同时删掉 :57 那句「已知边界」注释（它描述的正是被修掉的行为）。
新断言（能红）破一个 .gs.db ⇒ 经引擎端口读 ⇒ 必须得到 DB_OPEN_FAILED，不得是 INDEX_CORRUPT；把映射改回去 ⇒ 必须红。
明确不动为什么
不加表、不加迁移错误码不是数据表；29 张里没有它的事。
不改 IPC 契约码走的是既有信封的 error.code 字段，方法集合不变。
不改 .gs.db 格式只改「怎么说」，不改「怎么存」。
不加新按钮 / 新页面“重建元数据”这条自救路已经存在（libraryRebuild，U21 已裁定保留）。

6 · 验收（怎么算改对了）

  1. 两条路同名：同一个坏库，经引擎端口与经体检都必须得到 DB_OPEN_FAILED（现在一个 INDEX_CORRUPT、一个 DB_OPEN_FAILED）；
  2. 能红：把改名映射加回去 ⇒ 断言必须红；还原后复绿（原始输出进证据）；
  3. 码数可断言：SPEC §5 的「28」== 引擎 ERR 的键数（机械核，不靠人肉数）；
  4. 引擎单测全绿 · tsc 两工程 0 · 既有 27 码行为不变（新增=兼容）。

7 · 我的建议

选 A（加）

理由：① 它已经存在、已经在界面出现 ⇒ 加它是收敛；② 假因果是本项目明令要杀掉的失败模式（T-45 刚为同类问题杀过一次）；③ 成本是一个码 + 一句文案 + 删一行 case。

若选 B（不加）

我会把它如实留在 TASKS · U22，并在 storage-ports.ts:57 保留「已知边界」注释 —— 不假装它不存在。但用户那条错误路径会继续指错方向。

8 · 这份页面证明不了什么

  • 它不修「库打不开」本身（文件损坏、被占用、磁盘满）—— 只把名词与因果改对，让提示指向正确的自救动作；
  • 它不处理「库被别的进程占用」这种情形（那需要句柄/重试策略，是另一件事）；
  • 码数 27 → 28 会让 SPEC 与代码的既有机械核对变一次；除此之外不改任何行为阈值。
