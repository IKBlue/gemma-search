01项目框架审查 —— 架构师 & 开发者视角

1.1 技术栈选型评估

层选定评估
外壳Electron 44合理。本地桌面、离线、要跑 ONNX，Electron 是最稳妥的选择；「不换 Tauri」的判断成立，因为已有原生模块与打包经验沉淀。
运行时Node 24 + node:sqlite有风险 node:sqlite 仍是实验性 API，好在被薄适配层隔离（全仓仅 1 处 import），这是教科书式的风险隔离。
界面React 19 + TS strict + Tailwind 4 + shadcn/ui主流且正确。严格 TS + 类型门禁「必须能红」是亮点。
状态Zustand轻量合适；「只放状态与编排、不持久化」的边界清晰。
契约zod（单一来源 shared/ipc.ts）本项目最值得称道的决策之一：一份 schema 同时产出运行时校验 + 方法白名单 + 编译期类型，杜绝了「白名单是口号」。
引擎零第三方依赖、传输无关极强。引擎可脱离 Electron 用 node:test 直接测，这是「引擎即纯函数」的正确形态。

1.2 四层架构的执行落地

架构分层不是纸上谈兵，而是有机械断言钉住

UI → Operation → Adapter → Data

仓库里有 layering.test.mjs、dom-validity.test.mjs、style-contract.test.mjs 等守卫，注入违例能让测试变红（如 UI 层碰 window.api、渲染出嵌套交互元素、写死色值）。「唯一 Adapter 入口」「UI 零 window.api」「文案兜底只一份」都不是口号，是可执行的断言。这是我见过的对「架构漂移」最到位的对抗手段之一。

1.3 安全姿态

  • preload 只暴露 3 个成员；sandbox:true + contextIsolation:true。
  • IPC 只开 2 条通道；未登记方法一律拒绝；渲染进程传不进绝对路径（唯一例外 queryImagePath 有扩展名白名单）。
  • thumb:// 自定义协议只接受 libId + uid@size，路径由「注册表 + 索引」反查再校验包含；失败状态码映射 400/403/404/415/503/500 语义清晰。
  • 取件白名单（collect_dir 表）构成结构性安全边界——渲染进程连「传一个白名单外的路径」都做不到。
框架层面唯一的「反主流」决策需要警惕

「单一外部里程碑 M1，期间不发布可用版本」是偏瀑布的姿态。PLAN 里明确写「对外只有一个 M1」「期间不发布」。对一个桌面工具类产品，这会让「最贵的部分最后才被验证」——好在 M0 薄切片（找→取端到端）已经部分对冲了这个风险，但它被显式标注为「不是发布」。工程上没问题，产品节奏上是隐患。

把 TASKS.md 的任务状态与代码实际行为逐条对账，得到下表。关键结论：任务书的 ☑ 勾选严重滞后于代码现实——大量已完成项（Tailwind/shadcn 接入、IPC 契约重列、体检/重建）在 TASKS.md 里仍无勾，而真正未完成的是「建索引」「事务」「交付」这些写路径。

完整度的核心矛盾：工程投入与可交付能力脱节

仓库里有 51 个单测文件、16 个 E2E 规格、约 16,500 行 TS、几十份归档证据——但一个真实用户装上去，能用的只有「对已建好索引的库做检索 + 取件」。建索引（产品的立足之本）是桩，浏览页永远报错，设置页不存在。这是「工程完善度」与「产品完整度」严重错配的典型样本。

值得警惕的工作顺序：界面先于数据层

BrowsePage 是「把整个 UI（网格、虚拟滚动、筛选、空态三分类）写完，但数据读路径 items 还没实现，页面诚实地报错」。这种「先做界面骨架、后补契约」的顺序，对于一个把「契约是唯一来源」奉为圭臬的团队，恰好反证了契约设计没有先覆盖全屏面的数据流——items（U24）是在派工前才被 Lead 发现「F2 没有读路径」的。这说明上游设计阶段缺了一次「每个页面需要哪些方法」的端到端遍历。

03界面设计审查 —— 产品经理 & 设计师视角

3.1 设计系统：严谨，是加分项

  • 视觉令牌单一来源（tokens.css），组件不写死色值，派生色用 color-mix()，这是正确做法。
  • 对比度被逐值计算：正文 ≥4.5:1、非文字图形 ≥3:1，且把「填充色 vs 正文色」拆成两个令牌（--color-success vs --color-success-text）——很多产品团队根本意识不到这个坑。
  • 深浅色双块、reduced-motion / reduced-transparency 尊重、焦点环、44px 命中区，HIG 基线落地扎实。
  • 危险操作两段式确认 + alertdialog 焦点陷阱，无障碍语义正确。

3.2 实际渲染质感：功能性偏「原型」，离「精致」有距离

图标体系是最大的视觉短板

按钮里大量使用 Unicode 字符充当图标：↻（刷新）、?（帮助）、◫（以图搜图）、←（返回）、✓/✕（体检项）。依赖里明明有 lucide-react@1.56.0，但界面里几乎没看到它被用起来。Unicode 图标在不同平台/字号下字形不一致、无法着色、语义模糊，是「能用但显粗糙」的直接来源。一个以「Apple HIG」为视觉基线的产品，按钮里出现 ◫ 这种符号，观感落差明显。

  • 语言混用：eyebrow 是英文（LOCAL · PRIVATE · SEMANTIC、LOCAL IMAGE INTELLIGENCE、BROWSE、DIAGNOSTICS），正文是中文。对一个面向中文用户（素材库、渲染器分类、取件）的产品，这种「英文当装饰、中文当正文」的混搭显得不统一。品牌副标题「LOCAL IMAGE INTELLIGENCE」更偏向开发者自我表达，而非用户价值。
  • 死按钮暴露在首页：搜索页标题区有「＋ 添加图库」「↻ 更新索引」两个按钮，点了只弹 toast「还没实现」；帮助按钮弹「帮助中心将在正式版本中提供」。一个产品首页长期挂着若干点了无反应的入口，是完整度与诚意的双重扣分。
  • 信息密度偏低：结果卡只有缩略图 + 文件名 + 分类 tag + 分数；没有尺寸、有无包、时间等关键元信息的即时呈现（这些在详情页才有）。检索场景下用户通常需要「一眼看出哪个是带包的、哪个多大」。

3.3 空态与错误态设计：值得表扬

浏览页把空态拆成「库是空的 / 筛没了 / 读不出来」三种，并各自给出不同指引；诊断页把「重建修得好 / 重建修不好」区分开；任务页宁可用「该功能等数据表上线」的诚实占位也不用灰色假按钮。这套「不把 0 当没事、不把没做当做了」的哲学，在 B 端工具里是稀缺品质。

04交互方式审查 —— UX 视角

4.1 做对的部分

  • 破坏性操作两段式 + 取消零 IPC：取件、重建元数据都走「请求→确认」，取消路径有 store 级断言「一个 IPC 都不发」，连点只发一次。这是写路径交互的正确范式。
  • 结果卡标题是链接而非整卡包链接：避免了「链接套按钮」的嵌套交互元素（HTML 规范禁止、读屏会乱）。细节到位。
  • 详情页四分区动作 + 「需重编码/不重编码」角标：把领域判断直接标在按钮上，降低误操作。
  • 诚实文案：定位按钮只说「已请求在资源管理器中定位（系统未回报结果）」，不假装成功——这种对系统边界的诚实很难得。

4.2 缺失的关键交互（对桌面产品是硬伤）

能力优先级（任务书）现状影响
命令面板（Ctrl/Cmd+K）P0缺失（cmdk 已装未用）跳页/切库/跑体检全靠鼠标，桌面应用失去最大效率杠杆。
快捷键全流程P0缺失方向键移动、Enter 定位、Space 预览、Esc 清空均未见接线。
批量多选 + 批量动作P0缺失取件/交付只能单条，3594 条的库无法批量操作。
拖拽导入 / 粘图搜P0缺失最高频入口，SPEC 里自己都承认「比找菜单快十倍」。
设置中心P0缺失模型路径、主题、快捷键、日志导出全无可配置入口。
交互完备度与「P0 必须要有」的自我定位严重不符

SPEC §9 自己把命令面板、快捷键、拖拽、批量、设置中心都标为 P0（第一版必须有），但实际一个都没做。也就是说：团队对「第一版长什么样」有一份自己都没兑现的清单。这既说明规划是诚实的（知道什么重要），也说明执行距离那份规划还很远。

05数据表设计审查 —— 数据库设计师视角

5.1 设计本身：成熟、克制、有层次

「两个数据库 · 6 张表 · 四层持久性」是一个相当成熟的设计：

库级 .gs.db
asset（条目）· asset_file（文件角色，缺包=少一行而非 NULL 块）· asset_index_state（索引进度，存时刻不存枚举）
应用级 app.db
app_meta（兼迁移账本，单行守卫 id=1）· library_registry（库注册表）· collect_dir（取件白名单=安全边界）
  • 四层持久性（事实/过程/意图/应用）直接回答了「重建时什么可丢、什么必须留」——这是很多团队在建表时根本不会思考的问题。
  • 唯一写入口：每张表都锁死「谁能写」（asset/asset_file 只有扫描器写，asset_index_state 只有索引任务写），并有静态测试抓「调用方自己写 SQL」。
  • 克制：刻意不加 deleted_at_ms、thumb_hash、needs_reencode 等「迟早要用」的列，加列=一条迁移。拒绝过度设计。
  • 正确面对约束：明确承认「跨库外键不存在」（SQLite 无此能力），asset.lib_id 是普通 TEXT 不做 REFERENCES；Windows 路径规范化（大小写/8.3 短名）在写入方处理而非靠 UNIQUE 文本比较。
  • 从 DDL 派生清单：应有表清单由 DDL 反推，双向断言「迁移建出的每张表都必须在四层里被点名」——加表漏分类会被测试逼出来。

5.2 需要关注的取舍

「6 张表」是范围收窄，不是最终形态

第二批还有 14 张表未建（job、health_run、collection、tag、activity、doc_chunk 等）。这意味着当前 6 表只能支撑「检索 + 取件 + 体检」这一薄层；任务、交付、收藏、文档检索全部在等第二批。数据建模是分层的、有远见的，但当前落地的表覆盖不了产品的核心写路径——「job」表的缺席正是「建索引是桩」的数据层根因。

  • vector_row 的补充：asset_index_state 里 vector_row 是「绿地修正」补上的——因为它对应稠密矩阵的行号。这说明最初设计时对「索引行 ↔ 条目」的映射关系有过一次遗漏，好在被下游前置核查抓出。好事，但也是一次「设计基线不够完整」的信号。
  • FTS5 未建：文件名全文检索（asset_name_fts）在第二批，当前纯按文件名 LIKE 或向量检索，缺少「按文件名模糊找」这条最朴素也最常用的路径。

06与当前主流做法对比

6.1 方向正确性：踩在趋势上

主题主流实践本项目判断
本地优先 / 离线 AI2025-2026 年「on-device embedding + 本地向量检索」是明确趋势（如 AnythingLLM、private-gpt、桌面 RAG 工具）。全离线、不上传、单进程内检索。✅ 方向正确，且「只定位、不生成」的克制（不做 LLM 幻觉）是加分。
嵌入模型主流是 sentence-transformers / ONNX 量化模型，普遍选 int8/q4 以控制体积与内存。EmbeddingGemma-2 ONNX fp32（GB 级，2.28 GiB 内存峰值）。⚠️ fp32 未量化是明显偏离：768 维、单一素材库（<10 万块）场景，int8/q4 通常能换回数倍体积与内存收益，精度损失可测可控。2.28 GiB 峰值对 8GB 机器是重负担。
检索加速<10 万向量时主流用 NumPy/纯 JS 暴力点积即可，本项目判断正确（不引 sqlite-vec/hnswlib）。纯 Float32Array 点积，文本 P50 52ms。✅ 合理。规模没到，ANN 是过度设计。
数据层桌面应用普遍 better-sqlite3；Node 内置 node:sqlite 是新兴选项。node:sqlite + 薄适配层。✅/⚠️ 用内置省去原生编译地狱，但实验 API 是分发的隐性风险；适配层隔离做得好。
UI 组件shadcn/ui + Radix + Tailwind 是 React 侧当前事实标准。同款（含统一 radix-ui 包）。✅ 与主流一致。
测试策略桌面应用普遍轻测试；本项目是「机械断言 + 证据归档」的重工程。51 单测 + 16 E2E + 每结论必附证据。✅ 质量文化远超主流，但需注意「证据仪式」本身成为时间黑洞（见风险 R7）。

6.2 与主流「桌面生产力工具」的用户预期差距

主流桌面工具（如本地图库管理器、RAG 客户端）的第一版通常会优先交付：可用的浏览 + 可用的建索引 + 可用的批量操作 + 一个设置页，再谈检索质量。本项目反其道而行——把「检索质量、安全边界、工程纪律」做到极致，却把「浏览、建索引、设置」留在后面。从用户价值排序看，这是本末倒置的：用户装上去的第一件事是「导入库并建索引」，而这恰好是桩。

07风险清单（按严重度排序）

高
R1 · 产品核心价值依赖用户自备 GB 级模型 + GPU。干净机器装上后：无模型 → 只能看指引不能检索；无独显 → 图像检索 P50 1.48s（文本的 28 倍）。而「一键下载模型」是 P8 的「推荐项」，尚未实现。这意味着产品的差异化能力（语义/以图搜图）在目标用户中最常见的「普通笔记本」上体验堪忧。
R2 · 建索引是桩，产品无法冷启动。indexStart/Cancel/Resume 契约已删、job 表未建。一个全新用户连索引都建不起来，而「建索引」是产品立足之本。这比「缺模型」更根本——缺模型是自备问题，建索引是产品能力缺失。
R3 · 检索质量结论无凭据 + 分数阈值是暂定值。旧的质量证据（v2 PASS）已随旧文档体系清除，新的基线只有「编码路径一致性」（top10 逐位一致），没有「检索结果是否真的好」的标注质量评估。BANDS 阈值（text 0.72/0.65、image 0.90/0.80）被注释明说是「暂定」。核心价值「找得到」的质量承诺当前无实质证据。
M4 · 内存峰值 2.28 GiB。fp32 模型 + 3594×768 向量驻留主进程，8GB 机器上接近上限。未量化是主因。
M5 · node:sqlite 实验性 API。适配层隔离到位，但分发到旧 Windows/异常环境时行为未知，需真机矩阵验证（SPEC 自己标注「主进程内仍需复验」）。
M6 · 单一里程碑 + 串行推进。PLAN 规定串行（共享写入面），一个对外里程碑。进度风险高，且「多库合并、文档检索」被门控后可能永远排不上。
L7 · 工程仪式的时间成本。四份互锁文档 + 每结论必归档 + 机械断言 + 双向「能红」验证，是极强的质量文化，但也会让「改一行文案」级别的任务背负不成比例的开销。团队已在 TASKS 纪律里记了 15 条「踩坑复盘」，侧面说明协调成本不低。

08改进建议（优先级排序）

P0 —— 先让产品「能用」，再谈「好用」

#建议理由
1补上建索引（job 表 + indexStart/Cancel/Resume + 进度事件接线）。没有它，产品无法冷启动，其余一切白搭。这是完整度的第一缺口。
2落地 items 读路径，让浏览页真正工作（S8 已排期，建议提前并作为硬验收）。当前浏览页是「写完 UI 但永远报错」的半成品，比没有更尴尬。
3补设置中心（至少：模型路径、主题、取件目录、日志导出）。SPEC 自标 P0，且「所有可配置值唯一入口」是团队自己的规范。
4用 lucide-react 替换全部 Unicode 图标。视觉质感最大、成本最低的单点提升。
5清理首页死按钮：把「添加图库 / 更新索引」做成真功能，或至少在未实现时给禁用态 + 原因，而非可点后弹 toast。团队自己规范里就写「未实现功能显式占位，不许点了只弹 toast」（N17），首页两个按钮正好违反。

P1 —— 让产品「好用」

#建议理由
6命令面板（Ctrl/Cmd+K）+ 核心快捷键（方向键/Enter/Space/Esc）。cmdk 已装，接线成本低，桌面应用效率杠杆最大。
7批量多选 + 批量取件/交付。单条操作在 3594 条库上不可用。
8结果卡增加关键元信息（有无包/尺寸/时间）。检索场景的决策信息密度。
9文案语言统一（eyebrow 中文或全英文，二选一）；品牌副标题改为用户价值表述。消除「英文当装饰」的割裂感。
10评估 int8/q4 量化，压内存峰值、缩模型体积。2.28 GiB 峰值对 8GB 机器是真实负担；量化收益需与精度损失一起实测。

P2 —— 产品健康度

  • 建立检索质量标注基准（真查询集 + 人工相关性判断），把 BANDS 阈值从「暂定」变「有据」。
  • 真机矩阵验证：node:sqlite 在主进程、无独显回退、干净机器首启、NSIS 安装器。
  • 对「工程仪式」做一次成本收益复盘，看哪些断言/证据流程可以合并降噪，避免流程吃掉产出。
给所有者的最终建议：这个项目的底子是一流的——架构、契约、数据建模、安全、质量文化，任何一项拎出来都值得行业参考。但当前它更像一个「被精心打磨的地基」，而非「能交付的产品」。下一步资源投入的优先级应当是：建索引 → 浏览读路径 → 设置中心 → 图标与文案 → 快捷键/批量，把「找→取」这唯一能用的闭环扩成「导入→建索引→浏览→检索→取件→交付」的最小可用产品，再回来谈多库合并与文档检索这些门控功能。工程已经赢了，现在缺的是把工程兑现成产品的那一段。
