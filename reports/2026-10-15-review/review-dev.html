◎结论先行

这是我看过的同规模项目中工程自律性最强的之一：信封式错误、单一契约来源、机械断言、原子写入、write-ahead 事务日志，每一项都做到了行业上游。但自律不等于没有债——最典型的问题恰恰是「纪律体系内部的漏洞」：死代码没清、ID 用了 Math.random、有一处静默类型降级、指纹函数漏了保留命名空间。下面按严重度给出可复现、可定位的证据。

01漏洞与缺陷 —— 按严重度排序

高 · 数据正确性 指纹函数未跳过保留命名空间，与扫描器口径不一致

packages/engine/src/fingerprint.ts 的 fingerprintLines() 遍历库根时没有 isReservedLibraryName() 跳过，会把 .gs-index.bin、.gs.db、.gs.db-wal/-shm 全部算进 files 计数与指纹。

证据：fingerprint.ts walk() 循环里只有 if (!e.isFile()) continue，随后直接 lines.push(...)、counts.files++——无任何保留名判断。

而同一仓库里另一处「素材摘要」main/library-rebuild.ts 的 materialDigest() 有 isReservedLibraryName 跳过。两者是「同一概念的两种实现」（违反其自身 P1），且结果不一致：

  • engine.ts 的 doScan() 用 fingerprintV1(root) 返回 fingerprint 与 filesTotal——它会把索引/WAL 变化算成「库被改过」，索引一重建，库指纹就变，与扫描本身的 diff（那里有跳过）自相矛盾。
  • 这正是 U11 刚修过的「把 .gs.db 当素材」问题的复发形态：修在了 scanner / materialDigest，漏了 fingerprint。
建议：在 fingerprintLines 的 walk 里补 isReservedLibraryName(e.name) 跳过（与 scanner / materialDigest 同一判据），并加一条「指纹文件数 == 扫描器素材文件数」的机械断言。
高 · 数据正确性 num()/text() 静默把 bigint 降级成 0

apps/desktop/src/main/app-db.ts 里 const num = (v) => (typeof v === 'number' ? v : 0)。而同一层的 db/sqlite-adapter.ts 明确允许 bigint 作为 SqlValue 透出（注释还写了 changes/lastInsertRowid「可能是 bigint」）。

一旦 node:sqlite 升级、或某处打开 readBigInts，enabled/sort_order/schema_version 会静默变成 0——库被悄悄「停用」、迁移版本被读成 0，而没有任何报错。这与适配层自己写的「narrowValue 判不出来就抛、绝不静默返回 null」直接冲突：适配层防静默，行映射器却在静默。

建议：行映射器改用与适配层同源的值收窄（bigint → Number() 且校验 Number.isSafeInteger），或把 num() 改成「非 number/bigint 即抛」，与 narrowValue 口径统一。
中 · 安全 Math.random 生成 jobId，违反自身「用 nanoid」纪律

packages/engine/src/engine.ts:613：const jobId = 'j-' + Math.random().toString(16).slice(2, 6)。仅 4 位 hex = 65536 种可能，且非加密随机。

取件（doCollect）是并发可重复触发的路径，jobId 一旦碰撞会把两次取件记成同一个 job；AGENTS 明写「ID 新增处一律用 nanoid，不自己拼随机」，这里却用了最弱的拼接。

建议：crypto.randomUUID() 或 nanoid；引擎已依赖 node:crypto（uid.ts / index.ts 都在用），成本为零。
中 · 健壮性 缩略图缓存写入非原子，截断文件会被永久缓存

apps/desktop/src/main/thumb-cache.ts 的 writeCachedThumb() 用 fs.writeFileSync(cachePath, bytes) 直接落目标名。进程中途被杀会留下非零但截断的 JPEG。

readCachedThumb() 只判了「0 字节算未命中」，但截断的非零文件会被当作命中永久返回给界面（缓存从不校验、从不失效），结果是一张永远坏掉的图。对比同仓库 index-file.ts 的索引写入是「临时名 → fsync → 校验 → rename」，这里却退化成了裸写。

建议：复用「临时名 + rename」的原子写入模式（索引侧已有现成范式），或至少写入前先判 JPEG 尾部 EOI 标记（FF D9）再决定是否重算。
中 · 健壮性 未捕获异常/拒绝只记日志不退出

apps/desktop/src/main/index.ts 末尾：process.on('uncaughtException', (e) => log(...)) 与 unhandledRejection 同样只记日志。uncaughtException 之后进程可能处于半初始化/半写状态，继续运行会让「引擎没装配完、库打开一半」这类状态被当成正常。

对本项目「最怕静默」的哲学而言，这与它自己的纪律矛盾：一个兜不住的异常应当响亮地退出（或至少标记全局「不健康」），而不是只写一行日志让应用继续。

建议：uncaughtException 记日志后 app.exit(1)；unhandledRejection 按错误来源决定「退出 or 标记不健康」。至少要把「出过未捕获异常」暴露到诊断面板。
低 · 安全 生产态保留 DevTools + F12 快捷键

main/index.ts 建窗时 devTools: true，且 before-input-event 里写死 F12 切 DevTools。注释说「本机自用工具」，但这是一个要「分发给别人」的产品（SPEC 定位）。保留 DevTools 等于给任意拿到安装包的人一个调试后门，且与「渲染进程无 Node、preload 只暴露三键」的安全姿态不匹配。

建议：至少做成配置开关，默认关闭；或保留 DevTools 但去掉 F12 快捷键，改由显式环境变量开启。
低 · 健壮性 路径解析的 TOCTOU 与「祖先 realpath 失败静默放行」

packages/engine/src/library.ts 的 resolveInLibrary()：目标不存在时，找最深已存在祖先做 realpath 校验；但 catch { return target } ——realpath 失败时直接放行未经校验的路径。虽然调用方多是「先 existsSync 再 realpath」，但这条 catch 分支把「校验失败」静默等价成了「校验通过」。

建议：realpath 失败应 fail(PATH_ESCAPES_LIB)（或至少明确区分「拿不到结论」），不要 return target。

02技术债务 —— 会影响后续开发速度与正确性的负债

债务 row-types.ts 残留引用已删除表的死 SQL

apps/desktop/src/main/db/row-types.ts 仍保留 ITEM_INSERT_SQL、ITEM_UPSERT_SQL、ITEM_FIELD_COLUMNS（18 字段宽表 items）、sqlRowToItemRecord()——而绿地 schema 已经把 items/library 表删了。这些 SQL 生成器现在指向不存在的表，是 S2 重写后没清干净的遗留。

parseItemRecord()（源 items.json 的 18 字段解析）仍被 import.ts 使用，所以文件不能整体删——但 ITEM_INSERT_SQL/ITEM_UPSERT_SQL/sqlRowToItemRecord 三段是纯死代码。

建议：删除死 SQL 与 sqlRowToItemRecord，只保留源格式解析（parseItemRecord）与新的 joinedRowToItemRecord。
债务 引擎保留 6 个「收益为零」的诚实桩

packages/engine/src/engine.ts 的 UNIMPLEMENTED_METHODS（ingest/mutate/transactions/indexStart/indexCancel/indexResume）在 IPC 契约里已删除，但引擎侧仍生成这些方法、fake.ts 仍为其提供假实现。注释承认「删它们收益为零」，但这意味着：

  • 一个「不会被调用的 API 面」长期存在，新人会误以为它可用；
  • 每次改 engine.ts 的 api 对象都要绕着这 6 个生成方法走。
建议：要么真正删掉（连带 fake.ts 的对应键），要么在类型层把「已下线方法」与「可用方法」分开表达，别让不可达 API 与真实 API 同处一个对象。
债务 索引布局「旧/新」双轨并存

resolveIndexLocation()（index-layout.ts）与 storage-ports.ts 仍然要同时认「旧布局 <dataDir>/libraries/<id>/index.bin」和「新布局 <库根>/.gs-index.bin」，每一次索引读取都走 fallback 决策。这是迁移期的必要成本，但它是有明确寿命的债——迁移完成后旧布局应退役，否则「读索引」永远有两套路径要同时维护、同时测。

建议：给旧布局设一个退役时间点/版本门槛（例如库注册表已完全迁移后，旧布局只读不再写），并在 SPEC 记明。
债务 CSS 双轨：手写 renderer.css（114 条）与 Tailwind 并存

renderer.css 头注释自认「两层并存是过渡态，迁移进度约 9.5%」。手写层刻意排在 Tailwind 之后以保留覆盖能力——但这条 import 顺序本身就是债：一旦有人「顺手」把顺序理顺，现有外观会静默改变（注释自己都警告了）。

建议：设一个「renderer.css 归零」的目标卡，逐族迁移（Button/Chip 已迁完，继续 Panel/PhotoCard/Metric），否则每次改样式都要在两套体系里思考。
债务 配置来源五路并存

「库从哪来」有 4 条路（GEMMA_LIB_ROOT env → userData 注册表 → config.json → 索引自举），「模型从哪来」有 4 位（用户指定 → 程序目录 → userData → model-cache）。这些都是历史兼容的产物，但每一路都要各自测、各自在日志里解释，且 config.json 的 onnx_model_dir 字段目前没有任何设置界面可填（设置页不存在），等于一条只有老用户知道的隐式配置。

建议：做设置中心后，把「用户指定」的来源从 config.json 迁到 app.db，逐步让 env/config.json 只保留「开发期覆盖」的语义。
债务 BANDS 阈值仍是「暂定值」

packages/engine/src/engine.ts 的 BANDS（text 0.72/0.65、image 0.90/0.80）注释明写「暂定，需按真实查询集复核后再冻结」。这是会直接影响「结果档位」的用户可见行为，却尚未有质量证据支撑。

建议：P2 阶段做真查询集标注后回填阈值；在此之前，界面应弱化「高/中/低」档的确定性（或标注为试验性）。

03函数 / 方法级缺陷 —— 具体到函数

位置缺陷影响
encoder.ts · readImageAny() 为嗅探前 2 字节「BM」魔数，fs.readFileSync(absPath) 把整张图读进内存；BMP 回退路径还会再读一次。对几 MB 的大图是纯浪费。 性能（低）
transactions/executor.ts · checkSpace() const need = g.staged + Number(extraBytes) || g.staged 用 || 表达「为空则回退」，当 staged+extra 为 0 时语义混乱；Number(extraBytes) || 0 把 NaN 也吞成 0。 可读性 / 边界
engine.ts · pickEmbedding（last_hidden_state 池化） 均值池化路径未防御 T===0（除零 → NaN，随后被归一化掩盖）；虽不影响排序，但会静默产出全 NaN 向量。 健壮性（低）
app-db.ts · setDefaultCollectDir() 用 db.exec('BEGIN IMMEDIATE') 手工开事务，而 withAppDb() 每次调用是「打开→用→关」。当前单连接同步模型下正确，但一旦将来并发/多连接，手写 BEGIN/COMMIT 没有重入与嵌套保护。 潜在并发
index.ts · engineMethod() eng as unknown as Record<string, unknown> 强转访问动态方法名，绕过了类型系统；这是「运行时方法名」场景的无奈，但让「引擎少暴露一个方法」这类错误只能靠运行时抓到。 类型安全（低）
index.ts（readIndexBin） footLen 读出来后被 subarray 截到 EOF，但没显式校验 footLen 是否合理——损坏文件里一个 4GB 的 footLen 会报「footer 解析失败」而非「footer 长度非法」，误导排障。 可诊断性（低）
library.ts · resolveInLibrary() 「目标不存在 → 找最深已存在祖先」分支里 realpath 失败时 catch { return target }，把「校验失败」静默等价成「校验通过」（见漏洞 L1）。 安全（中低）

04行业编程规范对照 —— 符合 vs 偏离

4.1 明显高于行业主流的做法 ✅

  • 契约即类型 + 运行时校验：shared/ipc.ts 一份 zod 同时产出方法白名单、参数校验、编译期类型——比主流「TS 接口 + 手写校验」高一个段位。
  • 错误信封、永不抛给调用方：envelope() + normalizeError() 让调用点只有「判 ok」一种写法，消灭了 try/catch 兜底文案的复制。
  • 原子写入 + 写前校验：索引写入「临时名 → fsync → 五道校验 → rename」是教科书级做法，很多生产项目都做不到。
  • write-ahead 事务日志：executor.ts 七步状态机 + 8 个故障注入点 + 恢复判定表，是「写路径可恢复」的正确实现，且有真杀进程的测试。
  • 零依赖引擎 + 依赖注入：引擎不 import electron/fs 之外的第三方，端口全注入，可脱离 Electron 单测——这是可测试性的最佳实践。
  • 错误码集中、按 code 分支绝不按 message 分支：errors.ts 28 码 + 文案表，界面不自算文案。

4.2 与主流/自身纪律不符的做法 ⚠️

项现状行业标准 / 自身承诺
ESLint + Prettier package.json devDeps 无 eslint/prettier；T-09 未勾 AGENTS §1 明确列「已选定 eslint + prettier（开发依赖）」；N18 标 P1。当前仓库完全依赖 tsc + 测试做静态约束，缺未用变量/import 顺序/一致性这类检查。
ID 生成 engine.ts:613 用 Math.random 自身 AGENTS「ID 新增处一律用 nanoid，不自己拼随机」；行业用 crypto.randomUUID。
静默类型降级 app-db.ts num()/text() 返回 0/'' 自身适配层「narrowValue 判不出就抛」；行业「fail loud, never coerce silently」。
注释风格 几乎每个函数 10–30 行注释，写满「为什么」 「写为什么」是对的，但当前注释:代码比偏高，部分注释成了「决策日志」；业界更倾向「代码自解释 + 关键决策留档」的平衡。
renderer console.log store/hooks 里散落 console.log('[ui] …')（经 console-message 转发到日志） 可接受，但更规范的是注入一个统一 logger（主进程已有 log()，渲染层却各写各的 console）。
错误处理边界 uncaughtException 只记日志 主流桌面应用要么退出、要么进入安全模式；只记日志继续跑是少数「带病运行」的选择。

05建议的修复路线 —— 按投入产出排序

优先动作预期收益
P0修 fingerprintLines 漏跳保留命名空间（补 isReservedLibraryName + 一致性断言）。消除「索引重建 ⇒ 库指纹漂移」的数据正确性隐患，收敛两套摘要。
