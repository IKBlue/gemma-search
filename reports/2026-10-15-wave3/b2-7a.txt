【2. 字段与"为什么"（照抄设计基线 §206 / §214）】
| 表 | 字段 | 类型/约束 | 为什么（照抄基线） |
|---|---|---|---|
| `tag` | `tag_id` | TEXT **PK** | nanoid；**不用自增：跨库合并标签时会撞** |
| | `name` | TEXT NOT NULL **UNIQUE** | 单用户 ⇒ 唯一约束**只到 name**，不需要 Immich 的 `(userId, value)` 复合唯一 |
| | `created_at_ms` | INTEGER NOT NULL | 用于「**最近用的标签**」排序 —— 比字母序有用得多 |
| `asset_tag` | `uid` | TEXT NOT NULL **FK asset.uid PK(1/2) CASCADE** | 与 `tag_id` 组成复合主键 ⇒ **天然防止同一标签重复贴在同一条上** |
| | `tag_id` | TEXT NOT NULL **FK tag.tag_id PK(2/2) CASCADE** | 标签 |
| | `added_at_ms` | INTEGER NOT NULL | 贴上时刻 |
· 判据：T1 从 `SPEC-COMPACT.md` **解析**这两节（不手写第二份清单）与真 DDL **双向**对照 ⇒ 多/少都红。
· ⚠️ 两列**显式 NOT NULL**：SQLite 的 rowid 表里复合主键列**默认允许 NULL**，不留神能插进 `(NULL, tag)`
  这种"不指向任何素材的关联"，还能重复插（NULL 互不相等）⇒ T3 用 `PRAGMA table_info` 钉住两列 `notnull = 1`。
· ⚠️ `name` 的 UNIQUE **区分大小写**（不写 `COLLATE NOCASE`）：基线只要求 `UNIQUE(name)`；折叠会让"显示名"与
  "用于比较的值"纠缠，属写入口该决定的事，不是 DDL 静默改语义的地方（已写进注释）。

【3. 为什么是"关联表"而不是给 `asset` 加一列 `tags TEXT`（注释里也写了）】
把标签塞进 `asset` 的 TEXT 列（逗号分隔/JSON）会带来三个具体故障：
① 「按标签找素材」变成**全表 LIKE 扫描**（索引用不上）；② 改名标签要**逐行重写字符串**（改漏一处就出现两个近义标签）；
③ 无法表达"贴上的时刻"（`added_at_ms`），也没有约束能防重复贴。⇒ 规范化两张表 + 复合主键是唯一不产生这三种故障的形状。
· 另加 `idx_asset_tag_tag (tag_id)`：复合主键的索引前缀是 `uid` ⇒「这条素材有哪些标签」走得通，
  但「**这个标签下有哪些素材**」走不到 ⇒ 反向要单独一条索引（标签卡的**全部用途**——筛/统计/批量——都落在反向上）。

【4. ⭐⭐ 多对多的机械证明（T3）】
| 要证明的 | 怎么证（机械） | 结果 |
|---|---|---|
| 同一条素材**可挂 N 个标签** | 给 `aa…01` 贴 t1、t2 两行 | 都成功 |
| 同一个标签**可挂 N 条素材** | t1 贴到 `aa…01` 与 `aa…02` | 都成功 |
| **同一对不许重复** | 再贴一次 `(aa…01, t1)` | **被拒**（`UNIQUE|PRIMARY KEY`）⇒ 复合主键是承重的 |
| 主键的**顺序**是 `(uid, tag_id)` | `PRAGMA table_info` 的 `pk` 序号排序 | `['uid','tag_id']`（与基线 §214 的 1/2 与 2/2 一致） |
| 两列都 NOT NULL | `notnull` 标志 | `[1, 1]`（堵住 `(NULL, tag)` 那条缝） |

【5. ⭐⭐ 删除语义：**两侧都 CASCADE**，不是 SET NULL（T4）】
· 前提断言：`PRAGMA foreign_keys === 1`（本仓适配层默认开 ⇒ CASCADE 是**真会执行**的，不是纸面声明）。
· 删**标签** t1（原有关联 3 条中占 2 条）⇒ `asset_tag` 只剩 1 条 ⇒ **2 条被带走**；
  并断言"没有 NULL 残留"（`uid IS NULL OR tag_id IS NULL` 计数 = 0）⇒ **不是 SET NULL**。
· 删**素材** `aa…01` ⇒ 剩余关联也归零。
· 反证外键真的会拒：贴到不存在的 `tag_id` / 不存在的 `uid` ⇒ 都是 `FOREIGN KEY constraint failed`。
· 为什么**不能**用 SET NULL（注释里写清）：复合主键两列 NOT NULL ⇒ SET NULL 会把行写成非法值（会被约束拒），
  而且"一条 `(NULL, tag)` 的关联"本身没有意义。
· **能红②b** 就是拿掉这里的一条 `ON DELETE CASCADE` ⇒ 删标签时直接 `FOREIGN KEY constraint failed`（见 §8）。

【6. ⚠️ 与 `asset_user_meta` 的边界 · 为什么不合并 `is_favorite`（P1 · T5/T7）】
| | `asset_user_meta`（B2-3） | `asset_tag`（本卡） |
|---|---|---|
| 关系 | **1:1** —— `uid` **就是主键** ⇒ 一条素材**最多一行** | **N:M** —— 复合主键 `(uid, tag_id)` ⇒ 同条素材**可 N 行** |
| 承载什么 | 评分/备注/**收藏**（`is_favorite` 是**那一行里的一个布尔**） | 横切组织：贴了哪些标签、何时贴 |
| 机械对照（T5） | 同 uid 插第二行 ⇒ **被拒** | 同 uid 插 2 行 ⇒ 都成功（计数 = 2） |
**为什么不合并**（注释 + T7 机械钉住）：
1. 一个**布尔**会变成**一行的存在性** ⇒ 取消收藏 = 删行？那"曾经收藏过"与"从没收藏"就分不出来，
   而收藏按四层定义属于**必须留**的意图层 ⇒ 删行会丢历史；
2. 「筛收藏」是高频查询 ⇒ 要**特判特殊标签**（索引/统计/界面都开叉）；现有偏索引 `idx_meta_favorite … WHERE is_favorite = 1` 就是为它建的；
3. 收藏在 `asset_user_meta` 里**已经有一份真相** ⇒ 再来一份 = **P1 的第二份定义**。
· T7 的机械断言：`is_favorite` 出现在 `asset_user_meta` 的列里、**不在** `tag` 的列里；
  且 `tag` 里没有任何 `favorite/star/like/mark` 类列（把"第二套标记"这条路钉死）。
