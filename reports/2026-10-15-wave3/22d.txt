【3. arm64 专项：sharp 那个坑（代码级证据，不是推断）】
  问题：T-22c 证明 @img/sharp-win32-x64 **不能动**（移走连文本检索都失败）。sharp 是**按平台装包**的。
  本机实测：
    · node_modules/@img 下只有 colour · sharp-wasm32 · **sharp-win32-x64** —— **没有 sharp-win32-arm64**
    · node_modules/sharp/dist/sharp.cjs:69-70  case "win32-arm64": sharp = require("@img/sharp-win32-arm64/sharp.node");
    · node_modules/sharp/dist/sharp.cjs:113     报错文案 'Could not load the "sharp" module using the <runtimePlatform> runtime'
    · node_modules/sharp/package.json:188        "@img/sharp-win32-arm64": "0.35.5"（optionalDependencies，npm 按 os/cpu 门控安装）
    · package-lock.json:1649-1651                "node_modules/@img/sharp-win32-arm64" + resolved tarball（registry.npmmirror.com）
    · npm 缓存（%LOCALAPPDATA%\npm-cache 与仓库 .npm-cache）**内容搜索** sharp-win32-arm64 ⇒ **命中 0**
  结论 (1) **会报**：arm64 Windows 上会走 sharp.cjs 的 win32-arm64 分支去 require 那个包，而包里没有它
           ⇒ 正是「Could not load the sharp module using the win32-arm64 runtime」。
           （依据 = 代码 + 包内文件缺失；**不是**在 arm64 机器上跑出来的 —— 本机没有 arm64 硬件。）
  结论 (2) 想让 arm64 真能用，**必须让 arm64 的 sharp 包进产物**，两条路：
           (a) **按架构分别构建**（arm64 机器 / CI 上 npm ci + 打包）⇒ npm 按 os/cpu 自然装上 arm64 变体。推荐。
           (b) 本机交叉安装 npm i --os=win32 --cpu=arm64 @img/sharp-win32-arm64@0.35.5 ⇒
               同一次打包会同时带 x64 与 arm64 两份 sharp（约 +19 MB）。本机无网 + 缓存无命中 ⇒ **未做、未验证**。
       ⇒ 只改 electron-builder.yml **不足以**让 arm64 可用；**要改依赖安装方式**（分架构构建）。

【5. 顺带发现（**不在本任务范围**，未改任何 JS）】
  打包态日志出现**两对**「模型搜索命中 / 设备决策 / 载入完成」（3.6s 与 4.2s）⇒ ensureEncoder() 在并发下
  会加载两次模型（它只挡「encoder 已存在」，不挡「正在加载中」）。触发：预热(1.5s)未结束就发起检索。
  影响：多一次 1.7 GB 模型加载（内存峰值翻倍 + 首次检索变慢）。建议单开任务修（一行 in-flight promise）。
