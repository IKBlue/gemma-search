【实现要点】
1) **端口抛错纪律**（T-16a 的明文契约）：asEngineError() 统一转换 —— 已经是 EngineError 的原样抛（保住 code），
   其余按映射表给码。映射：.gs.db 打开失败 / 元表缺失 / schema 过新 / 迁移失败 / 导入族 ⇒ INDEX_CORRUPT（元数据损坏，
   处置就是重建）；没有落点 ⇒ INDEX_MISSING；实在认不出 ⇒ INTERNAL。M8 实测：坏索引 / 坏 .gs.db 走信封后
   code 仍是 INDEX_CORRUPT（**不是 INTERNAL**），且 userMessage 非空。
2) **回落必须明说**：ItemStorePort 找不到 .gs.db 时调 onFallback（默认 console.warn），文案含"回落到 items.json"
   与**具体路径**（M4 断言）。items.json 走**引擎的 readItems**，不重写第二份解析。
3) **回落带 mtime 守卫缓存**：引擎取件循环会对同一库反复 getItem（最多 200 次），每次重读 2 MB JSON 是浪费；
   缓存只在文件 mtime 变化时失效（改了文件立刻读到新内容，不是永久缓存）。
4) **root 与 .gs-* 落点分开**：storageOf().root = **声明库根**（素材所在地，scan/collect 数的是它）；
   .gs-* 路径可能落在 userData 回退目录（T-04 的裁定）。素材从不搬家，只有派生数据会回退（M2 断言）。
5) **写探测默认关**：端口每次 storageOf 都会被调，probeWrites=true 会在库根反复写删 .gs-write-probe-*；
   那是 T-04 启动路径的职责。代价（如实写）：ACL 拒绝的库根会被当成"存在即可用"。
6) 索引读取**只有一处入口**：index-file.readIndexBinAt → 引擎 readIndexBin（五道）。main 侧不出现第二份 GSIDX 解析
   （T-12a 的 A1 用例持续守着这件事）。
7) 可空性适配：.gs.db 里 vector_row / vector_source 可以是真的 NULL，而引擎的 IndexItem 把它们声明成
   「可选 number」/「可选 string」（可缺省、不可为 null）⇒ 映射时把 null 落成"键不存在"
   （语义相同：引擎用 == null 判断）。
8) ⚠️ 本轮抓到并修掉一个**真 bug**（由 M3/M7 的失败暴露）：sqlRowToItemRecord 最初按**字段名**取 SQL 行的值，
   而 SQL 行是**下划线列名**（lib_id / rel_path）⇒ 每一行都报"缺少字段 libId"。修法：先按 ITEM_FIELD_COLUMNS
   把列名翻成字段名（同一份配对，不另写映射），缺列**不补 undefined**（缺失要响亮）。

【这条工作**证明不了**什么（如实写）】
· **不等于"界面做到了 M0"**：本轮只到引擎 + 端口的调用面（脚本直调 createEngine），没有 Electron 窗口、
  没有 IPC、没有渲染层。界面侧的 M0 判据要等 T-20/T-21/T-22。
· 不是打包态实测：跑的是仓库内的 out-of-package 路径（node 直跑 .ts），electron-builder 打包冒烟不在此列。
· 检索用了**真编码器**（CPU，2.1s 载入），但查询是脚本写死的文本；**没有**覆盖图像查询、GPU 路径与性能阈值（那属 T-19）。
· 取件的"字节一致"是**副本内自洽**（源文件是按 items.json 的 relPath 落进副本的 32 字节文件），
  不是"从原库 G:/model 取出原件"——原库在本沙箱不可读写（环境限制，见下）。
· 索引读取正确性沿用 T-12b 的逐道破坏证据（本轮没有重复破坏五道）。
· 未跑全量 npm test / build / e2e（Lead 的分工）。
