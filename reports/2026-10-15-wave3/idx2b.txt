===== 1. 真实模式到底走哪条路（调用链） =====
**启动**：
  renderer → IPC `indexStart`（白名单/zod）→ main/index.ts（IDX-2b2 接线）→ `engine.indexStart`
  → `index-jobs.start()` → `requirePorts()`（无注入 ⇒ INTERNAL「IDX-2b 未接线」）→ `registry.requireExistingRoot(libId)`
  → 生成 `jobId`（`crypto.randomUUID()`，零依赖）→ 同步发**首条** `index.progress` → **立刻返回** `{jobId,total:0,phase:'scan'}`
  → 后台 `void (async () => …)` 调 `ports.buildIndex({ libId, libRoot, device, seq, rebuild, signal, onProgress, writeIndex })`
**进度**：indexer `buildIndex` 的 `onProgress` → 引擎归一化（单调钳制）→ `onEvent(index.progress)` → main `emit()` → `CH_EVENT` → renderer。
**写字节（唯一一条）**：构建器 → `writeIndex({ bytes })` → 引擎包一层补 `libRoot` → `ports.writeIndex({ libRoot, bytes })`
  → main 的 `writeIndexAtomically(libRoot, bytes)` → `<库根>/.gs-index.bin`。**引擎里不存在第二处写字节**（J8 有源码扫描）。
**取消**：`indexCancel` → `job.cancelled = true` + `controller.abort()` → 构建器在 safe point 抛 `BuildCancelledError`
  → 引擎 catch → `index.done{cancelled:true, ok:false}`（**不**发 `index.failed`）。
**续跑**：`indexResume({jobId, libId?})` → 同进程履历给 `device/seq/libId/done`；跨进程靠 main 传 `libId`
  → 以 `rebuild:false` 起构建 → 构建器按 compat 自行复用 → `index.done.reused` 上报真实复用数。


===== 2. 事件与返回形状（与 fake.ts 逐字段同形 ⇒ 渲染层不用两套） =====
`index.progress` `{ type, jobId, libId, done, total, skipped, failed, ratePerSec, etaSec, phase, note?, deviceFallback? }`
`index.done`     `{ type, jobId, libId, ok, cancelled, indexed, total, reused, encoded, failed:[{relPath,stage,error}], compat }`
`index.failed`   `{ type, jobId, libId, error:{ code, message } }`（**仅硬失败**；取消不算失败）
返回：`indexStart → {jobId,total,phase}` · `indexResume → {…, reused}` · `indexCancel → {cancelled, reason?}`。
⚠️ 真实模式下 `indexStart` 的 `total` 立刻返回 **0（未知）**：总数要等构建器 scan 阶段才确定 —— **不假装知道**；
   首条 progress 会带真实 total。fake 模式行为不变（它本来就先知道 total）。


===== 3. 「未接线」vs「接线了但环境不满足」—— 可区分且各有测试（Lead 2026-10-17 补的要求） =====
| 情形 | 表现 | 用例 |
|---|---|---|
| 没注入 `indexing`（2b 未接线） | `indexStart` **同步** `ok:false, code:INTERNAL`，message 含「IDX-2b 接入」 | J6 + fake.test F8/F17 |
| 注入了，但构建器报环境问题（模型缺失/库不可读…） | 异步 `index.failed{error.code = 真实码}`（如 `MODEL_MISSING`）+ 紧跟 `index.done{ok:false}`；**message 不提 IDX-2b** | **J5**（断言 `code === 'MODEL_MISSING'`、`code !== INTERNAL`、message 不含 IDX-2b） |
| 注入了，但库根不存在 | `indexStart` 同步 `LIB_ROOT_MISSING`（来自 registry 校验） | 既有引擎机制（registry.requireExistingRoot） |
⇒ 三种错误**互不冒充**：用户不会看到「永远为真的未接线」那种假答案。


===== 4. 四个能红（卡面要求） =====
1. **取消后索引文件被写坏 ⇒ 红**：J2 断言取消后 `writes.length === 0`。若引擎在取消后仍把字节交给写者，这条立刻红（没有「半个文件」的可能，因为唯一写入口根本没被调用）。
2. **进度回退 ⇒ 红**：J3 用回退序列 2→1→3，断言发出的是 `[0,0,2,2,3]`。**若去掉钳制**，序列会是 `[0,0,1,3]`（回退原样转发）⇒ 断言红。
3. **复用计数错 ⇒ 红**：J4 同时断言「返回里有 reused」「`index.done.reused === 2`（构建器上报）」「`rebuild === false`」「progress 里有 note」——任一错就红。
4. **引擎里出现第二份写入实现 ⇒ 红**：J8 **遮蔽注释后**扫描 `index-jobs.ts`/`index-ports.ts`：不许 `from 'node:fs'`、不许 `writeFileSync|renameSync|writeIndexAtomically`；并正向断言字节只经由 `p.writeIndex({ libRoot, bytes })`。
   （⚠️ 第一版 J8 因「注释里提到 writeIndexAtomically」假红 —— 已改成先 mask 注释，与仓库既有静态断言的写法一致。）

  **其余入参/出参形状一字未动**（Lead 授权的范围就这一行）。

===== 9. 建议的 SPEC §5.1 措辞（Lead 照抄；我不改规格） =====
在 §5.1 的 `indexResume` 条目里补一句（其余方法条目不动）：

```text
indexResume { jobId?, libId? } → { jobId, total, phase, reused }
  续跑一个被中断的索引任务。能否复用已编码行由**构建器**按 compat 判定（不等则复用 0 条，并在
  index.progress 的 note 与 index.done.reused 里说明）；引擎只转发，不自己判 compat。
  ⚠️ `libId` 是**可选**新增（IDX-2b）。原因：引擎没有持久状态 —— 进程重启后内存里没有该 job 的履历，
  只给 jobId 时无法知道续哪个库；main 从 job 行读出 libId 一起传。同进程内有履历时不传也可。
  跨重启续跑**必须**带上它（否则引擎返回 BAD_REQUEST 并说明原因）。
```

另：§6 的方法计数在 IDX-2a 已从 22 改为 25（U35 三个方法）；本次**没有**新增方法，只是 `indexResume` 入参加一个可选字段 ⇒ **计数不变**。
