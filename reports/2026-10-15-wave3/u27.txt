2. 契约（与裁定逐字一致）
=================================================================================
  appHealth {} → { unhealthy: boolean, count: number, reason: string | null, firstAt: string | null }
  · **只读**：不改任何状态（可以随便查）；
  · **恒成功**：不返回 ok:false —— 查不到事实本身就是一条事实（unhealthy:false）；
  · **不含** sessionExit / **不持久化**「上次崩溃」：不写 app_meta（会留下下次启动必然过期的假标记）；
    「上个会话异常退出」由**日志**说明 —— 面板里明确指向 data/_app.log，
    ⚠️ 并且**刻意不给「打开日志」按钮**：契约里没有「打开日志文件」的方法（reveal 只接受 libId+uid，是素材坐标），
       硬塞一个按钮就得先造接口或猜日志路径 ⇒ **宁可不显示，也不猜**；
  · **不含**路径/用户名/堆栈正文（清洗见 §3）· **不上报**。

8. e2e 注入方式（**刻意不给产品开测试口子**）
=================================================================================
  E15-b 往**主进程**投递一次 unhandledRejection（process.emit(...)）—— 那正是 Node 在真的未处理 rejection 时做的事，
  走的是 DF-6 **同一个处理器**（crash-policy.ts：记日志 + 标记不健康 + **不退出**）。
  ⚠️ **诚实标注**：事件本身是**合成的**（不是等一个真的异步 bug 发生）；
     但它触发的处理器 / 状态 / IPC 读口 / 界面渲染**全是真的**。这条断言能抓「接线断 / 状态没传出去 / 界面没说」；
     抓不到「Node 会不会真的把某类 rejection 交上来」（那是 Node 语义，不是本方法的契约）。
  · 先试过 utilityProcess.fork() + kill()：**实测不产生 rejection**（探针原文：fork 成功、kill 后无事件）⇒ 放弃，不留死代码；
  · 产品里**没有**任何为测试开的分支。
