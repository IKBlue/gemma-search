===== 1. A 核实（只核实，不改）：readImageAny 读整文件 =====
位置：`apps/desktop/src/main/encoder.ts:118`（`async function readImageAny`），调用点 `:230`。
核实：审查成立 —— 为嗅探前 2 字节 `BM` 走 `fs.readFileSync(absPath)` 把**整张图**读进内存；BMP 回退分支再读一次。
⚠️ 本卡边界明写「不改 main/encoder.*」，且 AGENTS §4 要求编码路径改动**先有 T-00 基线**（全库 min/中位余弦 + top10 对照）、改后重跑并归档 ⇒ 我**不动它**。
建议改法（给编码线）：
  1. 先用有界读拿头：`fs.openSync` + `readSync(buf, 0, 64, 0)`（上限取 64KB 足够）；
  2. BMP 判定只依赖前 2 字节 `BM` + 头部尺寸字段（BMP 头 14+40 字节）；
  3. 只有**确认是 BMP 且需要解码**时才读全文件（解码本来就需要全部字节，无法避免）；
  4. 能红：注入读取计数（或断言请求的字节数 ≤ 上限），大图路径必须 ≤ 上限。
风险：JPEG/PNG 路径改为只读头后，解码库仍要读全文件（那是它自己的读）；收益是**我们**不再多读一遍。

===== 3. C 修复：engineMethod 受约束类型（类型层能红） =====
### 3.1 三行
改前：`const table = eng as unknown as Record<string, unknown>; const fn = table[method];`（`method: MethodName`）⇒ 名字写错/引擎少暴露一个方法，**编译期都不报**，运行时才走「引擎无此方法」。
改后：`type EngineBackedMethod = { [K in MethodName]: K extends keyof EngineApi ? K : never }[MethodName];`
      + 断言函数 `isEngineBackedMethod(eng, m): m is EngineBackedMethod`（唯一的运行时→类型收窄桥）
      + `engineMethod(eng, method: EngineBackedMethod)`；查找用 `const table: Partial<Record<MethodName, unknown>> = eng;`（**结构化赋值，无 as**）
      调用点：`const fn = isEngineBackedMethod(eng, v.method) ? engineMethod(eng, v.method) : null;`
为何非放宽：名字来自运行时，但它**必须是引擎真的有的名字**。映射类型把不在 `EngineApi` 上的名字变成 `never` ⇒ 这类错误从运行时提前到编译期。唯一保留的 `as` 是把各异的引擎方法签名收成统一入参形状，且前面已有 `typeof === 'function'` 判定（注释写明这不是绕过）。
### 3.2 能红（两个探针：新/旧签名编同一个错名字）


===== 4. D1 修复：footLen 显式长度校验 =====
### 4.1 三行
改前：`JSON.parse(buf.subarray(start+blockBytes+4, start+blockBytes+4+footLen))` —— subarray 自动截到 EOF ⇒ 荒谬 footLen 走到 JSON.parse 才炸，报「footer 解析失败」。
改后：先 `if (footLen === 0 || footLen > FOOT_LEN_MAX || footLen > footHave) throw corrupt('footer 长度非法：…')`，再解析。
为何非放宽：上界是**格式不变量**（footer 是我们自己写的元数据 JSON，实测 ~200 字节；取 1 MiB ≈ 5000×），既挡住荒谬值、保护内存，又不误伤将来加字段；把「长度非法」与「内容解析失败」分成两个可诊断的错误。

===== 5. D2 / D3 / D4 / checkSpace：逐条判真伪（不改 + 理由） =====
### D2 `setDefaultCollectDir` 手写 BEGIN IMMEDIATE（`apps/desktop/src/main/app-db.ts:279-291`）
判定：**真，但当前无可达缺陷**。审查自己也写了「当前单连接同步模型下正确」。证据：`withAppDb()` 每次调用是「打开→用→关」，同一时刻只有一条连接、且调用同步；BEGIN IMMEDIATE→两条 UPDATE→COMMIT 之间没有 await ⇒ 不存在重入/嵌套。
不改的理由：① 现状无缺陷；② 全仓手写事务有 **3 处**（`app-db.ts:282`、`db/import.ts:290`、`db/migration-engine.ts:206`），只改 1 处 = 留下三套机制（P1/P2 更糟）；③ 迁移引擎那处的事务语义（每条迁移一个事务 + 回滚 + 版本记账）不能用一个通用包装器随替换。
建议：**单开一条**「统一事务助手」，一次把 3 处换掉（助手要显式支持「已在事务里就报错」，而不是静默嵌套 —— SQLite 不支持嵌套 BEGIN）。

### D3 `pickEmbedding` 的 `T === 0`（`packages/indexer/src/encode_queries.ts:50-71`，另有副本 `spike_onnx.ts:65` / `build_index_onnx.ts`）
判定：**半真**。真：确实**没有** `T === 0` 的防御。**假**：不会产生 NaN —— 除零被 `n = Math.sqrt(n) || 1`（`:67`）挡住了：T===0 时 data 全 0 → n=0 → `|| 1` ⇒ 归一化后仍是**全零向量**，不是 NaN。
   ⇒ 真实后果是「**静默产出全零向量**」（该素材检索时永不命中、且不报错），比 NaN 更隐蔽，但不是审查描述的 NaN。
不改：`packages/indexer/**` 属编码护栏禁改范围（Lead 裁定 b）。
建议（给编码线）：`if (!lh) throw …; const [B, T, D] = lh.dims; if (!T || !B || !D) throw new Error('last_hidden_state 维度非法');` 并同步两处副本的交叉核对。
   ⚠️ 顺带：`pickEmbedding` 现在有**多份副本**（encode_queries 与 build_index_onnx 各自实现），注释靠「交叉核对」保证不漂 —— 建议收敛成一份（P2，同属编码线的活）。

### D4 TOCTOU（同一函数）
判定：**真 · 固有**。`lstat/existsSync` 与调用方真正使用路径之间存在窗口（组件可能被替换/新建）—— 纯 Node 没有 openat/相对 fd 解析，窗口不可根除。
不改的理由：① 本轮修掉的是「**拿不到结论还放行**」这一半（真缺陷）；② 窗口那一半的缓解手段是「在使用点所在的层再校验一次」，而写入路径本来就有独立的一道：`assertWritableGsPath()`（直接子项 + 保留命名空间，见 §6 表第 3 行）与 `assertCollectDirAllowed()`（白名单，见 §6 表第 2 行 —— 那条**另有同类缺陷已上报**）。

### §03 第 2 条 `checkSpace` 的 `||`（`packages/engine/src/transactions/executor.ts:158`）
判定：**真 · 低（可读性/一致性），无可达缺陷**。`need = g.staged + Number(extraBytes) || g.staged`：所有 sane 输入（extraBytes ≥ 0、有限）下 `need === staged + extra`；staged=extra=0 时 `0 || 0` 仍是 0 ✓。
   **但有一处真实的不一致**：同一函数里同一个值两种兜底 —— `need` 用 `|| g.staged`，`details` 用 `Number(extraBytes) || 0`（`:160`）。NaN 会被两者吞掉，但方式不同。
不改：不在本卡 D 列表的批准范围内，且改动会改变负值/NaN 的行为（今天不可达）。
建议补丁（若 Lead 要）：`const extra = Number.isFinite(Number(extraBytes)) ? Math.max(0, Number(extraBytes)) : 0; const need = g.staged + extra;` 并让 details 复用 `extra`。
