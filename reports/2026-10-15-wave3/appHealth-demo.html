appHealth · 让「不健康」被看见

第 22 个 IPC 方法（只读） DF-6 的配套 设计稿 · 非已实现

一、它解决什么问题

DF-6 已经把「未捕获异常」从只记一行日志改成两条更响亮的策略：

事件现在的行为（已实现）界面能看见吗
uncaughtException先落盘三行 → flush → app.exit(1)（保留 Electron 收尾，不用 process.exit）下次启动由日志说明
unhandledRejection记日志（不退出）+ 标记进程内只读「不健康态」；原因取第一条（根因不被余波覆盖）看不见 ← 缺口就在这

「不健康」目前只活在主进程里（日志 + 可导入的 crashUnhealthyState()）。用户遇到的是「应用怪怪的，但没有任何提示」—— 这与本项目「最怕静默」的口径冲突。appHealth 就是把这件事接到界面上：只暴露事实，不做修复。

三、契约（拟）

appHealth(): Promise<{
  unhealthy: boolean      // 本次进程内是否出现过未处理异常
  count: number           // 次数
  reason: string | null   // 第一条的摘要（根因）
  firstAt: string | null  // ISO 时间
  sessionExit?: 'crashed' | null   // 上个会话是否以未捕获异常退出（读日志得出）
}>
只读
无副作用、不改任何状态 ⇒ 可以随便轮询（界面上只在启动 + 打开诊断面板时各查一次）
恒成功
不返回 ok:false：查不到事实本身就是一种事实（unhealthy:false）
不含敏感信息
只有计数、首条摘要、时间；不含路径/用户名/堆栈正文，也不上报
与 DF-6 同源
数据来自 crash-policy.ts 的同一份进程内状态 ⇒ 不产生第二份真相

四、为什么是「低调可见」而不是弹窗

做法为什么不
启动时弹模态框未处理异常常常是**已经被兜住的一次**网络/解码抖动；每次弹窗会把用户训练成"无脑关掉"
完全不提示等于回到静默：用户看到的是"检索偶尔不灵"，无法归因，也无法配合诊断
顶栏一个低调标记 + 诊断面板事实摆在**能被找到**的地方：不影响主流程，需要时点一下就有原因、次数、时间与「导出日志」

崩溃退出（③）无法在"当时"提示 —— 界面在那一刻已经没了。所以它的呈现是：下次启动时由同一条 appHealth 说明「上一个会话以未捕获异常结束」，并给出日志位置。

五、边界（P6 口径）

  • 它只暴露事实；不自动重启、不自动修复、不静默清零。
  • unhandledRejection 不退出（良性 rejection 不该杀掉应用）；只有 uncaughtException 退出。
  • 没有这个方法之前，实现者明确拒绝声称「诊断面板上能看到」—— 本稿就是把那句声称变成可实现的东西。
