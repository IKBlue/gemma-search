【1. 架构：三个文件、两个库、两份账本（为什么不能塞进一个函数的一次事务）】
```
引擎 collect（packages/engine/src/engine.ts 的 doCollect）
   └─ 复制文件（真正的"已交付"事实；返回 jobId + succeeded/skipped/failed）
        ↓  (只在真实模式；见 §8)
index.ts 的 collect 钩子  ──调用──▶  collect-ledger.ts::recordCollectBatch   ← **唯一的 1:N 编排**
                                        ├─ 库级 .gs.db   ▶  db/exports.ts::insertExportRows   （N 行，单事务）
                                        └─ 应用级 app.db  ▶  app-db.ts::insertActivity          （1 行）
```
· 为什么**不**写成一个事务：`asset_export` 与 `activity` **在两个不同的数据库文件里**（库级 `.gs.db` / 应用级
  `app.db`，schema-layers 的落点裁定）⇒ SQLite 的跨连接事务不存在。这里选择的是**顺序写 + 补偿**（§7），
  并把"这一次到底写成了什么"如实返回（`written/exportRows/activity/warning`）。
· 为什么两个写入口而不是一个：§2.3「每张表一个写入口」，且两张表属于**不同层的两套账本**；
  "1:N 这个事实"由**编排**负责，不是由某张表的写入口负责。

【2. ⭐⭐ 1:N 的机械证明（L1 · 跨两个库文件）】
一次 collect（batch='j-batch-1'，3 条：copied / skipped / failed）⇒
· `activity` **恰好 1 行**：`activity_id='j-batch-1'`、kind='collect'、lib_id='L1'、result='failed'（有 failed ⇒ 整批 failed）；
  `detail_json` 是**结构化**的：`{target_dir, target_dir_name, bytes_total, copied:1, skipped:1, failed:1}`；
· `asset_export` **恰好 3 行**，**三行的 `batch_id` 都是 'j-batch-1'`（两库之间**没有物理外键**，靠这个 id 关联）；
· 逐行映射对：`a.zip/copied/null` · `b.zip/skipped/already-exists` · `c.zip/failed/'DISK_FULL: 没空间'`。
· L1b 把 **result 判定表**也钉住：全 copied ⇒ `ok`；全 skipped ⇒ `skipped`；有 failed ⇒ `failed`。

【3. uid 指向 `asset` 的"最佳努力"（L3）—— 以及为什么这是必要的】
· 引擎的索引与 `.gs.db` 的 `asset` 是**两份来源**（索引可由 `items.json` 重建，不保证每条 uids 都在 `asset` 里落行）；
· 外键开着的库上，硬写一个 `asset` 里没有的 uid ⇒ **整批都写不进去**（一条坏 uid 毁掉 N 条历史）；
· ⇒ 写之前先 `SELECT uid FROM asset WHERE uid IN (…)` 过滤：认识的照写、不认识的落 **NULL**
  （DDL 本来就允许 NULL，且有 `ON DELETE SET NULL`）——"名字/结果/时刻"照旧留下，历史仍可读，只少一个可点链接。
· L3 钉住：known ⇒ 真 uid；unknown ⇒ NULL；且整批**仍然 written=true**（不因为一条对不上就整批失败）。

【5. ⭐⭐ 失败不静默（L5）· 绝不改判取件成败】
| 场景 | 结果 |
|---|---|
| `userDataDir` 为空（应用数据未就绪） | `written=false` + warning；**不抛** |
| `.gs.db` 落点没解析出来 | 同上 |
| `.gs.db` 父路径是文件（打不开） | 同上 |
| 没有结果行 | 同上 |
| 没有 batch id | 同上 |
· 设计口径：**文件是否已复制出去**由引擎按真实文件操作裁决；"记历史失败"只能变成**警告**（信封 `warnings`
  + 日志），不能把一次成功的取件说成失败 —— 否则用户会重试取件（目标已存在 ⇒ 全部 skipped，更乱）。
· ⚠️ 用例里踩到一个**正常行为**：`openGsDb` 会**自动建父目录/建库**（这是建库的正常语义，不是缺陷）⇒
  "打不开"必须用真正打不开的路径（父路径是**文件**）来造，否则会误判成缺陷。

【6. ⭐⭐ 补偿（L6/L7）—— 以及 L7 暴露并修掉的**真缺陷**】
· L6：先占住一个 batch id（activity 主键）⇒ 让 activity 写失败 ⇒ **这一批 export 明细被撤回**（行数 0），
  原本那一行 activity 不受影响 ⇒ 不会留下"N 行明细却没有活动记录"的半条历史。
· ⚠️ **真缺陷（L7 抓到，已修）**：第一版补偿是 `DELETE FROM asset_export WHERE batch_id = ?` ——
  但同一 batch 可能被**重放**（第一次成功、第二次因 activity 主键冲突失败）⇒ 按 batch 删会把**上一次成功的那批
  行一起删掉**（实测：重放后明细变成 0 行，期望 1 行）。改为**按本次生成的 `export_id` 删** ⇒ 只撤自己写的。
  这条已写进 `db/exports.ts` 的注释（把踩过的坑留在代码里，而不是只留在这份证据里）。
· L7：重放同 batch ⇒ `written=false`（activity 主键挡住）、明细**不翻倍**（1 行）、活动记录 1 行。

【7. 接线点与"模拟模式不造假历史"（§8）】
· 钩子在 `main/index.ts` 的 IPC 分派尾部：`if (!FAKE_MODE && v.method === 'collect' && res.ok)` ⇒
  调 `recordCollectLedger(res.data, v.params)`，把返回的 warning 挂到信封（**不改判 res.ok**）。
· ⚠️ 为什么 `!FAKE_MODE`：桩引擎的 collect 返回 `ok({succeeded: params.uids, …})` —— **没有真实文件、没有 jobId**
  ⇒ 造出来的是**假历史**（B2 系列的教训：宁可没有，也不要假数据）。真实模式才有"文件已复制"的事实。
· 映射口径：`assetName` 用**文件名**（失败时退回源相对路径 / uid —— 宁可退化，不要写空串，空串是无信息）。
