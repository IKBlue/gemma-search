【2. 三种原因**分开**（机器可读 code + 人话 reason）】
| code | 触发 | 人话（界面直接显示） |
|---|---|---|
| not-found | ENOENT / ENOTDIR / 空路径 | 库根不存在（盘符变了、盘未挂载，或目录被删除/改名） |
| not-a-directory | stat 成功但 !isDirectory() | 库根不是目录（同名文件占位？） |
| inaccessible | EACCES / EPERM / 其它 IO 码 / **探测超时** | 库根不可访问：权限不足（EACCES）… / 库根探测超时（400ms 内没回应；网络盘未挂载时常是这样） |
A1–A6 逐条钉住；**A5** 还要求"其它错误码不许被吞"（理由里要带上 EBUSY 这类码）。

【3. **不阻塞启动**（怎么做到的 + 证据）】
· 探测是 **async**（fs.promises.stat）+ Promise.race 的**有界等待** DEFAULT_PROBE_TIMEOUT_MS = 400：
  断开的网络盘 stat 会卡到 SMB 超时（几十秒），有界等待把它变成"400ms 后如实说探测超时"；
· probeRoots 对每个库**并发**探测、**每个自带超时** ⇒ 一个库卡住/坏掉**不影响其它库**；
· 定时器 unref()：不让一个探测把进程钉住。
· 证据 A7（40ms 有界等待，实测 took < 1000ms，code=inaccessible、理由含"超时"）·
  A8（GOOD 与"永不回应"的 Z:\slow 同时探测：GOOD 照常 available，slow 不可用，两条都在）。
· 另：`libraryList` 的行数与排序**完全没变**（同批行一个不少）⇒ decideGate 的"有库就进主界面"也不变 ⇒
  "其余库照常可用"不是靠新分支，而是**没有引入任何新分支**。
