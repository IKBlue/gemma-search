2. 两个变量为什么必须分开（可解释性，不是措辞）
================================================================
以前**同一个** `lib` 既当「体检看哪个库」又当「重建写到哪个库」⇒ 多库时用户无法回答
「我这次重建写进的是哪一个」。而读与写的**容错完全不同**：
· **读**错一次，再读一次就行 ⇒ 范围可以有默认视野（多库时取第一个可用的做默认视野是合理的）；
· **写**错会落到用户没指定的地方，无法"再写一次"抵掉 ⇒ 落点**不许猜**。

⇒ 本卡据此把两条语义**分开成两个状态**，并让写操作只认落点：
`decideWriteGate` **只看 `target`**；scope 是全部库**不会**让写变得更允许，也不会被当落点
（"不许拿全部库当落点"因此是**结构上**成立的，不是靠一处特判）。

================================================================
3. 能红（同一条判据考两种实现，给出相反答案）
================================================================
~
// 「合并版」参照实现（= U32 之前的写法：一个变量兼职）
const merged = () => { const s = deriveReadScope(data); ... return { scope: s, target: {libId: s.libId} } }
// 同一份数据（两个库、用户没指定）：
deriveWriteTarget(data)            => null            // 两变量版：落点未定
merged().target.libId              => 'L1'            // 合并版：**替用户挑了**落点

decideWriteGate(realScope, null)          => { allowed: false }   // 应然
decideWriteGate(mergedScope, mergedTarget)=> { allowed: true  }   // 合并版放行 ← 判据抓住它
~
⇒ 谁把两者合并回去，**U32-b 的断言（`allowed === false`）实测就是 true ⇒ 必红**。
（测试里用 `assert.notEqual(mergedGate.allowed, realGate.allowed)` 把这件事钉住；
  不是写一条注定失败的断言 —— 那种"能红"只会让套件变红，不是判据。）

⚠️ **写测试时真抓到一处设计缺陷并改掉了实现**（如实记）：第一版 `deriveWriteTarget` 规则是
"全库只有一个可用的 ⇒ 用它"，于是「用户明确选了 LB（不可用）+ 还有 L2 可用」时会把落点悄悄换成 L2。
U32-e2 当场红 ⇒ 改成：**chosen 指过但不可用 ⇒ 落点一律 null**（不许换库顶上，且要把不可用如实告诉用户）。
—— 这正是"判据先写、实现后改"的价值：不是先实现再编测试。
