  items: z.object({
    libId: LibId,
    folder: z.string().max(64).optional(),
    ext: z.string().max(16).optional(),
    hasArchive: z.boolean().optional(),
    sort: z.enum(['relPath','folder','stem','imageMtime','-relPath','-folder','-stem','-imageMtime']).optional(),

  · 一律 `.strict()`；**不接受绝对路径**（I1 断言多传 `root` 被拒）；

【2. 实现（main/items-ipc.ts · 新增）】
· **只读**：`openGsDb({ dbPath, readOnly: true })`；只跑 SELECT；`createLibraryResolverPort(...)` 用默认
  `probeWrites=false`（浏览是只读动作，**不能在库根写探针文件**）；
· **读映射只有一份（P1）**：行 → 条目复用 S2 的 `db/row-types.ts#joinedRowToItemRecord()`，我不重写类型判据；
  本文件只写**筛选/排序/分页/facets** 的 SQL。列别名写在**一张配对表** `ALIAS_PAIRS`（表.列 → 别名）里，
  并由 I8 逐字钉住 14 个别名 + 把造出的行喂给那个映射器（**别名一改就红**，不会静默错位）；
· `total` = 一条 `COUNT(*)`（**不是 rows.length**）—— 越界时 rows=[] 而 total 照旧；
· `facets` = 两条 `GROUP BY`（folder / preview ext）+ 两条 `COUNT(DISTINCT ...)` 作 foldersTotal/extsTotal，
  同一 `WHERE lib_id = ?` —— **不带筛选条件**（下拉永远看到全库）；count 降序 + value 升序，各取前 200（`FACET_LIMIT`）；
· 排序带 `a.uid` 兜底 ⇒ 分页确定、同一行不会出现在两页（I2 断言页间无重复）；
· 缺 `.gs.db` ⇒ **`DB_MISSING` + 人话文案**（用文件在不在判定，不靠 SQLite 报错文案；只读打开本就不会建库）；
  本模块自有码**不被引擎映射表改写**（否则 DB_MISSING 会被改写成 DB_OPEN_FAILED，界面就拿不到"先扫一次"）；
· **永不抛**：解析库/打开库/查询全包在 try 里，失败给带码信封 + `userMessage` 非空（I7）。
· index.ts：`if (v.method === 'items') → runItemsQuery({ libId, libraries: 已解析库清单, userDataDir, legacyLibrariesDir }, p)`
  —— 只递**已解析**的库清单，库从哪来仍由 library-config 决定（与 library-ipc.ts 同形）。引擎**未改**：
  这是一条外壳读路径（读 .gs.db 的 6 张表），引擎不 import 存储实现，加进引擎反而要新开一个端口。

【4. 为什么"能红"不是空话（断言设计）】
· 越界那条断的是 `total === 7`，而 `rows.length === 0` ⇒ 把 total 写成 rows.length 必红；
  判据来自 `limit < total`（满页 3≠7）与越界（0≠7）两个场景，**不是**靠"两者恒不等"（整库取完时 7==7，I4 里显式断言了这一点）。
· facets 那条断的是"**不在第一页**的 ZZ 必须出现"，而"从 rows 推导"看不到 ZZ（I5 里两条断言成对出现）。

===============================================================================
起因：P4-2 逐字核出 SORT_COLUMNS 只有 relPath|folder|stem|imageMtime（8 串）⇒ 没有体积列，
      而 F2 浏览页的计划写着「排序（名称 / 大小 / 时间）」⇒ 体积排序是**要求**（上一张卡漏了一列）。

【1. 白名单 8 → **12 项（逐字，界面可直接接）**】
  relPath · -relPath · folder · -folder · stem · -stem
  imageMtime · -imageMtime · imageSize · -imageSize · archiveSize · -archiveSize
  · imageSize = preview 行体积（asset_file role=preview.size_bytes）
  · archiveSize = 包行体积（role=archive.size_bytes）
  · 界面「大小（大→小）」= **-imageSize**；「包大小（大→小）」= **-archiveSize**
  · 契约（shared/ipc.ts 的 sort enum）与实现（main/items-ipc.ts 的 SORT_COLUMNS）**逐字一致**，
    由 I12 **双向**核对：12 项全部 validateCall 通过 + 4 个野键（size/imageSizes/-archiveSizeBytes/bytes）必须被拒。

【2. NULL 位次（写明 + 断言钉住）】
  imageSize / archiveSize 来自 **LEFT JOIN** ⇒ **没有那一行的条目是 NULL**
  （最常见：**无包条目**的 archiveSize —— schema 上「缺包 = 少一行」，**不是 0 字节**）。
  实现用 SQLite 默认语义，并**写进 shared/ipc.ts 的契约注释与 items-ipc.ts 的 SORT_COLUMNS 注释**：
    · 正序（imageSize / archiveSize）：**NULL 排最前**；
    · 倒序（-imageSize / -archiveSize）：**NULL 排最后** ⇒ 界面「大→小」时无包条目落在末尾。
  为什么保留默认而不改成「永远 NULL 最后」：默认就是 SQLite 的确定语义，两端都可预测；
  改语义要多写 CASE，且没有证据说需要 —— 先不发明（要改请开卡，我会同步契约注释）。
  断言：I10 正序 ['a2','b2','c1','zz1',110,130,160] / 倒序 [160,130,110,'a2','b2','c1','zz1']；
        I11 含 NULL 时逐页拼起来与一次取完**同序同集合**；I10 另断言 **rows.length = 7**
        （无包条目不许被 INNER JOIN 丢掉）且 **archiveSize 是 null 而非 0**。
