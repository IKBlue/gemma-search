【怎么复跑（文件头也写了这一段）】
1) 构建产物（e2e 跑的是 out/）：
     npm run build
   ⚠️ 本会话沙箱下 build 必须把 TEMP/TMP 指到仓库内，否则 esbuild 清理 AppData 临时文件被拒（EPERM）：
     $env:TEMP='<仓库>/data/_esbuild-tmp'; $env:TMP=$env:TEMP; npm run build
   （同一个 TEMP 也是 e2e 能起窗的前提：Electron 的 userData/临时目录都落在 TEMP 下。）
2) 只跑这一条（默认不设 GEMMA_PERF ⇒ skip）：
     $env:GEMMA_PERF='1'; npx playwright test -c apps/desktop/e2e/playwright.config.mjs perf.spec.mjs
3) 读输出：结论表搜 '[perf] TABLE'，原始逐次计时/内存细节搜 '[perf] RAW'。

【取数方法（与 19.txt 完全同口径；文件头也有）】
· 冷启动分段：读**应用自己的日志** data/_app.log 的 HH:MM:SS.mmm 时间戳，每段 = 该行 − 首行。
  ⚠️ log.ts 每次启动**重写**该文件；playwright.config 是 workers:1 串行 ⇒ 读到的一定是本次启动
  （这也是为什么两个真窗口套件不能并行跑 —— 会互相盖证据）。
  **里程碑行名（写死在文件头注释里，改日志格式要同步改这几条正则）**：
    [..] === gemma-search 启动 ===                        ← 日志首行（约等于进程起）
    [..] app ready
    [..] 窗口已创建 → out/renderer/index.html
    [..] 引擎阶段完成
    [..] invoke indexStatus <n>ms → ok                     ← **库就绪**
    [..] 载入完成 <n>s · 请求=cpu · 实际=cpu · 已验证 EP=cpu    ← **编码器就绪**
  另给 harness 口径（launch() 返回 / 首窗口 / 主界面 #query 可见）并列；首行只是"进程起"的代理。
· 检索延迟：真窗口里逐次 win.evaluate(() => window.api.invoke('search', …)) + performance.now()，
  含 IPC + zod + 引擎（编码 + 3594×768 点积 + 排序）；首次（含模型载入）单独列。
· 内存：主进程 app.getAppMetrics() 的 workingSetSize / **peakWorkingSetSize**（进程生命周期峰值）；
  渲染 JS 堆用 performance.memory。
· 夹具：仓库内库根副本（data/_perf-<rand>/lib），.gs.db 走**生产导入代码**（T-11b 的 importItemsFromJson）；
  图像检索用一条真 1×1 JPEG 落在 items.json 的 relPath 上。

【这个文件**证明不了**什么 / **不测**什么（承自 19.txt，未变）】
· **不做阈值判定**：没有 SPEC 阈值（U14 待所有者定），所以它只测量。把它当门禁用会立刻误判（文本 53ms 与图像 1.5s 差 28 倍）。
· 非打包态（打包态冷启动留给 T-22）· 单库规模（3594 条）· CPU provider（**GPU/webgpu 分支未测**）·
  文件系统缓存是热的（**应用冷启动 ≠ 冷盘启动**）· 内存是**单次峰值，不是泄漏结论** ·
  图像检索用真 1×1 JPEG（**时延量级可用，不能据此评价检索质量**）· 未测并发/多库合并。
· 检索计时走 preload 桥 + IPC，**不含 React 渲染与 store 更新**（那是另一条口径）。
