【实现要点（为什么这么写）】
1) 实验性 API 隔离：只有 sqlite-adapter.ts 出现 'node:sqlite'。它把 DatabaseSync/StatementSync 收窄成
   SqlDatabase/SqlStatement/SqlValue（不含 undefined、不含普通对象——传错是编译期错误）。
   行值读取处做了 narrowValue：只认 null/number/bigint/string/Uint8Array，**认不出就抛**，不静默变 null。
   A1 用例机械扫 src/main/db/**，除 sqlite-adapter.ts 外出现 'node:sqlite' 或任何文件 import 'electron' 即失败。
2) schema_version 元表（单行 id=1，CHECK 约束钉在库里）+ 两条迁移：
   v1 core = library + items；v2 docs-and-health = doc_dirs + documents + doc_chunks + health_runs + health_ledger。
   拆分 v1/v2 是为了让"按序推进"**可测**（B3：先只跑 v1、再跑全量），也给了只碰文档表的改动一个落点。
3) 幂等：没有 version > current 时不执行任何 DDL、不报错；DDL 全带 IF NOT EXISTS（双保险）。
   版本只有 schema_version 一处真相来源，**不**同步 PRAGMA user_version（两个来源迟早对不上）。
4) 每条迁移一个事务（BEGIN IMMEDIATE…COMMIT）：SQLite 的 DDL 是事务性的 ⇒ 失败整条回滚，
   schema_version 停在上一条，不留"半张表 + 已记账"（B6 用一条故意写坏的 v3 证明 probe_partial 被回滚）。
5) 库版本高于程序所知 ⇒ SCHEMA_TOO_NEW（不降级瞎改，B5 实测）+ 迁移清单断代 ⇒ SCHEMA_GAP。
6) items 与 data/libraries/L1/items.json 的 18 字段对齐：字段↔列配对只在 row-types.ts 定义一次
   （ITEM_FIELD_COLUMNS），ITEM_FIELDS / ITEM_COLUMNS / itemRecordToSqlValues / ITEM_INSERT_SQL 全由它派生，
   不可能错位。可空性：archive* 六个 + vector_row + vector_source 可空（缺包是 SPEC §1.1 的合法状态），其余 10 个 NOT NULL。
7) 纯模块、可注入：db 层不 import electron、不读 app.getPath()/process.env 全局单例；
   dbPath 由调用方（T-04 storage-roots.resolveLibraryStorage().db）传入；驱动/迁移清单/时钟都可注入。
   唯一一处"顺手创建"是 dbPath 的父目录 recursive mkdir（T-04 已裁定"回退目录首次写入时按需创建"），
   只读打开时不建目录。**可写性判断与回退告警不在这层**（要求 ⑤）。
8) removeGsDbFiles 连 -wal/-shm/-journal 一起删。只删主文件不够：WAL 里可能有未 checkpoint 的事务，
   留着边车会让新库接着旧日志 —— 那是"删了但没真删"的静默错误（SPEC §2.1 的"删掉重建"靠它）。
