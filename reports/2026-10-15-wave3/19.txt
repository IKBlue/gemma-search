【测的环境（每条结论都只在这个环境下成立）】
· 硬件：11th Gen Intel Core i7-11700K @ 3.60GHz · 16 逻辑核 · 55.8 GB RAM · win32 x64。
· 模式：**真实模式**（GEMMA_FAKE 未设）· 设备 **CPU**（config.device=cpu；本轮**没有**测 webgpu/Vulkan）。
· 库：data/libraries/L1 的**仓库内副本**（3594 条 · 768 维 · 索引 11042105 字节）· 非打包态（跑 out/ 产物）。
· 模型：model-cache/onnx/embeddinggemma-2/daa72c…/fp32（meta.json 里的 revision）。
· 并发：测量前后确认**没有别的重活**（队友全部 inactive；测量前后各查一次进程表）。

【取数方法（别人可复跑）】
1) 冷启动分段：**读应用自己的日志** data/_app.log 的时间戳（log.ts 每次启动会重写该文件 ⇒ 一次一跑）。
   里程碑行（都能 grep 到）：
     [..] === gemma-search 启动 ===        ← 日志首行（≈ 进程起：导入 log.ts 即写）
     [..] app ready
     [..] 窗口已创建 → out\renderer\index.html   / 启动流程完成（窗口已创建）
     [..] 引擎阶段完成
     [..] invoke indexStatus <n>ms → ok     ← **库就绪**
     [..] 载入完成 1.8s · 请求=cpu · 实际=cpu · 已验证 EP=cpu   ← **编码器就绪**
   每段 = 该行时间戳 − 首行时间戳（HH:MM:SS.mmm 解析成毫秒）。
   ⚠️ 口径说明：首行只是"进程起"的**代理**（真实进程创建 → 日志首行之间还有 Electron 引导时间，测不到）；
      另一条 harness 口径（launch() 返回 / 首窗口 / #query 可见）用 performance.now() 量，两条都列在表里。
2) 检索延迟：真窗口里通过 preload 桥逐次调用
     await win.evaluate(() => window.api.invoke('search', { mode:'text', text:'坦克 装甲车', topK:50 }))
   计时含 **IPC + zod 校验 + 引擎（编码 + 3594×768 点积 + 排序）**；用 performance.now() 前后差。
   交叉核对：日志里同一次运行的 'invoke search <n>ms → ok' 条数 = 42（1 首次文本 + 20 文本 + 1 首次图像 + 20 图像），
   与应用日志逐条一致。
3) 内存：主进程 app.getAppMetrics()（Electron 自带 workingSetSize / **peakWorkingSetSize**）；
   渲染 JS 堆用 performance.memory。peak 是**进程生命周期峰值**，不是采样曲线。
4) 一次完整测量脚本：node data/_t19/perf.mjs（工作目录 data/_t19/work，跑完自动清理；本证据的两行就是两次运行）。

【解读（哪些是数字、哪些是解读，分开写）】
· 数字：**库就绪 < 1 秒**（682–769 ms）；**编码器在第一次检索时才载入**（自进程起 2730–2797 ms，其中模型 1.8s）——
  所以模型载入**不在启动路径上**（引擎侧是懒加载，见 buildEngine 的注释）。
· 数字：文本检索稳态 **P50 ≈ 51–53 ms · P95 ≈ 62–69 ms · max ≤ 78 ms**（含 IPC + 文本编码 + 3594×768 点积 + 排序）。
· 数字：图像检索稳态 **P50 ≈ 1.48 s**，是文本的 **≈28 倍**（视觉塔在 CPU 上跑）。
  解读：这在 CPU 上是**固有的模态差异**；它对 UX 有直接影响（转圈/取消/进度提示），也是 SPEC §7 阈值要分开写模态的原因。
  本轮**没有**测 GPU（device=cpu），所以不能据此判断 GPU 下的图像检索。
· 数字：主进程工作集峰值 **≈2.28–2.29 GiB**（ONNX fp32 双塔 + ORT 运行时 + 11 MB 索引 + Node）。
  解读：这是**单次运行的单点**，不是泄漏结论 —— 要断言"不泄漏"必须做多次载入/卸载或长时间运行，本轮没做。
· 数字：渲染进程 ≈103 MiB（JS 堆只用 9.5 MB），GPU 进程 ≈145 MiB，Utility ≈52 MiB。

【**不测**什么（写明留给谁）】
· **打包态**（安装包 / asar / 程序目录 models/）—— 留给 T-22；本轮跑的是 out/ + node_modules/electron。
· **别的库规模**（只测了 3594 条 · 768 维）—— 10 万级分块/多库合并的延迟不在本轮。
· **低端机 / 其他 CPU·GPU** —— 本轮只有这一台 i7-11700K + CPU provider。
· **GPU（webgpu/Vulkan）路径与 effectiveProvider 的 GPU 分支** —— 未测；日志里那条"设备决策"只覆盖 cpu 分支。
· **冷盘启动**（文件系统缓存是热的：本机刚跑过多次）—— 表里的冷启动是"应用冷启动"，不是"从冷盘启动"。
· **内存泄漏/长时间运行** —— 只做了单点峰值，没做重复载入或小时级运行。
· **缩略图协议的取图延迟**（real thumb:// 生成）—— 本轮没有单独计时（M0 那条 e2e 里能看到它工作）。
· **并发/多库合并检索**的时间 —— 单库单请求。

【环境说明（哪些是环境、哪些是产品）】
· 库根用**仓库内副本** data/_t19/...：本会话沙箱把 electron.exe 的写限制在仓库内（TASKS §5）。
  这是**环境限制**，对延迟量级的影响应当很小（同一块盘，且索引/条目都在本地），但严格说不是"用户的 G:\model"。
· 检索计时走的是 **preload 桥 + IPC**（renderer↔main），不含 React 渲染与 store 更新 ——
  它测的是"引擎+传输"，不是"用户看到结果"的端到端（后者可用 E2E 的观感数字，但那是另一条口径）。
· 图像检索用的素材是一条**真 1×1 JPEG**（编码路径完全真实：解码 → 预处理(seq=140) → 视觉塔 → 768 维），
  但图像内容不代表真实素材 ⇒ **时延量级可用，不能据此评价图像检索质量**。
· 每个进程都会打一条 "(node) ExperimentalWarning: SQLite …"（T-03 已判可接受，引用既有证据）。
