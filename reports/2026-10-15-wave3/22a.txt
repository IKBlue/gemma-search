     · directories.output: data/_t22/dist                 ← 落在我自己的写入范围内
     · win.signAndEditExecutable: false                   ← 见下面「环境限制②」

3) 跑：node data/_t22/run-packed.mjs / run-packed2.mjs / run-packed3.mjs
   （用 @playwright/test 的 _electron 启动**打包后的 exe**，env 指夹具库 + 真模型 + 仓库内 userData）

【Q1 · asar 下的仓库根解析（含日志落点与警告）】
结论：**ROOT 解成了 asar 路径**（不是 exe 目录、也不是什么"仓库根"），**asar 警告打了**；
      但**默认日志目标不可写，且失败被静默吞掉** ⇒ 不设 GEMMA_APP_LOG 时**一条日志都没有**。

原始输出（run 1，主进程事实）：
{ "isPackaged": true,
  "appPath": "...\\data\\_t22\\dist\\win-unpacked\\resources\\app.asar",
  "exePath": "...\\dist\\win-unpacked\\gemma-search.exe",
  "resourcesPath": "...\\dist\\win-unpacked\\resources",
  "execDir": "...\\dist\\win-unpacked" }
应用自己的日志（设了 GEMMA_APP_LOG=<仓库>/data/_t22/packed-app.log 才拿得到）：
  [07:44:39.285] 日志文件 = D:\...\data\_t22\packed-app.log
  [07:44:39.286] 应用根 = D:\...\dist\win-unpacked\resources\app.asar
  [07:44:39.286] !! 注意：应用根落在 asar 内（HERE=...\app.asar\out\main），data/ 无法写入 —— 打包态需要改用 userData（P6）
代码事实（log.ts:61/63/66/111/116-117）：
  ROOT = GEMMA_ROOT || detectRepoRoot(HERE) || FALLBACK_ROOT
  → 打包态的 app.asar **内**带着仓库根那份 package.json（它声明了 workspaces）⇒ detectRepoRoot 把 asar 认成了仓库根。
  LOG_FILE = <ROOT>/data/_app.log ⇒ 打包态 = <asar>/data/_app.log（asar 只读、且该目录不存在）
  mkdirSync / writeFileSync / appendFileSync **全在 try/catch 里静默失败**（那里是"日志写不了不是致命错误"的刻意设计）。

「静默丢失」的**正面实测**（run 2 的 B 段：**不设** GEMMA_APP_LOG）：
  B) 不设 GEMMA_APP_LOG 时应用**确实起来了** = {"ui":true,"apiKeys":["invoke","onEvent","platform"]}
  B) 仓库 data/_app.log mtime 变了没 = **false**（before=1791963422891.2205 after=1791963422891.2205）
  B) <asar>/data/_app.log 存在 = false
  ⇒ 应用正常运行、界面正常，但**没有任何日志留下**。这是打包态的**产品级问题**（P6 该修：默认落到 userData）。
附带一条正面的：PACKED=true 时 assertRootOnce() 会**跳过**"ROOT 可疑"的自检（log.ts:86），
  改由上面那条 asar 警告负责 —— 机制按设计工作，没有误报。

【Q5 · 真实取图（thumb://）在打包态】
结论：✅ **能取到**（界面真正的方式：img src=thumb://…）。@256 与 @512 都解码成功，主进程日志两条"生成成功"。
⚠️ 方法学纠正（值得记）：第一版我用 fetch('thumb://…') 测，得到的是
   "Failed to fetch" + 渲染层 CSP 报错 "Refused to connect because it violates the document's Content Security Policy"
   —— 那是**我的测法**撞了 connect-src（应用自己从来不 fetch thumb://，它用 img 标签）。
   换成 img 之后：@256 ⇒ {"ok":true,"naturalWidth":1,"naturalHeight":1}（素材是我落的真 1×1 JPEG）；
   @512 ⇒ 同上。main 日志：
     thumb 库 id 映射 [["l1","L1"]]        ← Chromium 把 host 小写成 l1，主进程还原回 L1（大小写不是问题）
     thumb 请求 L1 8a70380a9575 256 → 缓存未命中：ENOENT ⇒ 重新生成 → thumb 生成成功 … 256 1x1→1x1 285
     thumb 请求 L1 8a70380a9575 512 → 同上 → 生成成功 … 512
   ⇒ thumb:// 协议、白名单、缓存、缩略图生成在**打包态**逐条可用。
