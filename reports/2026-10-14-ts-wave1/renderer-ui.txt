3. 类型化时真踩到的三个坑（都靠控制流解决，没有用断言换绿灯）
================================================================
3.1 CSS 副作用 import 与 import.meta.glob 没有类型（TS2882 / TS2339）
    前者：`import './renderer.css'`；后者：Vite 的 `import.meta.glob`。
    ⇒ 在 `global.d.ts` 里声明两者（类型与真实实现一一对应）。
    ⚠️ 没有选「改 tsconfig 关掉这条检查」：根配置归 Lead，且关检查等于把门禁调松。

3.2 store 的类型比真实数据**窄**（LibStatus 缺 root/compat、LibraryConfigData 缺 registryPath）
    这两个字段主进程一直在给（界面一直在读），只是上一版类型没声明。转 TSX 后 TS 把它们当错误。
    ⇒ 在 Operation 层**补声明**（不是新契约）：类型不得比真实数据窄，否则会逼调用点写断言。

3.3 ItemPage 的 `item` 收窄：三元链里 TS 收窄不了 `data.item`
    `item` 来自 `const item = data.item`，在同一个 return 的三元链里，TS **不会**把 `item` 收窄成非空
    ⇒ 下面 20+ 个 `item.x` 全报 TS18047。
    ⇒ 解法是**控制流**：把三个「不渲染主体」的条件提成早返回（loading / error / item === null），
      三块 JSX 与原实现**逐字相同**，只是从三元链里提出来。
    ⚠️ 试过的错误解法（记下来免得后人重踩）：① `item!`/`as` 断言 —— 属于换绿灯，禁止；
      ② `let item` —— 会失去 const 收窄，反而更糟。

3.4 unknown 字段的渲染：一律 narrow 后再显示
    store 的 `deviceFallback` / `resumeNote` / `outcome.error` / `failure.error` 都是 `unknown`。
    ⇒ 写了 `text()` / `fallbackFrom|To|Reason()` / `outcomeErrorText()` / `asFailed()` 这类**显式窄化**，
      并把「引擎没给」如实写出来 —— 不用 `String(x)` 把 undefined 变成字面量 'undefined' 弹给用户
      （那正是 Apple Style 审查 V-42 的成因，`hooks/useToast.ts` 的注释里记着）。
