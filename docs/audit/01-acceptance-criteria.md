> 由 Lead 冻结；执行者若认为某条不合理，**先提出来改本文件，不要在报告里另立标准**。

## 2. 通用质量门（三份报告都必须过）

| # | 门 | 判据 | 怎么验 |
|---|---|---|---|
| G1 | **不声称未验证的能力** | 每个「已验证」结论都能追溯到 `文件:行号` 或命令+输出 | 抽查 5 条 |
| G2 | **区分三类事实** | 每条结论明确标记：`代码事实` / `文档声称` / `行业做法`；无证据的判断标 `【判断，非实测】` | 通读 |
| G3 | **与基线零冲突** | 任何与 `00-current-state.md` 相反的说法必须附新证据 | 交叉比对 |
| G4 | **严重度可复算** | 每条问题按 §3 公式给分，不得只写「高/中/低」 | 抽 3 条复算 |
| G5 | **有可执行建议** | 每条问题给出「改哪里 + 怎么验」，不写「建议优化」这类空话 | 通读 |
| G6 | **诚实列未覆盖** | 报告末尾必须有「本轮未覆盖 / 无法验证」一节 | 存在性检查 |
| G7 | **中文** | 与本仓库既有文档一致 | 通读 |

## 3. 严重度口径（冻结，两份报告必须一致）

`Score = 影响面(1-3) × 触发可能性(1-3)`，再映射等级：

| Score | 等级 | 含义 | 处置期望 |
|---|---|---|---|
| 9 | **Critical** | 会导致数据损坏、安全边界失效、或功能静默失败且用户无感 | 必须立刻修，阻塞发布 |
| 6 | **High** | 功能不可用 / 明显偏离行业基线 / 用户可感知的错误行为 | 发布前修 |
| 4 | **Medium** | 有替代路径的缺陷 / 明显技术债 / 一致性偏差 | 排期修 |
| 1-3 | **Low** | 措辞、命名、文档细节 | 顺手修 |

**必须给分的强制项**（不得降级）：

- 安全边界（`SPEC-security.md` 声称的不变量）失效 → 至少 High；导致可读写任意文件 → Critical
- 「实现了但用户无从触碰」（死功能）→ 至少 Medium，且必须记录「用户实际会看到什么」
- 「文档说做了、代码没做」→ 至少 Medium；若影响用户可执行的操作路径 → High

## 4. ① 技术栈/框架审计：专项判据

除 §2 通用门外，必须**逐条回答**下列问题（缺一项即未完成）：

| # | 必答问题 |
|---|---|
| S1 | 分层（`core/` 零依赖 ↔ `src/` 外壳）是否达到同类项目水准？拿**具体项目**对比，不写「主流做法」 |
| S2 | `core/` 的「零依赖」是否**真的可执行验证**？有没有守卫脚本？守卫本身可靠吗？ |
| S3 | 构建链（electron-vite 三端 + external 策略 + preload 强制 CJS）是否正确？有无更优解？ |
| S4 | **规格承诺栈（TS + Tailwind + shadcn/ui）vs 实际栈（JS + 手写 CSS + 自研 ui）**：分别评判。给出「保持」或「迁移」的明确建议 + 代价估计 |
| S5 | 依赖选型逐个判断：zod / sharp / @huggingface/transformers / bmp-js / zustand / @tanstack/react-virtual / Radix（**装了但一个都没用**）有哪些是无用依赖？ |
| S6 | 测试策略：68 测覆盖了什么、**漏了什么**（尤其 Electron 主进程 / preload / IPC 三层是否有测试） |
| S7 | 打包与分发（`electron-builder.yml`）是否达到「分发到别的机器」的要求？模型/索引的处置是否合规？ |
| S8 | 索引格式与检索算法（3594×768 暴力余弦 + `index.bin` 自定义二进制）在此规模是否合理？何时需要换向量库？ |
| S9 | 是否有**未被任何门禁覆盖**的风险区（列清单） |
| S10 | 已发现的具体缺陷（至少覆盖基线 §5 的 D1-D6，并自行发现新问题） |

## 5. ② UI/UX 审计：专项判据

除 §2 通用门外，必须**逐条回答**：

| # | 必答问题 |
|---|---|
| U1 | 对标基准必须**指名具体文档与条目**（如 Apple HIG 的 Layout / Materials / Typography / Motion 章节，或 macOS 具体控件规范），不得只写「Apple 风格」 |
| U2 | 设计令牌体系（`static/prototype/tokens.css`）是否自洽？与 Apple 官方数值（SF 字号阶梯、8pt 栅格、44pt 触控、圆角）**逐项对差** |
| U3 | 颜色：`--color-bg-secondary: #f5f5f7` / `--color-accent: #0071e3` 等是否与 Apple 实际值一致？**深色模式是否缺失**？ |
| U4 | 字体：`-apple-system` 在 **Windows 上落到什么**？本产品的主力平台是 Windows（`npm run build:win`）——这个落差怎么补？ |
| U5 | 交互完整性：键盘可达性、焦点可见、`aria-*`、空态/错误态/载入态、触达目标尺寸 |
| U6 | 现有实现（`src/renderer/`，仅「语义搜索」一页 + 10 个自研 ui 组件）与**原型**（`static/prototype/` 6 页）的差距清单 |
| U7 | 动效与反馈（`DESIGN-app-details.md` 如有规定）：`prefers-reduced-motion` 是否处理？ |
| U8 | 与 `docs/design/UI-REVIEW-and-migration.md`（自称「UI 以它为准」）的偏差：**是 UI 偏离了该文档，还是该文档已过期**？ |
| U9 | 逐页给出「Apple 风格符合度」评级 + 具体差距；**不得用主观形容词替代证据**（如「不够精致」必须写成「X 处用了 Y，HIG 要求 Z」） |
| U10 | 可执行的改进清单，按严重度排序，每条含「改哪个文件 + 验收怎么看」 |

## 7. 独立复核（不得由作者自评）

| 项 | 规则 |
|---|---|
| 复核者 | 由 Lead 指定的**独立** Agent，**不参与**被复核报告的写作 |
| 复核产物 | `docs/audit/REVIEW-<report>.md`，含：`verdict`（pass / pass-with-issues / fail）、`blockers[]`、`spot_checks[]`（复核者**自己跑命令**得到的输出） |
| 复核必做 | ① 随机抽 5 条结论回原文件/原命令验证；② 复算 3 条严重度；③ 检查 G1-G7 逐门；④ 主动**反驳**：找至少 2 处「报告说 A，磁盘其实是 B」或「结论过强」 |
| 通过条件 | `verdict = pass` 或 `pass-with-issues` 且 blockers 已被作者处置并回写 |
| 复核失败 | 作者必须修正后重新提交复核，**不得 Lead 直接放行** |

---

## 8. 完成定义（DoD）

一份报告算「做完」当且仅当：

1. 文件存在于 §1 规定位置
2. §4/§5/§6 的必答问题**逐条有答案**（不允许「不适用」除非给出理由）
3. §2 的 G1-G7 全部自检通过并在报告中附自检表
4. 已通过 §7 独立复核，blockers 已清零
5. 未修改任何他人 write-scope 内的文件
