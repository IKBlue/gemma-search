# UI 评审与迁移方案

> 评审对象：`D:\Qwen\models\Sa2VA-1B\gemma-search-ui-prototype.html`（28.3 KB / 120 行 / 5 页面）
> 结论：**保留视觉语言与信息架构骨架，但必须按"素材库"领域重构，并补两个关键流程。**
> 技术选型：**同意你的方案，另加 5 项**（见 §4）。

---

## 1. 总体结论

| 维度 | 评价 |
|---|---|
| 视觉方向 | ✅ **保留**。深色侧栏 + 浅色工作区、紧凑卡片、鲜明的索引状态提示——与"专业本地工具"的定位一致 |
| 布局骨架 | ✅ **保留**。侧栏导航 + 面包屑 + page-head(eyebrow/h1/subtitle) + 面板 + 结果区 + 底部状态条 |
| 离线可用性 | ✅ **保留**。无任何外部引用；缩略图用 **纯 CSS 画**（8 个 scene），不依赖图片文件——这个做法很聪明 |
| 可访问性底子 | ✅ 保留。`aria-label`/`aria-pressed`/`role=status aria-live`/`:focus-visible` 都有 |
| **领域适配** | ❌ **必须重做**。它是通用照片管理器，不是素材库（§3 列 9 条差异） |
| **关键流程完整度** | ❌ 缺 2 个：**图片详情**、**文件操作确认**；**索引任务**与**操作记录**只是占位（§2 逐页） |
| 代码可迁移性 | ⚠️ 原型级，有 2 处需在 React 化时改掉（§2.6） |

**一句话**：把它的**皮和骨**留下（视觉 + 侧栏式 IA），把**内脏**换成我们的（素材/压缩包/多库/事务）。

## 2. 逐页评审

### 2.1 语义搜索（`page-search`）——骨架最好，领域最偏

**保留**：page-head → search-panel（输入 + 快捷筛选 chip + 排序）→ **4 张指标卡** → results-head（计数 + 网格/列表切换）→ gallery → 底部状态条（含耗时）。
这个层次是对的，指标卡放在搜索框下方也合理。

**必须改**：

| 现在 | 应改为 | 原因 |
|---|---|---|
| 筛选 chip：人物 / 自然风景 / 建筑 | **全部 / 未分类 / VR / CR / CR+VR / 其他** | 我们的领域维度是渲染器，不是内容类别 |
| 卡片显示 `3840 × 2560`、`相关度 0.98` | 显示 **`ID-713717.zip` · 2.3 MB · 相关度 0.9396** | 素材的价值在**取包**；尺寸对建模无用 |
| `98% 匹配` | **`0.9396` + 区间标签**（同款区间/同类区间） | 我们的分数是余弦相似度，实测区间有明确语义（图→图 ≥0.88 为同款；文本→图 0.74~0.80） |
| 卡片标签 `风景 · 山湖` | **分类徽标**（VR/CR/CR+VR/其他）+ **库徽标**（多库时） | 分类是取包时的关键判断 |
| 底部"耗时 0.18 秒（原型展示值）" | 保留位置，改为**真实 P50** | 我们的性能验收有明确口径 |
| 4 张指标卡：图库图片/已索引/索引状态/本地隐私 | **图库 3594 · 已索引 3594 · 索引状态 · 模型与设备**（含 CPU 回退提示） | 加"模型/设备"是因为 CPU 回退会让图像编码慢 3 倍，必须可见 |

**卡片操作（原型完全没有）**：悬停或选中后应出现 —— **定位**（资源管理器选中包）、**取件**（复制到 `E:\素材待用\`）、**更多▾**（CRUD 菜单）。

### 2.2 本地图库（`page-library`）——太薄，只够当一行摘要

现在只有一张卡片（路径 + 数量 + 进度条 + "查看详情"）。**需要扩展成"库注册表"**：
每个库一行：名称 / 根目录 / 素材数 / **索引一致性**（`compat`）/ 上次扫描 / **库指纹状态** / 动作（重命名、**重新指向**、扫描、重建索引、**移除**）。
顶部要有"**可合并检索 N 个库 · 被排除 M 个（原因）**"的一致性横幅。

> 这一页对应 SPEC-identity §6.3 与 DESIGN §7.7，是**多库**功能的主界面。

### 2.3 索引任务（`page-index`）——**只有一行进度条，远远不够**

原型的作者自己标注了"正式版建议显示：阶段、已处理/总数、预计剩余时间、失败项、取消与重试操作"。**这些正是我们审核里要求的**，必须全部落地：

| 必须有 | 依据 |
|---|---|
| 阶段（扫描 → 配对 → 编码 → 校验 → 落盘） | 让"卡住"可定位 |
| `已处理 / 总数` + `条/秒` + `预计剩余` | 我们实测 2.41 条/秒，可给出可信 ETA |
| **失败项列表**（哪条、为什么） | 实测本库有 **105 张扩展名与内容不符**、20 张 BMP 伪装的 `.jpg`——必然有失败项 |
| **取消**（只在状态边界生效） | SPEC-transactions §5 |
| **可续跑**（中断后复用已完成项） | 构建器已实现，界面要显示"本次复用 N 条" |
| **覆盖/一致性**：本次用的 `model_revision / 权重精度 / 预处理版本 / seq` | SPEC-identity §6.2，避免"建完了却不知道建的是哪套" |
| 期间的检索状态提示 | 建索引抢占 GPU，检索应禁用并说明原因 |

### 2.4 操作记录（`page-activity`）——缺少**撤销状态**，这是本应用的安全底线

现在只有 3 条纯文本。必须升级为**事务表**：

| 列 | 说明 |
|---|---|
| 时间 / 操作类型 | 入库、改目录、改 ID、替换预览图、移出库、撤销 |
| 对象 | **uid** + 文件名 + 库 |
| 前后路径 | 让"发生了什么"可核对 |
| **状态** | `已提交 / 已回退 / **待处理（RECOVERY_NEEDED）**` |
| **撤销** | 可撤销的给按钮；已过保留期的明确标注"不可再撤销"并说明原因 |
| 关联事务 | 点开看该事务的文件清单与校验值 |

> 关键：**"待处理"必须显眼**。启动时若有未完成事务，这一页要有红点，并且提供"重试 / 回退 / 保持现状"三条路（SPEC-transactions §4）。

### 2.5 设置（`page-settings`）——方向对，选项要对齐我们的决策

原型有：模型状态、CPU/GPU、启动检查变更、变更前确认。**保留这四项**（"文件变更前显示确认"尤其正确），补充：

- **模型**：repo + **revision（钉住）** + **权重精度**（fp32/fp16/q4f16）+ **预处理版本** + seq —— 切换任一项都提示"**需重建索引**（约 25 分钟）"
- **索引存放位置**：应用数据目录（默认）
- **取件目录**：默认 `E:\素材待用\`
- **撤销保留**：天数 / 容量上限 / 当前占用
- **缩略图缓存**：位置与占用
- **隐私**：明确"离线可用、绝不外传"——原型的"本地隐私"卡片可以搬到这里

### 2.6 ❌ **缺失的两个关键流程**（你自己也点名了，我完全同意）

**A. 图片详情页（`page-detail`）—— 原型完全没有**

这是"看清楚了再动手"的地方。内容：

```
┌ 大图（可缩放） ────────────────┐  ID-595812826
│                                │  分类：VR      库：室内素材
│                                │  预览图：G:\model\VR\ID-595812826.jpg
│                                │         1 788 × 1 800 · 334 KB · 2026-10-05
│                                │  压缩包：G:\model\VR\ID-595812826.rar
└────────────────────────────────┘         18.2 MB · 2026-10-05
   索引：已编码 · 向量行 1234 · 余弦自检 0.9999
   数据源：[以图搜同款]  [按 ID 查同族]
   取件：[在资源管理器定位]  [复制到 待用素材]  [复制包路径]
   维护：[改归档目录]  [改 ID]  [修正配对]  [替换预览图]  [移出库]
   危险区：移出库（可还原，30 天内）
```

**B. 文件操作确认弹窗 —— 原型只有 toast，没有确认**

这是本应用**误操作风险的控制点**。规格（来自 SPEC-transactions）：

```
┌ 将移出库？ ─────────────────────────────────────────┐
│ 这条素材将从库中移到：                                │
│   E:\移出素材\室内素材\20261010-131500\               │
│                                                      │
│ 将移动 2 个文件：                                     │
│   图  ID-595812826.jpg   334 KB                      │
│   包  ID-595812826.rar   18.2 MB                     │
│                                                      │
│ ✓ 可还原（保留 30 天）   ✓ 会写入操作记录              │
│ ⚠ 目标卷可用 484 GB，本次需要 18.5 MB                 │
│                                                      │
│                      [取消]  [确认移出]               │
└──────────────────────────────────────────────────────┘
```

**统一原则**：**确认框必须列出"将要发生的确切变更"**（源→目标、文件数、体积、是否可撤销），
**不含糊说"确定要执行吗？"**。这与界面里"预检"是同一份数据。

### 2.7 实现层面的两处问题（React 化时顺手改掉）

| 问题 | 说明 | 改法 |
|---|---|---|
| `setView()` 直接写 `style.gridTemplateColumns` | 内联样式**优先级高于媒体查询** → 窗口缩到 <780px 时网格/列表切换会与响应式断点打架 | 改成切 class（`data-view="list"`），样式交给 CSS/Tailwind |

其余（`Inter` 字体未打包、图标用 Unicode 字符）无害，正式版按 §4 处理即可。

## 3. 领域差异清单（通用图片管理器 → 素材库）

| # | 原型假设 | 我们的实际 | 影响 |
|---|---|---|---|
| 1 | 一个"图库"，一张卡片 | **多库 + 注册表 + 一致性校验** | 需 `page-library` 重做 + 顶栏库选择器 |
| 2 | 图片就是终点 | **每张图配一个同名压缩包**，包才是产物 | 卡片与详情必须显示包名/体积/取件 |
| 3 | 按内容分类（人物/风景/建筑） | 按**渲染器分类**（VR/CR/CR+VR/其他/**未分类**） | 筛选 chip 全换 |
| 4 | 尺寸（3840×2560）是重要信息 | **无关紧要**；要的是包体积、ID、日期 | 卡片信息重排 |
| 5 | 相似度 `98%` | **余弦 0.74~0.94**，且分区间有意义 | 分数显示与解释方式不同 |
| 6 | 无写入操作 | **可写库**：入库、改目录、改 ID、替换图、移出库 | 需要 CRUD 菜单 + 确认弹窗 + 事务状态 |
| 7 | 无"操作可恢复"概念 | **事务 + 审计 + 撤销 + RECOVERY_NEEDED** | `page-activity` 重做 |
| 8 | 索引只是进度条 | 索引有**精度/预处理/revision 绑定**与**失败项** | `page-index` 必须展示元数据 |
| 9 | 无健康度概念 | **图无包 / 包无图 / 扩展名与内容不符（实测 105 张）/ 重复内容（实测 5 组）** | 需要一个"库健康"面板 |

## 4. 技术选型：同意，另加 5 项

你的方案我全部同意。补充的是**我们这个项目特有的刚需**：

| 增补 | 为什么需要（不是"更先进"，是缺了会出问题） |
|---|---|
| **`zod` + 共享类型包** | 审核 P1 明确要求"**IPC 参数白名单校验**"。用 Zod 在 preload/引擎入口**运行时校验**，同时导出 TS 类型给渲染进程——一套定义两处受益，避免"类型说没问题、运行时崩了" |
| **`electron-vite`**（Vite + Electron 集成） | 主进程/预加载/渲染进程三端 HMR 与构建一体；比手搓 Rollup 配置省事，且产物可直接喂给 electron-builder |
| **`@tanstack/react-virtual`** | 搜索结果（Top-K ≤ 100）**不需要**虚拟列表；但**浏览整库 3594 条**时必须要——这是两件不同的事，不要为了搜索去上虚拟化 |
| **`vitest`** | 引擎（`core/engine.mjs` → TS）与事务状态机需要**快速单测**。这是"无头自测"思路在 TS 侧的等价物，不引入 CI |
| **自托管字体或纯系统字体** | 原型写了 `Inter` 但没打包。离线要求下要么自托管，要么就用系统字体栈（`Segoe UI`/`PingFang SC`/`Microsoft YaHei`）——**别偷偷回退到联网 CDN** |

**另外两点判断**：

- **不需要数据请求库**（TanStack Query / SWR）。索引进度是**IPC 事件流**（推送），不是轮询请求；UI 状态用 `zustand` 足矣。上 Query 只会多一层缓存语义。
- **`Radix UI` 的价值不只是样式**：`AlertDialog` / `Dialog` / `Popover` / `Toast` 正好覆盖我们要的**确认弹窗 / 详情抽屉 / CRUD 菜单 / 提示**，且焦点管理、ESC 关闭、`aria-*` 都是现成的——这正是 §2.6-B 需要的东西。选 shadcn/ui（把 Radix 封装成可改的源码）比用 Ant Design 更适配"有品牌感的工具"。

## 6. 四个关键流程的界面规格（**先做这四个，别先做动画**）

### 流程 1：搜索结果
- 触发：Enter / 点搜索 / 拖入图片 / `Ctrl+V` 粘图
- 分层：输入 → 筛选（分类 chip）→ 排序（相关度/文件名/最近/体积）→ 结果网格
- 卡片：缩略图 · **分数 + 区间标签** · 分类徽标 · 库徽标 · **包名 + 体积** · 悬停出「定位 / 取件 / 更多▾」
- 状态：搜索中（骨架屏）· 无结果（给可操作建议，如"换词/去掉筛选"）· **索引不完整**（明确告知只有前 N 条可检索）
- 键盘：`↑↓←→` 选 · `Enter` 定位 · `Ctrl+C` 复制包路径 · `Esc` 清空 · `空格` 预览

### 流程 2：图片详情
- 左侧大图（可缩放/适应窗口）；右侧元数据（ID/分类/库/两条绝对路径/尺寸/体积/日期/索引状态/向量行）
- 动作分区：**取件** / **维护（复用向量）** / **维护（需重编码，须提示）** / **危险区**
- 关键：把"**是否需要重编码**"直接标在按钮上（改目录/改ID 不重编码；换图/外部变更 要重编码）——这是本应用独有的判断，别让人猜
- 相关：疑似的**同内容素材**（实测 5 组）在此互相链接

### 流程 3：索引任务
- 阶段条（扫描 → 配对 → 编码 → 校验 → 落盘）+ `已处理/总数` + `条/秒` + `ETA`
- 头部显示本次的 **model_revision / 权重精度 / 预处理版本 / seq**
- 失败项**可展开**（哪条、为什么、能否跳过）；**取消**按钮标注"将在当前批次结束后停止"
- 完成后显示 **`复用 N · 新编码 M · 失败 K`** 与"数据正确性三项验收"的结果

### 流程 4：文件操作确认
- 统一模板（§2.6-B）：**确切变更清单 + 可撤销性 + 空间核算 + 二次确认**
- 危险操作（移出库）用 Radix `AlertDialog`，按钮文案写动词（"确认移出"）而不是"确定"
- 写操作进行中：卡片显示**进行中**且禁用重复触发
- 失败/中断：进入「操作记录」的**待处理**，并给"重试 / 回退 / 保持现状"

## 7. 迁移路线（对 P2/P3 的调整）

| 原计划 | 调整 |
|---|---|
| P2 Electron 骨架（含 `thumb://`、preload 白名单） | **不变**，另加：`electron-vite` 工程化 + `zod` IPC 契约 |
| P3 界面（检索） | 拆成 **P3a 设计系统落地**（Tailwind + shadcn/ui 基础组件 + 深色侧栏壳 + 路由）→ **P3b 流程 1 搜索结果** → **P3c 流程 2 图片详情** |
| P4 入库与增量 | 界面对应**新的两个侧栏入口**；实现流程 4 的确认弹窗（先于 CRUD 落地） |
| P5 多库 | 界面对应 `page-library` 重做 + 顶栏库选择器 + `compat` 标灰 |
| — | **新增 P3d**：`page-index` 与 `page-activity` 按 §2.3/§2.4 补齐（失败项、取消、续跑、事务状态、撤销） |

**顺序建议**：先做**流程 1**（能立刻用上已有索引），再做**流程 2 + 4**（读→写，风险从低到高），最后**流程 3**（最重但可在后台跑）。

**验收**（沿用 SPEC-acceptance 的口径）
- 流程 1：缩略图零 404；文本查询 P50 ≤ 80 ms；图像查询 P50 ≤ 1.0 s；键盘全通
- 流程 2：能显示两条绝对路径与索引状态；"需重编码"标注正确
- 流程 4：确认框列出的变更清单与事务日志**逐字段一致**（这是可测的：把弹窗数据与 journal 比对）
- 流程 3：进度可信（ETA 误差 < 30%）、取消在边界生效、失败项可解释

### 8.2 一处需要你定的冲突：侧栏深浅

令牌 §2.1 把「**侧栏**」归到 `color.bg.secondary` —— 浅色模式下那是 **`#f5f5f7`（浅色侧栏）**；
而你先前两次明确说过「**深色侧边栏**」，三页原型的侧栏也是 `#171923`。

处置：**默认按令牌**（浅色模式浅侧栏、深色模式深侧栏），同时把深色侧栏做成**一个属性开关**
（值取自令牌的深色档，不是新造的颜色）：

```html
<html data-sidebar="dark">   <!-- 固定深色侧栏 -->
```

**要哪种，一句话即可切**（见 `TASK-PLAN.md` §8 决策 4）。

### 8.3 实现约定

- 加载顺序必须是 **`style.css` → `tokens.css` → `app.css`**（令牌覆盖调色板，组件最后）
- **组件里不写十六进制**；派生色一律 `color-mix()`，这样「改一个令牌 = 全局一致」
- 分类徽标（VR / CR / CR+VR / 其他 / 未分类）与分数区间是**本项目新增令牌**，
  已在 `tokens.css` 登记并标注来源（令牌 §12 要求）

## 9. 我不建议做的（对应「不要急着做复杂动画」）

- ❌ 卡片悬停位移/阴影动画做到极致（原型有 `translateY(-2px)`，够了）
- ❌ 图表（Recharts 等）——本期无数据可视化需求
- ❌ 双主题同时做——先只做"深色侧栏 + 浅色工作区"，主题切换放后续设置项
- ❌ 数据请求库、状态机库、表单库——IPC 事件流 + zustand + 受控表单足够
- ❌ 为了搜索结果上虚拟列表——Top-K ≤ 100 不需要；**只有浏览整库才要**
