## 一、UI 怎么设计

> **本节已按 UI 评审升级**：目标信息架构、逐页评审、四个关键流程的界面规格、以及从原型迁移的差异清单，
> 都在 **`docs/design/UI-REVIEW-and-migration.md`**。此处保留核心结论。

**目标信息架构（侧栏 7 项 + 1 个详情页）**

```
语义搜索 · 本地图库 · 入库 · 增量 · 索引任务 · 操作记录 · 设置
（图片详情从结果进入，不占侧栏）
```

**必做的四个关键流程**（先做这四个，不先做动画）：

| 流程 | 要点 |
|---|---|
| **1 搜索结果** | 分数 + **区间标签** · 分类徽标 · **包名与体积** · 悬停出「定位 / 取件 / 更多▾」· 键盘全通 |
| **2 图片详情** | 大图 + 元数据（两条绝对路径、索引状态）· 动作按 **"是否需重编码"** 分区标注 |
| **3 索引任务** | 阶段条 + `已处理/总数` + ETA + **失败项可展开** + 取消（边界生效）+ 续跑 + **本次用的 revision/精度/预处理/seq** |
| **4 文件操作确认** | **列出确切变更清单**（源→目标、文件数、体积） + 可撤销性 + 空间核算；**不说"确定要执行吗？"** |

### 1.1 定位

**这是一个"查东西"的工具，不是素材管理系统。** 因此：**单屏、零导航、搜索框最大、结果网格为主角**。不做的：左侧树、标签体系、收藏夹、批量重命名、云端同步。

### 1.2 布局（单屏三段）

```

│  gemma-search                                    [⚙ 设置]            │  ← 顶栏

│  │ 描述你要找的东西…（中文即可）               │  │ 搜索  │ │ 图搜 │ │
│  └────────────────────────────────────────────┘  └───────┘ └──────┘ │
│  分类 (全部) VR CR CR+VR 其他        返回 24 ▾      [拖入或粘贴图片]  │
├──────────────────────────────────────────────────────────────────────┤
│  ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐             │
│  │  图    │ │  图    │ │  图    │ │  图    │ │  图    │             │
│  │ 0.940  │ │ 0.938  │ │ 0.936  │ │ 0.935  │ │ 0.930  │             │
```

### 1.3 每条结果的卡片

| 元素 | 内容 |
|---|---|
| 图 | 预览图（原图直出，不生成缩略图——库里的图本就 30~600 KB） |
| 分数 | 保留 3 位小数；**并排显示区间提示**（"同款区间"/"同类区间"/"较弱"），因为分数是唯一诚实的信号 |
| 分类徽标 | VR / CR / CR+VR / 其他（着色区分） |
| 包名 + 包大小 | `ID-713717.zip` · 2.3 MB |
| 动作 | 悬停浮出：**定位** · **取件** · 更多▾ |

**更多▾ 菜单**：复制包路径 / 复制图路径 / **以此为图搜同款** / 在应用内大图查看

### 1.4 交互（键盘优先）

| 键 | 行为 |
|---|---|
| `Enter` | 执行搜索（输入框内） |
| `↑ ↓ ← →` | 在网格中移动选中项 |
| `Enter`（网格内） | 定位该条（资源管理器弹出） |
| `Ctrl+C` | 复制选中项的**包路径**（不是文件，便于粘贴到别处） |
| `Ctrl+Shift+C` | 取件（复制包到取件目录） |
| `Space` | 大图预览 |
| `Esc` | 清空/关闭 |

**拖放**：图片拖到窗口任意位置 → 直接以图搜图（整窗是投放区）。
**粘贴**：`Ctrl+V` 若剪贴板含图片 → 以图搜图。

### 1.5 三类"非正常状态"必须显式设计（否则用户只会看到白屏）

| 状态 | 界面表现 |
|---|---|
| **模型未下载** | 首启向导：「需要下载模型」+ 三档体积与取舍 + [下载]（见 §4） |
| **模型在下载中** | 顶部进度条：文件、已下/总量、速度、剩余时间、[暂停] |
| **索引缺失/不完整** | 状态栏红点 + 中央提示：「索引 1200/3594，只有已编码部分可被检索」+ [扫描更新] |
| **正在建索引** | 搜索框置灰 + 说明「正在建索引，为避免争用已暂停检索」 |

> ⚠️ **绝不**把"等待模型加载"做成白屏——冷启动 11 秒是真实的，必须有文字反馈。

### 1.6 技术形态（因为现在是单进程）

- 渲染进程 `nodeIntegration: false` / `contextIsolation: true`，能力经 `preload.js` 白名单暴露
- **不需要 HTTP 服务、不需要端口**：主进程用 `ipcMain.handle` 提供 `search-text` / `search-image` / `reveal` / `collect` / `index-status` 等
- **图片经自定义协议** `thumb://<itemId>`（`protocol.handle`）由主进程直接从 `G:\` 读并回写 `Cache-Control`；渲染进程**不接触文件系统**
- 大图与网格用同一协议，只是尺寸参数不同

## 二、素材库怎么管理

### 2.1 结构约定（现状，复用）

```
G:\model\                     ← 库根（本期固定）
├── VR\       ├── ID-713717.jpeg      预览图
│             └── ID-713717.zip       同名压缩包
├── CR\       ├── ID-16010618.png
│             └── ID-16010618.zip
├── CR+VR\    └── …
└── 其他\     └── …
```

**配对规则**：**同目录 + 同名主干**（不跨目录配对）。
图扩展名 `.jpg/.jpeg/.png`；**包扩展名 `.rar/.zip/.7z`** —— 三种都必须认：

| 类型 | .jpg | .jpeg | .png | .rar | .zip | **.7z** |
|---|---|---|---|---|---|---|
| 实测数量 | 2644 | 742 | 208 | 2329 | 1189 | **76** |

> ⚠️ **踩过的坑**：曾漏掉 `.7z`，于是把 76 条 `.7z` 素材误判成"图无包"，
> 还差点据此改掉原本正确的旧实现。**扩展名集合必须是共享常量，两侧一致。**

### 2.2 写入纪律（**已修订**：不再是"库只读"）

> 初版把库定成"只读"，**这一条已按用户要求推翻**：应用必须能**入库**（上传新素材）与**管增量**。
> 修订后的原则是"**写入有纪律**"而非"不写"：
>
> - 写入**只能**通过应用的入库流程（§六），不接受任意路径写
> - 每次写入前**预检**（目标路径、重名、ID 重复），写入后**记审计**
> - 任何写入都可**撤销**（至少支持"移出库"）
> - 扫描/检索等**只读操作绝不写库**；扫描前后仍拍"库指纹"作**护栏**，一旦发现非入库流程造成的改动就报警

对库的**只读操作**（检索、扫描、缩略图）依然：不写、不改名、不移、不删。

### 2.3 库健康面板（只读，纯统计）

| 指标 | 说明 |
|---|---|
| 预览图 / 压缩包 / 配对成功 | 如 3594 / 3594 / 3594 |
| **图无包** | 有预览图但缺同名压缩包 → 列出；**不删除、不补** |
| **包无图** | 有压缩包但缺预览图 → 列出 |
| **扩展名与内容不符** | 实测 105 张（`.png`实为JPEG 68、`.jpg`实为BMP 20、`.jpg`实为PNG 17）；仅提示，**不修** |
| 各分类数量与占用 | VR/CR/CR+VR/其他 |
| 上次扫描时间 / 库指纹哈希 | 便于判断是否需重扫 |

### 2.4 新增检测（增量）

判定"需要重新编码"的依据：`rel_path` 相同但 **size 或 mtime 变化**。
- 新增 → 编码
- 消失 → 从索引移除（**只在索引里移除，绝不删库文件**）
- 变化 → 重新编码该条

## 三、索引怎么创建

> **索引元数据的权威定义在 `docs/spec/SPEC-identity.md` §6、§7**（字段清单、`compat` 判定键、`index.bin` 格式）。
> 本节只讲「怎么建」，不重复字段定义。

### 3.1 存储格式（自定，不再依赖 Python 的 .npy）

```
data\
├── index.bin       ← 头部 JSON + float32 连续块（N × 768）
│                     头部: {version, dim, count, model_id, precision,
│                            prefix_policy, image_seq_length, built_at, library_root}
└── items.json      ← 每条元数据（含向量行号）
```

- 为什么不用 `.npy`：`.npy` 是 NumPy 格式，Node 侧要额外解析器。自定格式让**读写都无依赖**
- **迁移**：若 ONNX fp32 与 torch fp32 向量等价（见 §4.4 spike），写一次性转换脚本 npy → bin，并**逐条比对 3594 个向量**确认无损
- **体积**：3594 × 768 × 4 B = **11.0 MB**（无需量化）

### 3.2 每条元数据字段

```
id, folder, name, rel_path, abs_path,
image_ext, image_size, image_mtime,
archive_name, archive_rel_path, archive_abs_path, archive_ext, archive_size, archive_mtime,
vector_row
```

### 3.3 创建流程

```
扫描库  →  与现有索引 diff  →  只编码差异  →  原子落盘  →  校验
  │            │                    │            │           │
  │            │                    │            │           └ 维度/条数/范数
  │            │                    │            └ 写临时文件再 rename
  │            │                    └ 分批编码，可中断续跑
  │            └ 新增 / 变化 / 消失
  └ 同目录同名配 + 库指纹
```

**必须做对的四件事**：

1. **原子落盘**：写 `index.bin.tmp` → `fsync` → `rename`。崩溃也不会留下半截索引
2. **向量 L2 归一化后再存**：检索即点积，省一次开方；并便于校验（范数应 ≈ 1）
3. **索引绑定"产生它的模型与预处理"**：`model_id` / `precision` / `prefix_policy` / `image_seq_length` 全部记入头部。**任一不符即拒绝检索并提示重建**——这是防止"跨空间检索"（结果静默变差）的唯一手段
4. **可中断续跑**：每 `N` 条刷新一次落盘；重跑时按 §2.4 复用已完成项

### 3.4 进度与取消（图形界面）

- **独立 worker 线程**跑编码，主进程不卡，界面不冻结
- 进度 = `已编码 / 总数` + `条/秒` + 预计剩余
- 取消 = 批间检查标志位；已完成的批次**仍然落盘**，下次续跑
- **索引期间禁用检索**：给明确文字，不静默变慢（实测同时跑会让吞吐掉一半）
- 高级选项：**强制重建**（换了精度或改了预处理时必须用；平时不用）

### 3.5 校验

加载索引时检查：`count` 与 `items.json` 一致、`dim == 768`、所有向量范数 ∈ [0.99, 1.01]。
任一不过 → **拒绝检索**并提示重建，绝不用可疑索引出结果。

## 四、模型下载与管理怎么操作

> **权重精度 ≠ 向量精度的区别，以及 `compat` 判定，见 `docs/spec/SPEC-identity.md` §6。**
> 本节讲下载与缓存管理。

### 4.1 下什么（关键：**不下音频塔**）

`onnx-community/embeddinggemma-2-ONNX` 里音频塔占 **40%** 体积，而本应用**不需要音频**（Python 侧早就 `audio_config: None` 关掉了）。

| 档 | 文本塔 + 视觉塔 | 加 tokenizer | 定位 |
|---|---|---|---|
| **q4f16** | 242.7 MB | ~274 MB | **默认**（小、快） |
| fp16 | 837.0 MB | ~868 MB | 质量优先 |
| fp32 | 1673.8 MB | ~1.70 GB | **spike 对照用**；与现有索引同精度 |

必下文件（以 fp16 为例）：
```
onnx/model_fp16.onnx  + model_fp16.onnx_data
onnx/vision_encoder_fp16.onnx + vision_encoder_fp16.onnx_data
tokenizer.json  tokenizer_config.json  config.json
preprocessor_config.json  processor_config.json
```
**明确跳过**：`onnx/audio_encoder*`（全部精度档）

### 4.2 放哪里

```
D:\USERS\Desktop\Agent\model-cache\        ← 模型资产统一根
├── hf\            （现有，Python/torch 缓存 1.42 GB，保留不动）
└── onnx\          （新增）
    └── embeddinggemma-2\<revision>\<precision>\
         ├── model_fp16.onnx(+_data)
         ├── vision_encoder_fp16.onnx(+_data)
         ├── tokenizer.json …
         └── manifest.json    ← 见 §4.3
```

**放 D: 的理由**：C: 仅剩 19.7 GB（系统盘，不挤）；G: 仅剩 44.3 GB（素材库盘，不写）。

### 4.3 下载机制（自己实现，不用黑盒）

| 需求 | 做法 |
|---|---|
| 只下需要的文件 | 直接请求 HF 的 `resolve` 地址逐个下，不用整仓快照 |
| 断点续传 | HTTP `Range`；`manifest.json` 记录每个文件已完成的字节数 |
| 可暂停/取消 | 流式写入 + 中断即停，已完成文件不重下 |
| 进度 | 每文件 + 总体：已下/总量、速度、剩余时间 |
| 完整性 | 记录 size + sha256；启动时默认校验 size（快），**"深度校验"按需算 sha256** |
| **版本钉住** | `manifest.json` 记录 **repo + 完整 commit revision**；重下不得静默换成别的权重 |
| 离线 | 文件齐全即**永不联网**；「检查更新」默认关闭、需手动点 |
| 删除 | 设置页可删某个精度档并回收空间（显示各档占用） |

`manifest.json` 形态：
```json
{ "repo": "onnx-community/embeddinggemma-2-ONNX",
  "revision": "<commit-sha>",
  "precision": "fp16",
  "downloaded_at": "2026-10-10T…",
  "files": [ {"path":"onnx/model_fp16.onnx_data","size":542113792,"sha256":"…"} ] }
```

### 4.4 ⚠️ 铁律：**精度绑定索引**（这是最容易出错的地方）

量化编码器产出的向量与 fp32 **不在同一空间**。若索引用 fp32 建、查询用 q4f16 编码，分数会**整体偏移**——不报错，只是结果变差，属于最危险的失败模式。

**因此**：
- `index.bin` 头部记录 `precision`
- 启动时若「当前精度 ≠ 索引精度」→ **拒绝检索**，提示：重建索引，或切回该精度
- 设置页切换精度时，明确告知"需重建索引（约 N 分钟）"

### 4.5 必须先跑的 spike（决定整条路线）

在写应用前，用 **fp32** 做一次对照实验：

| 步骤 | 内容 |
|---|---|
| 1 | 下 fp32 的文本塔+视觉塔（1.70 GB，**不动现有 hf 缓存**） |
| 2 | 用 `@huggingface/transformers` 编码 **20 张库内图 + 5 句中文** |
| 3 | 与现有 `embeddings.npy` 中对应向量算余弦 |

| 余弦结果 | 结论 |
|---|---|
| **≥ 0.999** | 向量等价 → **直接复用现有索引**，Python 侧完全退役 |
| 0.95 ~ 0.999 | 需用 ONNX 重编码索引（一次性，CPU 较慢） |
| **< 0.95** | **放弃 ONNX 路线**，保留 Python 后端 |

同时**顺带量三件性能事实**（都会写进方案）：CPU 上单张图编码耗时、单句文本耗时、模型载入耗时。

## 六、上传（入库）与增量管理

> 这是**范围变更**：应用不只是查，还要能**把新素材收进库**并**管理数据增量**。
> 下面带 ❓ 的是需要你拍板的决策点；每个都给了我的推荐默认值。

### 6.1 上传（入库）流程

```
拖入 压缩包(.zip/.rar) + 预览图(.jpg/.png)
        │
        ▼
① 配对      按文件名主干配对"图 ↔ 包"；配不上的列出来，不静默丢弃
        │
        ▼
② 取 ID     从文件名提取 ID-<digits>；**提不到就停下来问你**，不擅自编号
        │
        ▼
③ 归档目录  **可选**。默认进 `未分类\`，你想分就选 VR/CR/CR+VR/其他
        │
        ▼
④ 预检      显示"将要写入的确切路径" + 重名 + ID 重复 + 体积；有问题就不许提交
        │
        ▼
⑤ 提交      写入 `G:\model\<目录>\` 并按约定规范化命名（已确认允许写库）
        │
        ▼
⑥ 增量索引  只编码新增条目，进度可见、可取消
        │
        ▼
⑦ 审计记录  何时/从哪/写成什么；支持"移出库"撤销
```

**① 配对规则**（与检索侧一致，复用同一份代码）
- 同一次拖入的若干文件里，按**主干名**配对；`ID-123.rar` ↔ `ID-123.jpg`
- 主干名不同但有唯一候选时，提示"是否配对？"，**不自动改你的文件名**
- 图缺包、包缺图 → 都列出来，**允许只入库其中一个**（库里本来就允许单边存在，健康面板会显示）

**③ 归档目录：不做自动分类（已定）**

自动分类要**读进压缩包内容**（列目录/解压后读 `.max` 的 Render Data），开销大；而且**不是每个用户都会分类**，
所以它**不该是入库的必经步骤**。设计如下：

- 默认写入 **`G:\model\未分类\`**（库中新增一个目录；扫描本来就容忍任意子目录名）
- 想分类就在下拉里选 VR / CR / CR+VR / 其他，**一次点击的事**
- 入库后仍可在「增量」视图里**改分类**（等于在目录间移动文件，走同一条审计）
- **应用完全不解析 `.zip`/`.rar` 内容** → 不必引入压缩库、不会因解开大包卡住、也没有解压路径安全风险
- 如果以后想要"从文件名猜"（如包名含 `corona` 就预选 CR），那是**纯字符串判断、零开销**，可作为后续小改进——**本期不做**

### 6.2 增量管理

回答"**库里发生了什么、索引跟没跟上**"：

| 区块 | 内容 |
|---|---|
| **待入库队列** | 已配对、尚未提交的项（可取消、可改分类/ID） |
| **本次增量** | **新增 / 变更 / 消失** 三类，逐条带缩略图与路径；每类可展开 |
| **索引状态** | 每条标"已编码 / 待编码 / 待重编码 / 已从索引移除" |
| **批量动作** | 提交索引（编码新增）、重新编码（对变更）、移出库（对新增）、忽略 |
| **库指纹** | 上次扫描的 文件数 + mtime 摘要；不一致时红字报警（区分"入库流程写入"与"外部改动"） |
| **历史审计** | 每次扫描/入库的时间、数量、结果；可回看 |

**关键的诚实设计**：
- "消失"（库里文件没了）**只从索引移除，绝不删任何东西**；界面明确写这一句
- "变更"（同名文件 size/mtime 变了）→ 标"待重编码"，**不自动重编码**（重编码很贵，且可能不是你要的）
- 批量动作都要**二次确认**，并显示"将要影响的条目数"

### 6.3 对规格的影响

| 原规格 | 修订 |
|---|---|
| 「素材库严格只读」 | → 「**写入有纪律**：只能经入库流程，预检 + 审计 + 可撤销」（§2.2） |
| 「不包含：素材上传/编辑」 | → **删除该排除项**；本期包含"入库"与"增量管理"，**不含**素材内容编辑（改图、改模型） |
| 成功标准 | 追加：⑩ 能入库并索引；⑪ 增量可审阅、可撤销；⑫ 非入库流程的库改动会被指纹护栏发现 |

### 6.4 决策已定（本轮拍板）

| # | 问题 | **决定** |
|---|---|---|
| **Q1** | 能否直接写 `G:\model`？ | **可以**。走预检 + 审计 + 可撤销（§2.2 的"写入有纪律"） |
| **Q2** | 分类怎么定？ | **不做自动分类**。默认进 `未分类\`，分类可选、可后改；应用**不读压缩包内容** |
| **Q3** | 是否自动重命名？ | **从文件名提取 `ID-<digits>`；提不到就停下来问你**，不擅自编号 |
| **Q4** | 是否含删除？ | **只提供"移出库"**（移到 `E:\移出素材\`，可还原），**不提供真删除** |

## 七、素材增删查改 与 多库管理

> 第二个范围扩张。**多库直接推翻了原定的"本期固定 `G:\model`"**。

### 7.1 ⚠️ 架构必改：索引主键从"路径"改为**稳定 UID**

原设计用 `rel_path` 标识一条素材。**CRUD 一来这个就不成立了**：改名或改目录会让路径变化，
而**图像内容没变 → 向量应该复用，不该重算**（重算一次 0.42 秒，3594 条就是 25 分钟）。

**改为**：

```
index.bin 每条 = { uid, lib_id, vector_row, ...路径属性(可变)... }
```

| 好处 | 说明 |
|---|---|
| 移动/改名/改配对 **零重编码** | 只改路径属性，向量照旧 |
| 跨库移动素材 | 向量还可以带走（同模型同 seq 时） |
| 审计与撤销有稳定引用 | 撤销时按 `uid` 找回，不受改名影响 |
| 多库检索可安全合并 | 按 `lib_id + uid` 消歧 |

`uid` 生成：`sha1(lib_id + 首次入库时的文件名 + 时间戳)` 取前 12 位——**不依赖路径**，且可读、可调试。

### 7.2 增（Create）

| 入口 | 说明 |
|---|---|
| **入库** | 拖入 包+图 → 配对 → ID → 目录（可空，默认 `未分类`）→ 预检 → 写入 → 编码（§六） |
| **补齐** | 对"图无包 / 包无图"的既有素材，补上缺的那一半。**复用原 uid**，索引只补元数据 |
| **从别库移入** | 见 §7.7 跨库移动 |

### 7.3 查（Read）

| 方式 | 说明 |
|---|---|
| 语义检索 | 中文描述 / 参考图（现状） |
| **按 ID 精确查** | 你知道编号时直接跳——`ID-595812826` |
| 按目录浏览 | 点 VR/CR/CR+VR/其他/未分类 看该目录全部素材 |
| 健康面板 | 图无包 / 包无图 / 扩展名与内容不符（实测 105 张） |
| 审计历史 | 谁在何时对哪条做了什么 |

### 7.4 改（Update）—— 六种，**标注是否需重编码**

| 操作 | 影响 | 需重编码？ |
|---|---|---|
| **改归档目录** | 图与包一起移动 | ❌ 复用向量 |
| **改 ID（重命名）** | 图与包一起改名，**原子操作**（一个失败就回滚） | ❌ 复用向量 |
| **修正配对** | 把另一张图/包与之配对 | ❌ 复用向量 |
| **替换预览图** | 换成新的图 | ✅ **必须重编码**（旧的备份进 `E:\移出素材\`，可还原） |
| **文件内容变更**（外部改过） | size/mtime 变化 | ✅ 重编码（增量视图标"待重编码"） |
| **备注 / 标记** | 只存应用侧索引，**不往库里写任何文件** | ❌ 与向量无关 |

> 「改 ID」和「改目录」都要**图和包同时成功**：先都复制到目标名，校验字节一致，再删原件；
> 任何一步失败即回滚。**绝不允许出现"图改了包没改"的半截状态**。

### 7.5 删（Delete）—— 只提供"移出库"（已定）

| 操作 | 行为 |
|---|---|
| **移出库** | 图与包一起移到 `E:\移出素材\<库名>\<时间戳>\`，**可还原**；索引条目移除（向量可留作回收） |
| 从索引移除 | 文件在库外已被删掉时用；**只动索引，不动磁盘** |
| **真删除** | ❌ 不提供 |

所有"删"都写入审计，且「撤销」能从 `E:\移出素材\` 原样还原（含原目录与原文件名）。

### 7.6 写入纪律的统一形态（四步，缺一不可）

```
① 预检   算出"将要发生的确切变更清单"（源→目标、重名、ID 冲突、体积）
② 执行   临时名写入 → 校验字节 → 原子替换/移动；多文件操作要么全成要么全回滚
③ 审计   记 {时间, 库, uid, 操作, 前后路径, 结果} 到操作日志
④ 撤销   任何一步都能反向执行；撤销本身也记审计
```

**只读操作（检索/扫描/缩略图/浏览）永远不写库**，且扫描前后比对**库指纹**，发现非本流程的改动就报警。

### 7.7 多库管理

#### 库注册表

每个库一条记录：

| 字段 | 说明 |
|---|---|
| `lib_id` | 稳定标识（建库时生成，永不变） |
| `name` | 显示名，如「室内素材」「灯具专用」 |
| `root` | 库根目录，如 `G:\model`、`E:\素材库2` |
| `folders` | 该库的归档目录集合（默认 `未分类/VR/CR/CR+VR/其他`，可增删） |
| `index_meta` | 产生该库索引的 `model_id / precision / seq / dtype` |
| `last_scan` / `fingerprint` | 上次扫描时间与库指纹 |
| `enabled` | 是否参与检索 |

#### 跨库检索的**铁律**（与"精度绑定索引"同源）

只有 **`model_id + precision + seq + dtype` 完全一致**的库才能一起检索。
不一致的库**在界面上明确标灰并说明原因**（"该库索引由 seq280 建立，与当前 140 不一致"），
**绝不静默混入**——否则结果会静默变差，这是本项目最危险的失败模式。

#### 索引文件放哪里（**已定：应用数据目录**）

| 方案 | 结论 |
|---|---|
| **A. 应用数据目录** ← **采用** | `%APPDATA%\gemma-search\libraries\<lib_id>\`。库目录保持干净（只有素材与压缩包），便于备份/同步库 |
| B. 库内隐藏目录 `<root>\.gemma-search\` | **本期不做**。"随库存放"的开关将来需要便携搬机时再加 |
| C. A+B 开关 | 同上，推迟 |

**代价（已知且接受）**：库换机/换盘要重建索引（实测 0.42 秒/张，3594 张约 25 分钟/库）。
用「重新指向」按库指纹判断是否同一个库，可避免误重建。

#### 库自身的 CRUD

| 操作 | 说明 |
|---|---|
| **添加库** | 选目录 → 扫描 → 若已有索引文件则按指纹校验后复用，否则新建（编码 0.42 s/张） |
| **移除库** | **只从注册表移除，绝不删文件**（界面明确写这句） |
| **重命名库** | 只改显示名，不动磁盘 |
| **重新指向（换盘/搬目录）** | 选新根目录 → 按指纹（文件数 + 抽样 mtime）判断是否同一个库：一致则**只改 root**，不一致则要求重建索引 |
| **跨库移动素材** | 图+包一起移入目标库；**同 model/seq 时向量随迁**（零重编码），否则目标库需重编码该条 |
| **扫描/重建索引** | 按库进行；进度与取消独立（当前库才争用 GPU） |

#### 库切换与检索范围

- 顶栏一个**库选择器**：`全部库` / 具体某个库
- 选「全部库」时：只合并**一致性通过**的库，并在状态栏显示"已合并 3 个库，2 个因精度不一致被排除"
- 结果卡片上带**库徽标**（多库时必显示），避免"这张图是哪个库的"混淆

### 7.8 决策已定（本轮）

| # | 问题 | **决定** |
|---|---|---|
| **Q7** | 索引文件放哪？ | **应用数据目录** `%APPDATA%\gemma-search\libraries\<lib_id>\`；库目录保持干净。"随库存放"开关**推迟** |
| **Q8** | 是否跨库合并检索？ | **是**。但**只合并一致性通过的库**；不一致的**显式标灰并写明原因**（如"seq280，与当前 140 不一致"），**绝不静默混入** |

## 八、传输层：要不要引入 REST API？

### 8.1 结论

**本期不引入 REST。** 客户端与后端用 **Electron IPC**；但**引擎必须做成"传输无关"的模块**，
将来加 REST 只是加一个适配层，不是重写。

### 8.2 为什么不做（三条，按分量排序）

**① CRUD 改变了风险等级（这是决定性的一条）**

应用现在能**移动、重命名、移出库**。一旦把这些能力挂到 `http://127.0.0.1:<port>`：

> **你浏览的任意一个网页都能向 `localhost` 发请求** —— 本机 HTTP 服务的 CSRF / DNS-rebinding
> 是已知的真实攻击类。一个恶意页面可以在你不知情时 `POST /api/mutate` **移走你库里的文件**。

`localhost` 不等于安全：它只挡住"从外部网络进来的人"，挡不住**从你浏览器里发起的请求**。
IPC **根本不存在这个攻击面**（浏览器无法调用 Electron 的 IPC）。

**② 两套接口会漂移，而单机单窗口不需要第二套**

IPC 已经够用：有类型、无端口、无 CORS、无鉴权、无序列化边界。再加 REST 就是同一件事两个入口，
以后每加一个能力都要写两遍，且容易只更新一边。

**③ 复杂度不便宜**

端口选择与冲突、服务生命周期（起停/重启/僵尸进程）、CORS 配置、模型必须只在一处加载（否则显存/内存翻倍）。

### 8.3 但必须为"将来可能加"付一次几乎为零的成本

引擎与传输**解耦**：

```
core/engine.mjs        ← 纯逻辑：无 Electron 依赖、无 HTTP、无全局状态
  createEngine({ libraries, modelDir, device }) → {
    search({ libIds, mode, text|imagePath, topK, folder }),   // 查
    item({ libId, uid }), thumbPath({ libId, uid }),
    reveal({ libId, uid }), collect({ libId, uid, targetDir }),
    ingest({ files, folder }), mutate({ libId, uid, op, args }),  // 增改删
    scan({ libId }), indexStatus({ libId }), indexStart/Cancel({ libId })
  }

transports/
  ipc.mjs    ← 本期唯一实现（Electron 主进程 ↔ 渲染进程）
  http.mjs   ← 将来可选：本地 REST 适配层（薄薄一层）
  mcp.mjs    ← 将来可选：DSH 的 MCP stdio 适配层
```

**测试直接打 `core/engine.mjs`**（不经传输），所以"REST 便于测试"这个理由在这里不成立——
我们不需要 HTTP 就能测。

### 8.4 什么时候才值得加（触发条件，任一成立就回头做）

| 触发条件 | 说明 |
|---|---|
| 想在**手机/平板**上浏览素材库 | 只有 REST 能做到 |
| 想让 **DSH/MCP 复用同一个模型实例** | 否则 DSH 那边要**再常驻一份** 243 MB ~ 1.6 GB |
| 想**脚本化**：定时扫描、批量入库（如从微信目录自动收） | curl 比模拟 IPC 现实 |
| 出现第二个客户端 | 任何形式 |

### 8.5 如果加，安全基线是硬要求（因为现在能写库）

1. **只绑 `127.0.0.1`**，绝不 `0.0.0.0`
2. **Token 鉴权**：每次启动随机生成，渲染进程从主进程取；`Authorization: Bearer <token>`
3. **Origin / Referer 校验**：拒绝浏览器跨站来源的请求（直接掐掉 CSRF 那一类）
4. **写操作默认关闭**：`ingest / mutate / 移出库` 需要显式开关 + token；只读接口（search/thumb/item）可先开
5. **不接受任意路径**：一切按 `lib_id + uid` 寻址，`thumb`/`open` 绝不接收客户端给的绝对路径
6. 端口冲突处理；不写系统日志、不暴露库外目录

### 8.6 一个折中选项（若你想早点拿好处）

**只读 REST（search / thumb / item）**：不写文件 → 攻击面仅限"读到库数据"，配上 token + Origin 校验后风险可控；
能立刻换来"浏览器直接看结果"与"为将来复用模型铺路"。
**但本期仍建议先不做**——IPC 已能满足单机单窗口，且等触发条件真的出现时，`transports/http.mjs` 是一天的工作量。

### 8.7 与已有工作的关系

之前那套 Python HTTP 接口（`/api/stats` `/api/search` `/api/thumb` `/api/item` `/api/open`）**不是白做的**：
它已经验证过端点划分是否好用。将来写 `transports/http.mjs` 时直接沿用这套划分即可。
