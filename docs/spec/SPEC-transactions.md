> **状态**：**待实现 —— 规格已成文，实现未开始（P4）** · **最后核对**：2026-10-12
> **权威范围**：事务日志与状态机 · 跨卷操作流程 · 启动恢复 · 撤销策略与保留期 · 并发与取消 ·
> 磁盘空间核算 · 故障注入用例 · 与界面/引擎的接口约定。
>

> `mutate` / `ingest` 等方法由主进程显式拒绝（见 `docs/spec/CONTRACT-engine-v1.md` §2.5–§2.10）。

>

## 0. 先更正：之前承诺过强

原计划写"图与包同时成功，失败则回滚"，并提到"临时名 + 校验 + 原子 rename"。

**这个说法把两件事混为一谈了**：

| 我原先的说法 | 实际成立的范围 |
|---|---|
| "原子 rename" | ✅ 只对**单个文件、同一卷内**的改名/移动成立 |
| "图与包同时成功（原子）" | ❌ **不成立**。两次 `rename` 就是两次系统调用，中间可以被杀死；跨卷移动更不是 rename（是复制+删除） |

**正确的承诺应当是**：

> 任何文件操作都做到 **崩溃一致（crash-consistent）且可恢复**，而**不是**原子。
> 即：无论在哪一步被杀，重启后系统都能**明确判定**该操作处于什么状态，并**收敛到一个确定的结果**
> （完成它，或回退它），**不会静默丢失素材、也不会留下无法识别的半完成状态**。

"回滚必定成功"同样**不能作为前提**：回滚动作本身也可能失败（目标盘掉线、权限变化、空间不足）。
所以回滚也必须是**被日志记录、可重试、可人工介入**的流程。

## 1. 事务日志（唯一事实来源）

- 位置：`%APPDATA%\gemma-search\libraries\<lib_id>\journal\`
- 形态：**每条事务一个文件** `txn-<utc>-<rand>.json`，追加写 + `fsync`。
  用"一事务一文件"而非单个大日志，是为了**避免写日志本身成为并发瓶颈与新的单点**。
- 每条记录至少包含：

```jsonc
{
  "txnId": "20261010T121530Z-a1b2c3",
  "state": "PREPARED",              // 状态机见 §2
  "op": "move-folder",              // ingest | rename-id | move-folder | re-pair | replace-image | move-out | move-lib | restore
  "libId": "L1",
  "uid": "9f3c1a2b4d5e",
  "reason": "用户操作 / 撤销 / 恢复",
  "createdAt": "...", "updatedAt": "...",
  "files": [
    {
      "role": "image",              // image | archive
      "src": "G:\\model\\未分类\\ID-1.jpg",
      "dst": "G:\\model\\VR\\ID-1.jpg",
      "stage": "G:\\model\\VR\\.gs-staging\\<txnId>\\ID-1.jpg",
      "size": 41233,
      "sha1": "…",                  // 源文件实测哈希
      "stagedSha1": null,           // 落盘后回填
      "srcDeleted": false
    }
  ],
  "indexUpdate": { "done": false, "before": { … }, "after": { … } },
  "undoOf": null                    // 若本条是撤销，指向原 txnId
}
```

**每次状态跃迁都先写日志再动文件**（write-ahead），且 `fsync` 后才继续。

## 2. 状态机

```
PREPARED ──→ STAGED ──→ VERIFIED ──→ COMMITTED ──→ CLEANED
   │            │            │             │
   │            │            │             └─→ （索引已更新、源已清理）
   │            │            └─→ 校验失败 → ABORTED（清 staging，源保持不动）
   │            └─→ 中断 → 恢复时判定为"未验证" → ABORTED
   └─→ 中断 → 恢复时判定为"未落盘" → ABORTED

任意状态中断 → 启动时进入 RECOVERY_NEEDED（仅当判定不唯一时）
```

| 状态 | 含义 | 恢复时的处理 |
|---|---|---|
| `PREPARED` | 计划已写盘，尚未动任何文件 | **回退**：删 staging（若有），源不动 |
| `STAGED` | 目标卷上已写出暂存副本 | **校验**：比对 `stagedSha1`；一致 → 前进到 VERIFIED；不一致 → ABORTED |
| `VERIFIED` | 暂存副本字节与源一致 | **前进**：执行最终 rename，进入 COMMITTED |
| `COMMITTED` | 目标已是最终名；**索引尚未更新** | **前进**：更新索引 → CLEANED；再清理源 |
| `CLEANED` | 终态，可归档日志 | 无 |
| `ABORTED` | 终态，源与索引均未变 | 无 |
| `RECOVERY_NEEDED` | **判定不唯一**（如源与目标同名但字节不同） | **停下来问人**，绝不猜 |

## 3. 操作流程（跨卷安全）

以"改归档目录（G: 内移动）"与"移动到别库（G: → E:，跨卷）"为例，**流程完全一致**——
区别只在 staging 落在哪个卷上。

```
① 预检
   · 解析 uid → 图与包的当前路径
   · 目标路径是否已存在？存在且字节不同 → 拒绝，报"目标已占用"
   · 目标卷可用空间 ≥ 需要量（§6）
   · 取锁（§5）
② PREPARED（写日志 + fsync）
③ STAGED：把图与包都复制到 **目标卷** 的 staging 目录（不覆盖任何既有文件）
④ VERIFIED：逐个比对 stagedSha1 == 源 sha1（不一致即 ABORTED）
⑤ COMMITTED：rename staging → 最终名（同卷 rename，单文件原子）
   · 图与包**逐个 rename**；若在中途被杀，日志仍停在 COMMITTED 之前的中间态，
     恢复时按"逐个核对"继续——这就是为什么需要能"完成它"而不是只依赖回滚
⑥ 更新索引（同一事务内；索引写入见 SPEC-identity §4）
⑦ CLEANED：删除源文件（移动类操作）+ 写审计
```

**两条不可动摇的规则**：

1. **源文件在 `COMMITTED` 且索引更新成功之前绝不删除。**
   （宁可留下重复文件让人看见，也不要出现"文件没了、索引还指着它"。）
2. **绝不覆盖已存在的不同内容文件。** 目标重名且字节不同 → 拒绝并让人处理；
   字节相同 → 视为幂等命中，跳过该文件而不是再写一遍。

## 4. 启动恢复

启动时扫描 `journal/*.json`，对每个非终态事务：

```
读取 state
 ├ 终态（CLEANED / ABORTED）           → 归档日志，不动文件
 ├ PREPARED                            → 回退（删 staging）
 ├ STAGED                              → 校验 staging；一致则前进，不一致则回退
 ├ VERIFIED / COMMITTED                → 前进（完成 rename + 索引 + 清理源）
 └ 判定不唯一（源与目标都存在且字节不同，
    或 staging 丢失但源已不在）         → RECOVERY_NEEDED：界面弹「待处理操作」
                                          列出：库、uid、源、目标、缺什么
                                          动作：重试 / 回退 / 保留现状（都由人点）
```

**恢复必须是幂等的**：同一个事务恢复两次，结果一致，且不会把已完成的动作再做一遍
（靠 `srcDeleted`、`stagedSha1`、`indexUpdate.done` 这些标记判定）。

**恢复报告**：每次启动若有未完成事务，状态栏给出明确提示，不静默。

## 5. 并发与取消

| 粒度 | 规则 |
|---|---|
| **库级** | 扫描/重建索引取**排他锁**：期间不允许 ingest/mutate（避免"边扫边改"导致指纹永远对不上） |
| **素材级（uid）** | ingest/mutate 按 uid 加锁；同一素材的并发操作**串行**执行，不并行写同一路径 |
| **撤销 vs 原操作** | 撤销是**新事务**，与原事务互斥（同一 uid 锁） |
| **取消** | 只在**状态边界**生效：`PREPARED`/`STAGED`/`VERIFIED` 可取消并回退；**`COMMITTED` 之后不可取消**——必须把索引更新完，否则就制造了半完成状态 |
| **死锁** | 多 uid 操作按 uid 字典序取锁 |

**界面**：同一素材正在被操作时，其卡片上的写操作禁用并提示"正在处理中"。

## 6. 磁盘空间（最坏情况，必须先算再动手）

**执行任何事务前**，在目标卷上核算：

```
需要空间 = Σ(staging 文件大小)                       // 通常是该次操作的图+包大小
         + 索引重建期的新索引                          // dim×4×count ≈ 11 MB
         + 索引重建期**新旧并存**                      // 再 +11 MB
         + 模型缓存（一次性，若尚未下载）               // ≤ 1.7 GB（fp32 档）
         + 撤销保留区（§7）
```

- 实测余量：**C: 19.7 GB · D: 107 GB · E: 484 GB · G: 44.3 GB**
- **G: 是库盘且余量最小 → 所有 staging 都落在目标卷，所以往 G: 里入库时要按 G: 的余量核算**
- 空间不足 → **在 `PREPARED` 之前拒绝**，给出"需要 X、可用 Y"的具体数字，**不进入任何文件操作**

## 7. 撤销策略与保留期

**撤销 = 反向的新事务**，不是"就地回滚"。

| 项 | 规定 |
|---|---|
| 可撤销的操作 | ingest（→ 移出库）、rename-id、move-folder、move-lib、replace-image、move-out（→ 还原） |
| 撤销的实现 | 生成反向事务（如 A→B 的撤销是 B→A），走同一状态机与同一套日志 |
| **保留期** | 移出库与替换预览图的旧文件保留在 `E:\移出素材\`；**默认保留 30 天**或**累计超过 5 GB** 时提示清理，两者先到为准 |
| 空间不足时 | 提示"撤销保留区将满"，让人选择：清理旧的 / 扩大上限 / 放弃本次撤销能力（**绝不自动删旧文件**） |
| **撤销失败** | 目标被占用 / 盘掉线 / 权限变化 → 事务停在 `RECOVERY_NEEDED`，**明确报告原因**，原文件仍在，不动无关文件 |
| 记录本身 | 审计日志**永久**保留（只记文本）；撤销所需的文件按上表保留 |

> ⚠️ **必须说清的两点**（来自审核，我完全同意）：
> 1. **库指纹不是备份。** 指纹只能检测变化，**无法恢复**被误删的文件。重要素材需要独立备份，这不是本应用能替代的。
> 2. **审计日志不是撤销能力。** 记录了"某文件被移动"不等于程序一定能安全移回。§8 的故障注入就是来验证这件事的。

## 8. 故障注入测试（**实现该模块时的硬门禁，当前未执行**）

必须**真的杀进程**，不能只做代码评审。在每个状态边界各注入一次：

| # | 注入点 | 期望结果 |
|---|---|---|
| 1 | 写 `PREPARED` 前 | 什么都没发生，重试即可 |
| 2 | `PREPARED` 后、写 staging 前 | 恢复=回退；源完好 |
| 3 | staging 写到一半 | 恢复=回退；staging 被清理；源完好 |
| 4 | staging 完成、校验前 | 恢复=校验后前进或回退，二者都可接受，但**必须确定** |
| 5 | 校验通过、rename 前 | 恢复=前进 |
| 6 | 图已 rename、包未 rename | 恢复=把包也 rename（**前进**，因为源还在），不留半截 |
| 7 | rename 完成、索引未更新 | 恢复=更新索引；**绝不出现索引指向不存在的文件** |
| 8 | 索引已更新、源未删 | 恢复=删源；即使不删也只是多一个重复文件，可检测 |
| 9 | 跨卷（G:→E:）在第 3、5、7 点各注入一次 | 同上；**E: 拔盘**时预期停在 RECOVERY_NEEDED 并明确报错 |
| 10 | 同一事务重复恢复两次 | 幂等：第二次不改动任何东西 |

**通过判据**：10 项全部满足"不丢素材、不产生无法识别的状态、结果确定且可复现"。

## 9. 与界面/引擎的接口约定

- 引擎**唯一**允许写文件的路径是事务执行器；**任何其它代码不得直接 `fs.rename`/`fs.unlink` 素材文件**。
  （用一条单测/静态检查守住这条：搜 `unlink`/`rename` 只允许出现在 `packages/engine/src/transactions/` 目录内 —— 该目录尚未创建。）
- `mutate()` 返回事务 id；界面据 id 查询状态、显示进度、提供撤销入口。
- 事务**永不**部分成功返回"成功"：返回值只有 `committed` / `aborted` / `recovery_needed`。
